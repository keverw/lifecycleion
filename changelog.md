## 0.0.1 (Feb 23, 2026)

- Initial package publish

## 0.0.2 (Feb 28, 2026)

- LifecycleManager error and warning logs now pass full error objects in `params.error` for consistency with other component-operation log paths

## 0.0.3 (Feb 28, 2026)

- LifecycleManager, added `attachSignalsBeforeStartup` for attaching signal handlers before startup begins while preserving the original `attachSignalsOnStart` behavior
- LifecycleManager now automatically stops components that finish starting after LifecycleManager shutdown has already begun
- LifecycleManager, startup timeouts without `onStartupAborted()` now auto-stop the component if that delayed startup later completes

## 0.0.4 (Mar 2, 2026)

- LifecycleManager, fixed `enableLoggerExitHook()` so `logger.exit()` calls made during an already-running shutdown are deferred and completed after shutdown finishes instead of being left pending

## 0.0.5 (Mar 3, 2026)

- CurlyBrackets now supports array index paths such as `{{users[0].name}}`, `{{matrix[0][2]}}`, and mixed object-array traversal with existing fallback behavior preserved
- Logger redaction now supports the same mixed object-array paths in `redactedKeys`, including paths like `users[0].password`
- CurlyBrackets and logger docs/tests now explicitly cover nested path fallback behavior, primitive intermediate values, falsey terminal values, and `Error` interpolation behavior

## 0.0.6 (Mar 3, 2026)

- CurlyBrackets now supports quoted bracket keys such as `{{user["display-name"]}}` and mixed paths like `{{users[0]["display-name"]}}`
- Logger redaction now supports matching quoted bracket-key paths such as `users[0]["password-hash"]` in `redactedKeys`
- Shared internal path parsing now rejects unsupported syntax cleanly instead of partially tokenizing invalid paths

## 0.0.7 (Mar 4, 2026)

- Logger messages now render from redacted params when `redactedKeys` are configured, so templated sensitive fields are masked in `message` as well as `redactedParams`
- CurlyBrackets and logger redaction now share an internal value-stringification helper so arrays, objects, and `Error` values are normalized consistently before rendering or redaction, non-string values are now always stringified before passing to redaction functions

## 0.0.8 (Mar 18, 2026)

- Added `lifecycleion/dev-mode`, a runtime-settable dev/production mode flag with auto-detection from CLI args (`'dev'`/`'prod'`) or `NODE_ENV`, first-wins semantics for HTML injection compatibility, and `overrideDevMode()` for test/tooling use

## 0.0.9 (Mar 19, 2026)

- LifecycleManager error and warning log messages now include `error.message` inline (e.g., `"Component failed to start: Connection refused"`) so failure reasons are visible in plain log output without a custom structured sink

## 0.0.10 (Apr 7, 2026)

- Added the new adapter-based HTTP client foundation in `lifecycleion/http-client`, including the shared `HTTPAdapter` contract, fluent request builder, retries, redirect handling, cancellation, interceptors, response/error observers, request tracking, and the default `FetchAdapter`
- Added `MockAdapter` plus server-side cookie jar support and shared HTTP client request/response utilities
- Added `lifecycleion/http-client-node` with a Node adapter for server-side HTTP requests, streaming downloads, multipart uploads, Unix sockets, and TLS/mTLS options
- Added `lifecycleion/http-client-xhr` with an XHR adapter for environments that expose `XMLHttpRequest`, including real per-chunk upload/download progress, redirect detection, and Playwright-based browser integration tests
- Added `lifecycleion/domain-utils`, hardened helpers for normalizing and matching domains and origins, including IDNA/TR46 normalization, IPv6 literal support with zone-ID rejection, wildcard CORS matching with PSL/IP-tail guards, credentials-safe origin matching, and re-exports of `tldts` helpers (`getDomain`, `getSubdomain`) so consumers don't need a separate install
- Added `lifecycleion/lru-cache`, a TTL-aware LRU cache with configurable max entries, optional byte-size limit, per-entry TTL overrides, automatic expiration, and pluggable size calculators
- Fixed test-only TypeScript assertion issues reported in some unit test cases. No runtime or API behavior changed for them
- Added `lint` and `type-check` to `prepublishOnly` to strengthen the future release process

## 0.0.13 (Apr 19, 2026)

- Repeated shutdown escalation now tracks request count and timing window across real signals, keyboard-triggered shutdown requests, and programmatic `triggerShutdown()` calls that flow through the same signal callback path

- Repeated shutdown escalation now supports optional `armedAfterFailureMS` overrides so failed or stalled shutdown attempts can stay force-armed longer than the default derived post-failure window
- LifecycleManager shutdown logs now distinguish between the normal first shutdown request, repeated shutdown requests still being tracked, and repeated-request escalation when the force threshold is reached

## 0.0.14 (Apr 28, 2026)

- LifecycleManager now detects when a stalled component's original `stop()` or `onShutdownForce()` promise eventually resolves and automatically transitions it from `stalled` to `stopped`, clearing the stall record and emitting a `component:stalled-resolved` event. A per-component stop generation token prevents a late-resolving promise from affecting a component that has already been restarted since stalling.
- Docs now document the `stop()` promise-deduplication pattern as the recommended approach when `onShutdownForce()` should join an already-running `stop()`, and the `onGracefulStopTimeout()` pattern as an alternative for unblocking `stop()` without a concurrent second close.
- BaseComponent now exposes a protected `reportUnexpectedStop(error?)` method. Call it when the component detects an internal failure (crashed server, lost connection, exited worker) to let the manager mark it stopped, store the error as `lastError`, emit `component:unexpected-stop`, and then emit the canonical `component:stopped` event for the resulting stopped state. A subsequent `stopAllComponents()` call skips the already-stopped component and proceeds normally. The call is a no-op once the manager begins stopping or unregistering the component, and the handler is automatically re-armed after each successful restart.
- If `reportUnexpectedStop()` fires during `startAllComponents()`, required components now fail the bulk startup with `code: 'component_unexpected_stop'` and trigger rollback of later-started components, while optional components are recorded in `failedOptionalComponents`.
- Added `component:unexpected-stop` event (payload: `{ name, error? }`) emitted when a running component calls `reportUnexpectedStop()`, immediately before the follow-up `component:stopped` event.
- BaseComponent now exposes a protected `getSelfStatus()` method that returns the component's own `ComponentStatus` from the manager without requiring the caller to pass the component name.

## 0.0.20 (Aug 21, 2026)

- **Added `crl` to `NodeAdapterConfig`:** certificate revocation lists, so a server certificate whose serial has been revoked is rejected even though its chain and hostname still verify. Revocation failures resolve as status `495` like other TLS certificate errors. The value is read on every request, so refreshing a revocation set does not require rebuilding the adapter, and no connection-pool handling is needed. `crl` is part of Node's pool key, so changing it partitions the pool and a socket established under the old CRL is never reused under the new one.
- **Concatenated CRL bundles are split for you.** Node reads only the **first** CRL of a concatenated PEM string and silently ignores the rest, unlike `ca`, which reads every certificate in a bundle. The bundle is the standard interchange format. Apache documents `SSLCARevocationFile` as "the concatenation of the various PEM-encoded CRL files," nginx and HAProxy agree, and `openssl verify -CRLfile` reads a whole bundle. This is Node diverging from the library it links rather than an OpenSSL limitation. The adapter splits bundles on the RFC 7468 boundary, including strings nested inside an array, so `[bundleOfTwo, oneMore]` contributes three CRLs. This includes **Buffers**: `fs.readFileSync('bundle.pem')` without an encoding returns one and its contents are PEM like any other bundle, so passing Buffers straight through would leave the most ordinary way of loading a file silently truncated. In testing, a bundle whose second CRL revoked the server's certificate accepted the connection as a Buffer and rejected it once split. DER Buffers pass through untouched, since DER encodes exactly one CRL. Note also that OpenSSL uses the **first** CRL it has for a given issuer rather than the newest, so a bundle must not contain two CRLs for the same issuer. Without this the failure is `UNABLE_TO_GET_CRL`, which reads as "no CRL supplied" rather than "your bundle was truncated." A bundle whose first entry happens to cover the root in use appears to work until the roster or export order changes.
- **Revocation failures are now classified as TLS certificate errors**, so they resolve as status `495` rather than a generic transport failure. This covers `CERT_REVOKED` plus every CRL verification code OpenSSL exposes, matched by property rather than by name, since the message-text fallback catches almost none of them (`CRL has expired` and "format error in CRL's lastUpdate field" contain none of the words it looks for).
- **Only PEM blocks and whitespace are accepted in a `crl` string.** A truncated or corrupted CRL, a damaged delimiter, or decoded `openssl ... -text` output is refused with an error rather than silently dropped. Splitting keeps only complete blocks, so a cut-short entry would disappear while the intact ones stayed in force, leaving the caller enforcing a set they never supplied, with no error. Passing the string through unsplit is no better, since Node reads its first CRL and ignores the rest. The rule is exact rather than heuristic because a parser cannot distinguish a half-written CRL from a line of commentary, so admitting the second necessarily admits the first. Strip annotations before passing a bundle.
- **Bun compatibility note:** Bun ignored `crl` entirely through 1.3.14. It accepted a revoked certificate with no error, no warning, and no throw on a malformed CRL, meaning the option was never read. The same was true of `minVersion`, `maxVersion`, and `secureProtocol`. All are fixed in Bun 1.4.0, which matches Node 25.9.0 on every case tested. **Require Bun >= 1.4.0 if you depend on these options for security.** The enforcement tests probe the runtime and skip where `crl` is unsupported rather than passing for the wrong reason. The bundle-splitting tests run everywhere.
- Two caveats worth reading before enabling `crl`, both fail-closed and therefore safe, but both able to refuse healthy connections: every certificate in the chain needs a covering CRL (`X509_V_FLAG_CRL_CHECK_ALL`, so a partial CRL set refuses every root it does not cover, even unrevoked ones), and CRLs expire (`CRL_HAS_EXPIRED` blocks good certificates past `nextUpdate`). See `docs/http-client.md`.
- Adapter contract types (`HTTPAdapter`, `AdapterRequest`, `AdapterResponse`, `AdapterType`, `AdapterProgressEvent`, `HTTPMethod`) are re-exported from the adapter subpaths, so code driving an adapter directly no longer has to import types from `lifecycleion/http-client`. Type-only, so nothing is added to the runtime bundle. The node subpath also re-exports the response-streaming types.
- Pinned `@types/bun` to 1.3.14. `@types/bun` 1.4.0 declares `off`/`removeListener` overloads for its `memoryPressure` event directly on `NodeJS.Process`, which shadows the generic `EventEmitter` overloads that `@types/node` relies on being inherited, breaking `process.off('SIGINT', ...)` and every other signal detach at the type level. Types only, so no runtime or security impact.
- Applied `brace-expansion` and `js-yaml` overrides to clear two high-severity advisories reaching the tree through ESLint's dev-only dependencies.
- Dependency refresh within existing ranges: `find-my-way` 9.8.0, `tldts` 7.4.10, `uuid` 14.0.2, `@playwright/test` 1.62.1, and the `typescript-eslint` packages 8.67.0.

## 0.0.21 (Aug 25, 2026)

- **Fixed callback error reporting on Node.js.** `safeHandleCallback()` and `safeHandleCallbackAndWait()` report failures by dispatching an `ErrorEvent` of type `'reportError'` through `globalThis.dispatchEvent()`. Node 25 added a global `ErrorEvent` constructor but did **not** make `globalThis` an `EventTarget`, so `dispatchEvent`, `addEventListener`, and `removeEventListener` are all `undefined` there. This meant callback errors were caught and then silently dropped on Node. The existing tests missed this because they run under Bun, which provides the browser-style global event methods. The same gap made `logger.registerReportErrorListener()` return `'not_available'` on Node.
- **Added [global-event-target](./docs/global-event-target.md)** (`lifecycleion/global-event-target`), a conservative polyfill that supplies the missing global event methods, backed by a single shared `EventTarget`. It installs only when all three methods are absent, so native and user-installed implementations are never overwritten. It is idempotent, keeping the backing target and install flag in one shared object on `globalThis` (`__lifecycleion_global_event_target__`, the same style as `dev-mode` and `process-signal-manager`) so repeated initialization and multiple copies of the package share it. Installed properties are non-enumerable and bound to the backing target. A partial or foreign surface (some methods present, others missing or present but not callable, such as `globalThis.dispatchEvent = null`) is deliberately left alone rather than mixing methods from unrelated targets or clobbering a value the application put there. A member explicitly assigned `undefined` counts as absent, since that is how a global gets cleared. Reporting is skipped there, and the helpers still return their normal results. Because installation runs during module initialization, it never throws. A non-extensible global object (`Object.freeze(globalThis)`) or a non-configurable property returns `'blocked'`, and every global it reads, including the three methods and the `EventTarget` constructor, goes through one guarded read, since reading a global runs its getter and a getter can throw. A throwing accessor is reported as `'partial'` (or `'unsupported'` for the constructor) rather than crashing the import. The reporting path is likewise throw-proof. It can drop a report, but never raise an error while reporting one rather than breaking the import of `safe-handle-callback` and everything downstream of it. A definition rejected despite that preflight is rolled back so nothing is left half-installed. Importing `lifecycleion/safe-handle-callback` or `lifecycleion/logger` installs it, so for most users this is transparent. Browser and Bun behavior is unchanged, and `ErrorEvent` is never polyfilled. Node 25+ is the supported floor and provides it natively.
- **Added Node-runtime tests.** A Bun-only suite cannot catch this class of bug, since Bun has the globals natively. The new suite bundles fixtures with `Bun.build({ target: 'node' })` and runs them under the real `node` binary, asserting that a plain `globalThis.addEventListener('reportError', ...)` receives both synchronous throws and rejected async callbacks, that the reported `ErrorEvent` carries the wrapped callback name and original error details, that nothing becomes an uncaught exception or unhandled rejection, and that repeat installation and pre-existing global implementations are handled as documented. It also pins down that Node itself has `ErrorEvent` but no global event methods, so the assumption behind the fix fails loudly if it ever changes.
- `sideEffects` is now a list rather than `false`: the installation happens at module initialization, and a blanket `sideEffects: false` would let a bundler drop a bare `import 'lifecycleion/safe-handle-callback'` despite the documented guarantee that importing it installs. Only the `safe-handle-callback` and `logger` entry files are listed, so the rest of the package stays fully tree-shakeable, and the reporting path re-runs the install itself so a swallowed error can never be a packaging artifact.
- Documentation now describes `'reportError'` as Lifecycleion's reporting convention built from web-standard primitives (`ErrorEvent` plus the global `EventTarget` methods), rather than implying the event type itself is a web-standard API.
- **Fixed unsafe retries on `FetchAdapter` when a response body was truncated.** A body that failed after headers arrived (peer reset mid-body, premature close, short read against `Content-Length`) rejected out of `send()` because the body read sat outside the adapter's `try`/`catch`. That landed on `HTTPClient`'s generic network-error path as `status: 0`, which is in `RETRYABLE_STATUS_CODES`, so the request was retried up to the policy limit. Headers arriving means the server received and processed the request, so replaying a non-idempotent write could apply it twice. `NodeAdapter` already resolved these as `isStreamError` and never retried them, so **the same truncation was retried on `fetch` and not on Node**. This was a correctness difference rather than a performance one, and one that would not show up for anyone testing on Node and shipping on Bun or in a browser. Note that the client's retry guard (`!adapterResponse.isStreamError`) was correct throughout and never fired: it only runs on a _resolved_ adapter response, and a throw out of `send()` never becomes one. `FetchAdapter` now resolves with `isStreamError: true`, `streamErrorCode: 'stream_response_error'`, the real HTTP status, and the underlying `errorCause`. A caller's `AbortSignal` still re-throws so cancellations stay classified as cancellations rather than network faults. It now carries the response metadata out with it, since the adapter sees one composite signal and cannot tell a caller cancel from a per-attempt timeout. Without that, a timeout firing mid-body-read lost the real status and left an otherwise terminal post-header failure eligible for retry, the same divergence in a second guise. `NodeAdapter` already tagged its response-stream aborts this way. The client sorts the two apart. (Carrying the metadata out was necessary but not sufficient. See the entry below on which rejections the client would accept it from.)
- **Added `MockResponse.streamError`** so the `isStreamError` branch can be tested without a real socket. Pass `true` for the default `'stream_response_error'`, or name the code explicitly. The mock reports the `status`, headers, and cookies you set, matching a real post-header failure, where the status is known and only the body is lost, while forcing `body` to `null` regardless of what the handler returned.
- **Documented which `isStreamError` guarantees are Node-only.** `NodeAdapter` covers streamed and buffered bodies and distinguishes `stream_write_error` from `stream_response_error`. `FetchAdapter` covers buffered bodies in both server runtimes and browsers. Headers have arrived by then, so the status is readable either way, but it always reports `stream_response_error`, since `fetch` buffers the body and exposes no per-chunk delivery to tell a local write failure from an upstream one. `XHRAdapter` does not report the flag at all, and that one is a spec-level limitation rather than a browser inconsistency: setting `XMLHttpRequest`'s error flag sets the response to a network error, which forces `status` to `0`, leaving no evidence that headers ever arrived. A mid-body truncation is therefore indistinguishable from a connection refused there, stays an ordinary transport failure. For an idempotent method that is still eligible for retry, so a truncated `GET` is silently re-fetched rather than reported with its real status. A non-idempotent write is spared only because `XHRAdapter` never supplies `wasDefinitelyNotSent` and the default rule blocks a replay for want of proof, not because the truncation was recognized, so enabling `retryNonIdempotentMethods` removes that protection. Browser code making replay decisions on non-idempotent writes should prefer `FetchAdapter`.
- **`NodeAdapter` now decides transport-failure replay safety from the error code** rather than from a body-byte count. The old test was `uploadedBodyBytes === 0`, which reports `0` for a request with no body, so an empty-body `POST` whose headers reached the server and then lost the connection was marked safe to replay. The counter also tracks bytes handed to the stream rather than bytes on the wire, so it could be non-zero for a connection that was never established. Only codes proving no connection happened (`ECONNREFUSED`, `ENOTFOUND`, and similar) are now treated as replayable. `ECONNRESET`, `EPIPE`, `ETIMEDOUT`, and anything unrecognized fall on the side of possible delivery. `EHOSTUNREACH` and `ENETUNREACH` are excluded despite reading like connect-time failures, because an ICMP unreachable arriving for an established connection surfaces on that connection with the same code. Seeing one does not rule out a request that was already written and received. That verdict is carried on the new `wasDefinitelyNotSent` rather than on `isRetryable`, which blocks retries for every method and is reserved for the case below. The error code is also the only signal that behaves identically on Node and Bun. `socket.bytesWritten` is not implemented under Bun and `socket.connecting` reports the wrong value there, so either would have silently claimed "nothing sent" for a request the server had already received.
- **`isRetryable: false` is now reserved for failures no method should retry.** It blocks a retry for every method, but `NodeAdapter` was setting it once a request body had started going out, including for a mid-upload socket error and both body-write failure paths. That stopped retrying an idempotent `PUT` or `DELETE` after an ordinary transport blip, the case a retry is most likely to fix, and it overrode `retryNonIdempotentMethods` where the caller had stated a replay is safe. Whether a partly-sent request may be replayed is the method question below, and withholding `wasDefinitelyNotSent` already answers it, so those three vetoes are gone. The remaining use is a rejected TLS certificate, where another attempt genuinely cannot succeed.
- **`FetchAdapter` now classifies TLS certificate failures as `495`**, matching `NodeAdapter`, instead of letting them arrive as `status: 0`, which is in `RETRYABLE_STATUS_CODES`, so a bad certificate was retried to the policy limit, failing identically each time. This is a server-runtime classification: Bun exposes the OpenSSL code on the rejected error and Node hangs it off `cause`, both of which are now recognized, while a browser reports an opaque `TypeError` with neither and such a failure keeps the ordinary transport-error shape. `XHRAdapter` cannot classify these at all.
- **Added `AttemptEndEvent.retrySuppressedReason`** so a suppressed retry explains itself. `willRetry: false` could not distinguish a policy declining from a safety rule stepping in, which made the non-idempotent default below discoverable only by reading this changelog. When the status alone would have allowed a retry, the event now names what stopped it: `adapter_veto` (the adapter reported `isRetryable: false`), `stream_error` (the body failed after headers arrived), or `non_idempotent_method`. Absent when a retry was scheduled, when no policy is configured, when the policy has no attempts left, or when the status was never retryable. In those cases nothing was suppressed.
- **Added `MockResponse.transportError`** so the replay rules are testable without a socket. `MockAdapter` could simulate cookies, redirects, delays, and (as of this release) stream errors, but had no way to produce a failure with no response at all, so none of the rules below could be exercised against it. It delivers nothing from the handler's response (no body, headers, cookies, or terminal progress) and accepts the signals a real adapter would attach: `wasDefinitelyNotSent` for proven non-delivery, `isRetryable: false` for a failure no method should retry, and a diagnostic `status` such as `495`.
- **Retries no longer replay `POST` and `PATCH` by default.** The retry decision never consulted the request method, so with a retry policy active a `POST` was retried on a `500`, even though the handler definitely ran and may have committed, making it a stronger case against replay than the transport failures above. `HTTPClient` now declines to retry the methods RFC 9110 does not define as idempotent: never after a real HTTP response, never after a thrown adapter error or per-attempt timeout, and after a transport failure only when the adapter reports the new `AdapterResponse.wasDefinitelyNotSent: true` (proof that no request bytes reached the server). The transport condition is part of the rule rather than a shortcut: on a real response delivery is already settled the other way. `isRetryable` deliberately does **not** grant this exception. It is a retry hint whose contract only ever defined `false`, so a custom adapter may set it `true` for a failure it considers transient without knowing whether the request was delivered, and reading that as proof would replay a write after an ambiguous failure. `PUT` and `DELETE` are unaffected. Both mutate, but both are idempotent by definition, so replay is safe. Set `retryNonIdempotentMethods: true` on the client config, or `.retryNonIdempotentMethods(true)` per request, to restore the old behavior for writes guarded by an idempotency key. This only ever removes retries. It never adds one, and does nothing unless a retry policy is active.
- **Set-Cookie now survives a post-header stream abort.** Cookies were stored only when an adapter resolved a response. As a result, `Set-Cookie` was dropped when the body was cut short by a timeout, a stream abort, or the caller cancelling mid-read. The identical response arriving intact stored it, as did a buffered stream failure that resolved rather than threw. Headers had arrived in every one of those cases, which is the whole basis for the existing behaviour of applying cookies from error responses to follow-up requests, as browsers and curl do.
- **The response-stream abort marker, not the error's name, is what routes a post-header abort.** The client's branch for a body that failed after headers arrived required both the adapter's marker and an error named `AbortError`. But an adapter tags that throw whenever the attempt signal aborted mid-body, and the rejection it hands back is whatever the runtime produced. Undici surfaces a timeout during the body read as `TypeError: terminated`, not as an `AbortError`. The tag arrived on an error the gate then refused. With the cancel signal untouched, because a per-attempt timeout aborts only the timeout controller, the throw fell past the cancellation check too and landed on the generic network path: the tagged status and headers discarded, `status: 0` reported, and since `0` is retryable, a `503` whose body was cut short replayed against a server that had already answered. An idempotent method is not spared, the method rule below covering only `POST` and `PATCH`. The marker is now the whole gate. This is what makes the previous entry's fix effective rather than merely present.
- **A marker is trusted only when it reads exactly `true`.** Both marker checks tested for the property rather than its value, so an ordinary adapter error carrying one as `false` reached a branch meant for a tag an adapter deliberately set. For the response-stream marker that branch is terminal _and_ writes to the cookie jar, so an error that also carried stale `streamAbortStatus`/`streamAbortHeaders` fields had that response's `Set-Cookie` filed under the current request's URL. For the XHR browser-timeout marker, a deliberate cancel reported `isTimeout`. Every adapter writes the literal `true`, so nothing is lost by asking for it. Both reads are also guarded now: the value is whatever a runtime, a library, or a caller's abort reason produced, and a throwing getter would otherwise escape the classifier that exists to normalize the failure.
- **Fixed a DNS failure reading as a permanent certificate failure.** The TLS classifier falls back to matching certificate wording in the error message, and that message is one the runtime built. For a DNS or connect failure, it has the hostname interpolated into it. `getaddrinfo EAI_AGAIN certificates.internal.corp` matches on the host's name alone, so any deployment calling a `certificates.*` or `certificate-authority.*` host had every DNS blip resolve as `495` with `isRetryable: false`. This veto holds for every method, including an idempotent `GET`, turning the most transient failure there is into a permanent one. Retrying a genuine certificate failure wastes milliseconds. Refusing to retry a DNS blip defeats the point of having retries. A code that names a transport failure now settles the question and the message is not consulted. **This predates the changes above:** `NodeAdapter` has used this classifier all along, so the false positive was live on Node, and `FetchAdapter` adopting it only widened the surface. Note the fix could not simply be "skip the message whenever the error has a code", because OpenSSL exposes far more verification failures than the classifier names, and `CERT_UNTRUSTED`, `CERT_REJECTED`, `HOSTNAME_MISMATCH`, `UNABLE_TO_GET_ISSUER_CERT` and `INVALID_CA` match no code rule at all, so the message is the only thing that catches them. Nothing covered those nine, which is how a change breaking every one of them could leave the suite green. They are covered now.
- `CRL` is matched as an underscore-delimited token rather than as a substring. This keeps the argument for asking by property rather than by list. Future OpenSSL CRL codes still match, including the plural `NO_CRLS_INCLUDED`, while excluding `CRLF`, the one word that shares the prefix by accident and the one a header- or framing-error code would plausibly be named for. Such a failure is a connection problem, the opposite of a permanent certificate verdict.
- Clarified in the `isStreamError` doc comment and in [http-client](./docs/http-client.md) that for replay decisions a stream error groups with a **real response**, not with a transport failure. Both leave you without a usable body, but a `status: 0` transport failure may never have reached the server, while a stream error means it arrived and may have committed, just as a 500 tells you. The resemblance is superficial and inverts the decision.
- **A truncated `3xx` keeps its redirect target.** `FetchAdapter`'s post-header failure path reported the real status but not `wasRedirectDetected` or `detectedRedirectURL`, which the intact path resolves for every response. So with `followRedirects: false`, a `302` carrying a `Location` header whose body was then cut short arrived with nothing to say where it pointed, while the identical intact response reported the resolved absolute URL. The headers arrived before the body failed, so the target is known just as well either way.
- **A truncated `3xx` is no longer followed.** `HTTPClient` checked the redirect status before the failure state, so with `followRedirects: true` a `302` whose body failed after headers arrived was followed like any other. The `Location` header had survived, which is exactly what made this quiet: the hop continued, a healthy destination answered `200`, and the attempt that failed was no longer the one being reported. This left a documented terminal failure resolving as a success. A per-attempt timeout striking mid-body is the sharpest form of it, since `wasTimeout` rides on the attempt result and the next hop overwrites it with its own. Redirect following is now gated on `!isStreamError`, so the response reports the real `3xx` status with `isStreamError`, the timeout if there was one, and still `wasRedirectDetected` / `detectedRedirectURL`, so the caller loses none of what the previous entry restored. The `followRedirects: false` branch is deliberately not gated: it follows nothing, and reporting a truncated `3xx` exactly as it reports an intact one is what that branch is for.
- **A truncated `3xx` reported by a _thrown_ abort keeps its redirect target too.** Both adapters resolve `wasRedirectDetected` / `detectedRedirectURL` on a post-header failure they hand back as a response, but when the body fails via a tagged throw the client rebuilds the response itself from `streamAbortStatus` / `streamAbortHeaders`, and those two fields were simply never set on it. That was invisible while such a hop was still followed. Making a stream error terminal for a `3xx` is what exposed it, since nothing downstream resolves the target any more. A per-attempt timeout striking mid-body, the sharpest case for the entry above, therefore reported `wasRedirectDetected: false` on a `302` whose `Location` header had arrived intact, and with `followRedirects: false` the same response came out the other way round: that branch hardcodes the flag, so it claimed a redirect and had no destination to name. The client now resolves both from the tagged headers, exactly as `FetchAdapter` does on the path where it resolves rather than throws.
- **A rejected install no longer destroys the shared state it replaced.** Rollback exists so a failed install leaves the environment exactly as found. That held for the three methods, where deleting them is the undo, but not for the shared-state key: once an unusable state object could be _replaced_ rather than reused, rolling back deleted it outright, so a failed install destroyed another copy's object as a side effect. The original descriptor is now put back in place and never deleted first, since whatever rejected the definition may have sealed the global object and re-adding a key to a non-extensible object throws. Reaching this at all takes the one piece of caller-controlled code that runs between the preflight and the first definition, the `EventTarget` constructor itself. A fixture uses exactly that to seal the global mid-install, and asserts the original object comes back by identity.
- **A backing target whose `bind` returns a non-function no longer installs.** `bind` is an ordinary property on a method, so a target reachable through the shared global can replace it with something that returns a non-function without ever throwing, while every cheaper check passes, since the three members still read as functions. Guarding only a throwing `bind` put that value straight onto `globalThis` and reported `'installed'`: `addEventListener` became a number, `isGlobalEventTargetPolyfilled()` claimed the polyfill was in place, and every `reportError` dispatch threw `TypeError`. That is strictly worse than not installing, because these methods start out absent. What `bind` returns is now checked, and a target that fails it is passed over for a fresh one. A related gap in the result codes is closed at the same time: an `EventTarget` constructor that is callable but cannot produce a usable instance. It may throw on construction or return something that cannot service the three methods. The constructor now reports `'unsupported'` because nothing was ever offered to the global object, so `'blocked'` would have been the wrong story, and nothing is left behind.
- **The backing event target is re-validated at the moment the globals are bound to it.** `installGlobalEventTarget` validated the shared state's `target` when it read the state, then bound `globalThis.addEventListener` and friends to a second, unguarded read of the same field, the one read in the module that actually matters. The field belongs to an object anything on the global object can reach, so a getter returning a real `EventTarget` when probed and something else afterwards would have bound the three methods to a value that never passed a check, and a getter throwing on that second read turned a perfectly viable install into `'blocked'` with all three methods rolled back, leaving Node with no event methods at all. The bind now takes the target and the three methods off it in one validated pass. Binding a method read later would have been the same gap moved one level in, since a method on somebody else's object is no more ours to trust than the field holding it. A target that no longer vouches for itself is treated as absent: installation proceeds with a fresh one, which orphans nothing, since a target that cannot service the three methods never had listeners registered through this module.
- Corrected the `retrySuppressedReason` documentation for `adapter_veto`, which said no built-in adapter produces it. `NodeAdapter` and `FetchAdapter` do not, for the reason given, but `MockAdapter` does. `transportError: { isRetryable: false }` leaves the default retryable `status: 0` in place, so the veto is what stops the retry. That is the point of the example the same page already gives.

The previous run's error stayed on a component that was running again, so a reader taking it for the current run was told the restart had not worked; a clean late stop already cleared it for the same reason. It is cleared when the new run reaches `running`, not when it begins, so it still names the previous failure while the restart is `starting`; `ComponentStatus.lastError` now documents that, and a reader wanting "is this component failed" should read it together with `state`.

Reported callback errors retain the original thrown value on `event.error.cause` instead of embedding a pre-rendered table in the wrapper message. Sinks can implement `writeDiagnostic()` to accept the structured `LoggerDiagnostic` directly; otherwise they receive a pre-rendered error entry tagged `lifecycleion-diagnostic`. A diagnostic delivery failure ends at guarded `console.error`, preserving both the original diagnostic and the secondary failure, and is never dispatched again; even a malformed payload passed through the logger's public `emit()` is read guardedly there. `ConsoleSink` honors mute and close for diagnostics too. Close-time sink failures skip sinks that are themselves being closed, reaching an external diagnostic listener or guarded console instead. That is the logger's diagnostic channel, for a `close()` that throws. A `FileSink` / `NamedPipeSink` close-time `'lost'` / `'no_entry'` report goes to `onError` instead; logging those through the logger being closed is dropped with no diagnostic fallback, because the handler returned successfully. Report them with `console.error` or a destination this logger does not own. Logger-specific failure callbacks were removed before release, leaving one routing rule for all logger-owned failures. `addDiagnosticSink()`, `removeDiagnosticSink()`, and `getDiagnosticSinks()` support runtime configuration.

Removing or clearing a later listener from a callback no longer skips that listener during the current emission, and a callback added during dispatch waits until a later emission; a nested emission takes its own current snapshot. Cookies imported from browser-oriented jars with domains such as `.example.com` are canonicalized to `example.com` and match both the apex and its subdomains instead of being stored but never sent.

Objects are masking configurations, not replacement values. The default masks 90% of sufficiently long strings and fully replaces short strings and values rendered from non-string types. Invalid or unreadable redaction lists fail closed; in particular, `sensitiveFieldNames: null` no longer renders in the clear.

The logger entry point now exports the shared failure types plus `FileSinkHealth`, `NamedPipeSinkHealth`, and `FlushResult`.
- **BREAKING: the queueing sinks are bounded and level-filtered by default.** `FileSink` and `NamedPipeSink` now retain at most 10,000 queued entries unless `maxQueueSize: -1` is set, dropping the oldest entry and reporting/counting the loss when full. `NamedPipeSink` now defaults to `LogLevel.INFO` and adds `minLevel`, `setMinLevel()`, and `getMinLevel()`; set `LogLevel.DEBUG` to preserve the previous all-level pipe output.

A `basename` such as `'nested/app.log'` that used to write into a subdirectory must move that segment into `logDir`.
- **BREAKING: `CurlyBrackets` renders are capped at one million characters by default.** A template whose substituted values exceed `maxRenderLength` (default 1,000,000) is cut with a `[max length exceeded]` marker and reported through `onTruncate`, where `main` had no bound. Pass `maxRenderLength: Infinity` to a standalone `lifecycleion/curly-brackets` caller that relied on unbounded output; the logger, `stringifyValue()` and `errorToString()` share the same default.
- **BREAKING: `serializeError()` output changed shape.** A `bigint` leaf is rendered as its digits, `function` and `symbol` leaves become `<function>` / `<symbol: …>` markers rather than being dropped, a non-string `name`, `message` or `stack` is rendered rather than passed through, and depth and total-size limits plant markers where they cut. Consumers that parse the serialized form strictly - an IPC schema, a stored fixture - must accept the markers.
- **BREAKING: `TmpDir` refuses a `prefix` or `postfix` holding a path separator or control character.** The constructor throws `ErrTmpDirConfigErrorNamePart`; `prefix: 'foo/bar'` used to create, and with `unsafeCleanup` recursively delete, a directory outside `baseDirectory`.
- **BREAKING: an unquoted `CurlyBrackets` path segment now admits `-`, `@`, and `$`, and any Unicode letter, digit, or mark.** This is what lets `{{user.password-hash}}` and `{{user.@id}}` resolve and redact. The cost is that a hyphenated or `@`-prefixed phrase in braces - `{{opt-in}}`, `{{2024-01-01}}`, `{{@mention}}` - now parses as a path, resolves to nothing, and renders the fallback (`(null)` by default) where it used to be left verbatim. Prose with spaces or other punctuation, such as `{{Hello world}}`, is still left as written, and substituted values are never re-scanned, so text that _contains_ such a placeholder - a component's own error message logged as `{{error.message}}` - survives intact. Escape the braces if a literal hyphenated placeholder must render.
- Redaction paths now use the same fail-closed semantics across logger params, `errorToString()`, `stringifyValue()`, and `redactValue()`, and support array wildcards such as `users[*].password` / `users.*.password`. A path identifies a location rather than every alias of the same object. `LogEntry.redactedParams` is a fresh top-level bag with copies only along masked branches, so unmasked nested values remain caller-owned references; custom sinks should read or serialize it before awaiting and must not mutate nested values. A container the pre-walk normalization cannot copy - an array or prototype past the entry cap, a read that throws - is now withheld with the failure marker and reported, rather than left in place where a key hidden from enumeration could still be rendered. A named member whose read throws during that pass is withheld the same way, where it used to be skipped with the caller's accessor left in place for the walk and the renderer to call again - an accessor that throws once and answers a secret afterwards was the one second-read case the pass still let through. `errorToString()`, `stringifyValue()` and `redactValue()` now read their options object once, through a guard, before the render begins: an options object with a throwing accessor used to escape the never-throws promise, since the reads sat outside the `try` that keeps it, and now falls back to each option's documented default. An entry with path syntax that the grammar refuses - a trailing dot, an unterminated bracket - is now reported as a logger diagnostic or through the standalone renderer's `onFormatError`, under `kind: 'redaction'` with the entry as written; its literal reading is still used, and a valid path that merely matches nothing stays silent. The top-level `params` bag is bounded as every nested container already was: a bag with more than a million keys is refused outright, reported through the applicable diagnostic path, and rendered with only the named keys marked, where it used to be copied in full - reading every value - synchronously inside `logger.info()`. When the normalization pass runs out of its million-container budget before reaching every named path, each container it had not reached is now withheld with the failure marker at its parent's key, where it used to be left as the caller's original - so a key hidden from enumeration beneath it could still be resolved by the renderer's property read and printed; the shortfall is still reported through the applicable diagnostic path.
- Added `lifecycleion/stringify-value` with `stringifyValue()`, `redactValue()`, shared masking types, bounded rendering, and explicit markers for cycles, unreadable values, and output/depth limits. The logger and error-rendering entry points also export the applicable `RedactFunctionResult`, `RedactMaskConfig`, `FormatErrorHandler`, and `FormatFailureKind` types, and the logger exports `REDACTION_FAILED_MARKER`. `CurlyBrackets`, logger formatting, and redaction now use this renderer, producing consistent JSON for plain containers and stable descriptions for class instances; `CurlyBrackets` and `compileTemplate()` accept `CurlyBracketsOptions.onFormatError` for failed reads/renders. A `redactFunction` replacement longer than `maxRenderLength` is now cut to the caller's cap in the structure `redactValue()` returns, not only in rendered text, so the returned leaf and `onTruncate` agree. Under `maxRenderLength: Infinity`, or a cap above one megabyte, a replacement is no longer pre-cut at the fixed constant. The cap bounds content; truncation markers sit on top of it, bounded to a few per render, which is now documented. `stringifyValue()` and `redactValue()` now run the same pre-walk normalization the logger's params already got: every container along a path named in `redactedKeys` is read once into a copy that stands in for the original, so a value that answers differently on a second read - a `Proxy` whose `get` trap returns `{}` while it is being masked and `{ password: 'secret' }` to the render that follows - is masked and printed from one snapshot instead of leaking the second answer into the output. A container on a named branch is therefore now an equal copy rather than the caller's own object, carrying exactly the keys `for...in` yielded; branches no path names are still passed through by reference, a non-plain root is still left alone, and the input is still never modified. A cut at `maxRenderLength` now steps back to a character boundary rather than only off a split surrogate pair: a cut that landed between a base letter and its combining mark, inside a joiner sequence, before a variation selector or skin-tone modifier, or between the two halves of a flag left the kept text rendering differently from how it was written, on the JSON, mask and key caps that the table renderer's grapheme-aware wrapping already avoided.
- Added `lifecycleion/to-error` with `toError()`, `describeError()`, and `isErrorValue()` for safely handling arbitrary thrown values, including cross-realm errors and values whose properties or string conversion throw. Callback, lifecycle, retry, logger, sink, and HTTP failure paths now preserve non-`Error` values on `cause` instead of losing them or throwing while attempting to report them.
- `errorToString()` now accepts shared redaction and `onFormatError` options, renders `cause` and falsy error fields, and bounds width, depth, and total output. Rendering or redaction failures produce safe, specific markers and a diagnostic callback instead of exposing the original value, silently dropping fields, or throwing; empty ASCII tables also remain renderable when their message exceeds the requested width. `serializeError()` likewise terminates on cyclic, deeply nested, cross-realm, or unreadable input, accepts `SerializeErrorOptions.onFormatError`, and exports its option/failure types. `deserializeError()` preserves a generated stack when the serialized stack is empty and treats `__proto__` as data. `serializeError()` output is now genuinely JSON-serializable: a `bigint` leaf is rendered as its digits instead of making `JSON.stringify` throw, and `function` / `symbol` leaves become the markers `<function>` / `<symbol: …>` instead of being dropped without trace - which also stops a hostile own `toJSON` from throwing inside the caller's own `JSON.stringify`. A `sensitiveFieldNames` entry spelled from the error the way the rendered table spells it - `additionalInfo.password` - is read both as written and with the prefix removed, so copying a location out of the table no longer matches nothing and prints the secret. `errorToString()` now runs the same pre-walk normalization the logger's params, `stringifyValue()` and `redactValue()` run, over `additionalInfo` and over `cause`: every container along a `sensitiveFieldNames` path is read once into a copy that stands in for the original, so a `Proxy` that answered `{}` to the masking walk and `{ password: 'secret' }` to the table render that followed is now masked and printed from one snapshot instead of printing the second answer in the clear.
- Added `reportCallbackError()`, `runCallbackSafely()`, and the overridable `EventEmitterProtected.handleEventHandlerFailure()`. Logger-owned event-handler failures use the logger's separate diagnostic channel so they cannot feed back through ordinary logging. Formatting failures emit one diagnostic per failure kind rather than once in total, so a params pass that both fails to mask and fails to render reports both.
- Lifecycle, signal, and retry failure reporting no longer silently drops late or secondary failures. `LifecycleManager` logs component, message, health-check, and lifecycle-handler failures that arrive after a timeout; `ProcessSignalManager.detach()` reports a failure to restore terminal mode; `RetryPolicy.mostCommonError` safely handles unreadable failure values; and `RetryRunner` reports genuine late or duplicate `reportResult()` calls while allowing an aborted attempt to acknowledge cancellation normally. A throw of `undefined` - or a bare `Promise.reject()` - after `reportResult('success')` or `reportResult('skip')` is reported too; only a rethrow of the error already reported is treated as the same outcome. A shutdown started by a signal now attaches a rejection handler: `stopAllComponentsInternal` has no `catch`, so a logger that threw while the shutdown was being logged rejected the floating promise on `SIGINT`/`SIGTERM` with nothing attached - fatal under Node's default - before any component was stopped. The failure is reported on the global `'error'` channel instead.
- `FileSink` and `NamedPipeSink` now render entries before queueing, retry failed writes consistently, expose aligned health and drop counters, bound shutdown with `closeTimeoutMS`, and ignore late events from replaced streams. `NamedPipeSink` keeps entries in its managed queue until writes are confirmed, honors backpressure, reconnects automatically after pipe/open failures without requiring new log traffic, and no longer keeps the process alive when a FIFO has no reader. File rotation now uses millisecond timestamps plus a collision suffix so multiple rotations cannot overwrite an archive; a rotation that still finds no free name after a hundred attempts rotates onto the last one, as before, but now reports it first as a `'setup'` failure with the archive about to be replaced as the target, where it used to overwrite in silence. A `close()` that gives up at `closeTimeoutMS` with a write still in flight now reports it as a `'close'` failure carrying `disposition: 'no_entry'`, rather than resolving indistinguishably from a shutdown that wrote everything; the entry is not counted in `droppedEntries`, since whether its bytes reached the file is unknown. `NamedPipeSink.close()` says the same thing at the same moment: a close that gives up with writes still buffered in the stream reports one `'close'` failure carrying `disposition: 'lost'` before it resolves, where the report used to come from the errored write callbacks on a later tick - or, with a reader attached but not consuming, only once that reader went away - so a shutdown handler exiting on `await close()` never heard it. The callbacks still count each entry in `droppedEntries` and do not repeat the report. `FileSink.close()` reports bytes its final flush timed out on the same way, as `'close'` / `'no_entry'`, unless its in-flight write report already named them. `FileSinkOptions.maxSizeMB` is validated like the queue options: a zero, negative, or unreadable threshold takes the 10 MB default instead of being honoured literally, where it previously made every freshly opened log file already over the limit and rotated it in an unbounded loop. Both sinks now drain what they can before giving up: `FileSink.close()` reopens its file inline as it always did, and `NamedPipeSink.close()` re-probes for a reader across a short grace window (500ms, polled every 50ms) when entries are still queued and no stream is open, so a consumer restarted alongside the writing process still receives the backlog. The probe is non-blocking, so a pipe nobody is reading returns at the end of that window rather than holding for `closeTimeoutMS`, and a sink with an empty queue closes immediately. `FileSink.flush(timeoutMS)` also bounds its initialization wait by the caller's timeout, where a hung directory previously made it never return, and no longer rotates an empty file for an entry larger than `maxSizeMB`, which left a zero-byte archive per oversized line. Both sinks resolve `closeTimeoutMS` (and `FileSink.flush(timeoutMS)`) the same way: `NaN`, a non-number, or a negative value takes the 30-second default instead of making the drain loop's deadline never fire, `Infinity` is bounded at the longest wait a timer can keep instead of firing at once, and `getHealth().isHealthy` is `false` for the whole of a `close()` rather than only after it. `FileSink.flush()` calls now run one at a time, so two flushes in flight together partition the lines written and lost between them rather than both reporting the same window; a call that waits behind another still answers within its own timeout. A write acknowledged after its stream was rotated away is no longer charged to the new file's size, where it made the fresh file rotate early. `FileSink` expects one writing process per `logDir` + `basename`: rotation reserves an archive name and then renames onto it, serialized on the sink only, so two processes sharing a log file can overwrite each other's archive. `NamedPipeSink` now checks the descriptor it actually opened with `fstat` before promoting the stream, so a path swapped for a regular file between the FIFO check and the open is refused as `not_a_pipe` and retried, where it used to take every line as an append to that file. The bound on blocked opens now holds: with two abandoned `open(2)` calls still held by the kernel, neither a `write()` nor `reconnect()` starts a third - the cap was previously read only while a stale open was pending, so the attempt after two abandons started another blocked open and `reconnect()` never checked at all. `reconnect()` answers `{ reason: 'error' }` naming the cap, the cap is reported once, and attempts resume when one of the blocked opens returns. A service or entity name can no longer carry a line break or other control character into a sink: the text sinks frame the two as `[service] [entity]` with nothing escaped, so a name built from request data could end the line and start a second entry with any prefix it liked. Each run of control characters becomes one space and the name is trimmed, on every sink, at the logger.
- `ArraySink` now stores a bounded snapshot of `redactedParams`, including named array properties, rather than retaining its mutable nested structures; copy and transformer failures are surfaced through its `onFormatError` option. Raw `params` remains the caller's object by reference.
- HTTP client cancellation methods now return the number of requests cancelled, and `CookieJar.fromJSON()` returns the number of cookies restored. User-supplied attempt, progress, observer, interceptor, and adapter hooks are contained and reported without changing an otherwise valid request outcome. `fromJSON()` reads and copies the whole payload before it clears the jar, so an unusable payload throws a `TypeError` with the jar untouched, and a caller's own cookie objects are never written into. A cookie whose `expires` cannot be read as a date is refused and left out of the count: it used to be restored as an `Invalid Date`, which `isExpired` never found expired, so one corrupt date in a persisted jar made a cookie that was sent for the life of the jar and never purged. A `null` or absent `expires` means no expiry; a number is epoch milliseconds. The same refusal covers `maxAge` and `createdAt`: a value that is not a finite number made the Max-Age arithmetic `NaN` and the cookie just as immortal, and `setCookie()` now returns `false` for an `Invalid Date` `expires` or a non-finite `maxAge` / `createdAt` on the programmatic path too. The expiry check itself fails closed, so a cookie whose expiry can no longer be read is withheld and purged rather than sent. `setCookie()` also refuses a name or value the `Cookie` header cannot carry as one `name=value` pair - a name that is empty or holds `=`, `;`, whitespace or a control character, a value holding `;` or a control character - so a value of `x; other=evil` set programmatically or restored from a persisted jar is no longer sent as two cookies, and a CR LF is no longer a header injection; the Set-Cookie parser could never produce these. The check is looser than RFC 6265's cookie-octet grammar on purpose - a value may still hold spaces, commas, quotes and backslashes, as browsers allow, because real servers send them - and refuses only what would change the header's framing. The same check runs on the way out: `getCookiesFor()` and the header withhold a stored cookie whose name or value was mutated through `getAllCookies()` into something the header cannot carry, as they already withhold one whose expiry was mutated to unreadable. `getCookiesFor()` and `getCookieFor()` now return copies rather than the stored objects, and every outbound check runs against that copy: `name`, `domain`, `path`, `hostOnly` and `secure` come from the scope `setCookie` accepted the cookie with, and each remaining field is read exactly once. A Secure cookie stored for `https://app.example.com` whose `secure` was cleared through `getAllCookies()` used to be sent in the clear, and one whose `hostOnly`, `domain` and `path` were widened the same way used to reach a sibling host and a path it was never stored for; bucketing by apex bounded that to one registrable domain but not within it. Reading a field for the check and again for the header also let the two reads disagree, so a `value` getter answering a safe string first and `x; other=evil` next put a second pair on the wire; the header is now built from the vetted copy, one pair per cookie. A field whose read throws withholds the cookie instead of throwing out of `getCookieHeaderString()`, as the expiry check already fails closed. Writing to a returned cookie no longer changes the jar — use `setCookie()` for that, and `getAllCookies()` still hands back the live objects. `clear(host, 'hostname')` and `getStoredDomains()` read that same stored scope: a cookie whose `domain` was rewritten through `getAllCookies()` used to dodge a clear by the host it was filed under, and be counted under the new name, while the header went on sending it for that host; it is now cleared and counted where it was filed. The parser now follows RFC 6265 on two attributes it read loosely: a `Path` that does not start with `/` is ignored in favour of the default-path rather than stored as written, and a `Max-Age` that is not an optional `-` and digits is ignored rather than read as a prefix, where `Max-Age=60abc` was a minute and `Max-Age=1e9` was one second; a `Max-Age` past what milliseconds can hold is capped.
- Node response streaming now treats writable callback failures as terminal `stream_write_error` outcomes and safely reports late `'error'` events instead of letting them become uncaught exceptions. Custom `WritableLike` implementations may expose `off` / `removeListener` and `errored`, and `end` callbacks may receive an error; the adapter bounds and shares its temporary late-error listener.
- Node multipart uploads now reject bodies that write fewer or more bytes than their declared `Content-Length`; early responses no longer strand their request sockets. Every Node response to a bodied request exposes `requestBodySettled?: Promise<Error | undefined>`. This advisory promise never rejects or changes response status/failure classification; it reports whether the upload completed, including failures that occur after an early response is returned. It is present on the responses the client builds with no adapter response behind them too - a cancel, a per-attempt timeout, an adapter that threw - where the field used to be omitted and `await response.requestBodySettled` therefore answered `undefined`, the documented value for an upload that went out in full. A write failure reported after the response has arrived now settles the promise itself rather than waiting for a writer that may be blocked in `Blob.stream()`. The promise is created as soon as the request has a body rather than at the first byte written, so an abort that lands before the writer starts is reported through it as well. Absence now means one thing: no adapter reported an upload outcome - no body, never dispatched, or an adapter other than `NodeAdapter`. After a followed redirect, `requestBodySettled` carries the outcome from the latest hop that had a body, so a `POST` answered early by a `302` and completed by a bodiless `GET` no longer reads as an upload that went out in full. A terminal `3xx` with no `Location` after a bodied hop carries it too. A `requestBodySettled` value whose thenable check throws - a `Proxy` from a custom adapter - is treated as absent rather than failing an otherwise successful response. A followed redirect now waits for that hop's upload to settle before the next hop is dispatched, so a `307`/`308` no longer uploads the same body twice at once; a cancel ends the wait. The wait is bounded by the request's `timeout` as a stall bound - the clock restarts on every upload-progress report, so an upload that is still moving is never cut: a custom adapter that sets `requestBodySettled` and never settles it used to hold a followed `307`/`308`, or a retry, until the caller aborted, and now fails the request as a timeout once the upload has reported no progress for that long, rather than dispatching a second upload beside the first, with the broken contract reported on the global `'error'` channel; `timeout: 0` leaves the wait unbounded as it leaves the per-attempt timer. Both timers now resolve `timeout` before using it: `NaN` or a non-number - `Number(process.env.UNSET)` - takes the default (30 seconds on the client config, the client's own resolved `timeout` for a per-request override), `Infinity` disables the timer as `0` does, and a finite value past the longest wait a timer can keep (2^31 - 1 ms) is clamped to it, on the client config and the per-request override alike. Giving up on an upload at that stall bound now also tears the attempt down, as a per-attempt timeout does: the request was already reported as timed out, but the per-attempt timer is cleared once `send()` resolves, so a `NodeAdapter` writer parked on a slow source - given a minute by its own watchdog - went on putting bytes on a socket the caller had been told was finished, and a custom adapter that ignores `requestBodySettled` had no end at all; the attempt's own abort signal is fired instead, which `NodeAdapter` answers by destroying the request and settling the outcome. The bound also counts silence from before the wait began - the clock is read on entry, and every attempt stamps it when it dispatches - where the first arm used to sleep for the whole bound however long the upload had already been quiet. Taken literally, `NaN` passed the check that arms the per-attempt timer and the check that disables the settle wait, so a bodied redirect or retry re-armed a `NaN` timer every millisecond and could never expire; `Infinity` fired the per-attempt timer after 1 ms. The client now hands every bodied attempt an upload-progress callback of its own for that purpose, whether or not the caller asked for progress. A throw between hops carries the outcome too. A retry waits the same way: a bodied `PUT` answered early by a `503` used to dispatch its next attempt after the backoff with the first attempt's body still going out, the same double-send. A retry after an attempt that _threw_ waits too, for a custom adapter that rejects `send()` while its upload is still going out and tags the error with the open outcome; `NodeAdapter` settles the outcome before it throws, so nothing changes there. A retry-phase interceptor that cancels or throws now carries the previous attempt's outcome on the result, as a cancel during the backoff already did. The field is genuinely absent where no outcome was reported - a bodiless `GET` no longer carries an own `requestBodySettled` property holding `undefined`. The stall watchdog that cuts a stalled upload short after the response reports that failure on the global `'error'` channel, as every other late upload failure already did. Every path that tears the request down after a failure - a `streamResponse` factory that threw or cancelled, a body write that failed - now does so through the same guarded destroy the abort and timeout paths use, so a `destroy()` that throws `ERR_SOCKET_CLOSED` on some runtimes can no longer skip the settle that follows and leave the attempt hanging. The watchdog now tells a writer waiting on its _source_ from one the socket has stopped accepting: a multipart `File` on a slow disk that leaves `Blob.stream()`'s read outstanding for more than five seconds after an early response used to be destroyed as stalled, and is now given a minute for the read before that verdict, so a healthy upload the server had already acked is no longer cut short over a slow read.
- `TmpDir.cleanup()` now removes an empty initialized directory in safe mode, treats an already-removed directory as successfully cleaned up, and continues to refuse non-empty directories unless unsafe cleanup is enabled. `initialize()` creates the directory exclusively and retries on `EEXIST` instead of checking first and adopting a path another process created in between. Two `initialize()` calls on one instance now share one creation: they used to race each other, each creating a leaf, with the loser's path overwritten and orphaned where a safe-mode `cleanup()` could never reach it. The constructor now throws `ErrTmpDirConfigErrorNamePart` for a `prefix` or `postfix` holding a path separator or control character: `prefix: '../escape'` created, and with `unsafeCleanup` recursively deleted, a directory outside `baseDirectory`.
- **BREAKING: `CookieJar` enforces the `Secure` attribute at store time as well as send time.** `parseSetCookieHeader()` and `processResponseHeaders()` now follow RFC 6265bis: a `Secure` cookie from a response over a non-secure scheme (anything but `https:` / `wss:`) is refused, and a non-`Secure` cookie from such a response is refused when the jar already holds a `Secure` cookie of the same name whose path covers it and whose domain domain-matches it in either direction - a `Domain=example.com` plant from `http://example.com` is refused beside a host-only Secure `session` on `app.example.com`, which it would otherwise be sent alongside - including a `Max-Age=0` or past `Expires` that would have evicted it. Store-time identity is `name` + `domain` + `path`, so a `Set-Cookie: session=evil` over `http:` used to replace the `https:` session cookie under the same key and then be sent over `https:` as the real one; the send path's Secure-on-`http:` check never saw it, because the cookie it withheld had already been overwritten. The check reads the stored scope, so a `secure` cleared through `getAllCookies()` does not open the door. The `__Secure-` and `__Host-` name prefixes are enforced, matched case-insensitively: `__Secure-` requires `Secure`; `__Host-` requires `Secure`, no `Domain` attribute and `Path=/`. `setCookie()` and `fromJSON()` have no request URL to judge and are unchanged. A `MockAdapter` flow that set `secure: true` cookies against the default `http://localhost` origin stored them and never sent them; it now refuses them at the door - use an `https://` `baseURL` for such mocks. `getCookiesFor()` now sends a `Secure` cookie over `wss:` as well as `https:`, matching what the store side accepts. `SameSite` is documented as stored but not consulted on send, which is what the jar always did.
- The HTTP client's fallback signal composition, used when `AbortSignal.any` is unavailable, no longer leaks abort listeners. It added a `{ once: true }` listener to each source signal per composition and removed it only on abort, so a caller's signal reused across `send()` calls, or the request's own cancel signal across a long redirect-plus-retry chain, kept one listener per request or attempt until the signal was aborted or collected, and the runtime eventually warned of a leak. Every listener a request adds is now released when that request ends. Runtimes with `AbortSignal.any` are unaffected.
- `FetchAdapter` now documents what `fetch()` cannot tell it: `onUploadProgress` reports `1` when the response headers arrive rather than when the body finished, and the adapter never sets `requestBodySettled`, so the client's wait before a followed `307`/`308` hop or a retry - added in this release for `NodeAdapter` - does not apply on it. A server that answers a large `POST` before consuming it gets the next hop dispatched while the runtime may still be sending the first body. Use `NodeAdapter` for uploads to early-ack endpoints on Node.
- `NodeAdapter` no longer presents the caller's TLS identity on a cross-origin redirect hop. `servername` and `mtls.cert` / `mtls.key` were applied to every `https:` request, so with `followRedirects` on, a `Location` header pointing at another origin had the adapter present the caller's client certificate to, and send the configured SNI to, a host the caller never named. The client now passes the original request's URL to the adapter as `AdapterRequest.initialURL`, and a hop whose origin (scheme, host or port) differs is sent without either; the trust settings - `ca`, `mtls.ca`, `crl` and `rejectUnauthorized` - still apply on every hop, since they say which servers to believe rather than who the caller is. Same-origin redirects and the adapter driven directly without `initialURL` are unchanged; an `initialURL` that cannot be parsed fails closed and withholds the identity. `NodeAdapter` also now removes the `'abort'` listeners it put on the request signal once the request has settled - the response delivered and the upload's outcome known, whichever is later - where `XHRAdapter` and `MockAdapter` already did; they used to stay on until the signal was aborted or collected. The listener deliberately outlives `send()` while an early-answered upload is still going out, since the attempt signal is what the client's settle deadline uses to tear that upload down.
- The logger no longer reads an unusable `redactedKeys` list twice. `handleLog` snapshots the list once and, when that snapshot is refused, used to hand the caller's own object on to `applyRedaction`, which snapshotted it again: a `Proxy` that refused the first read and answered as an empty array the second took the "nothing was asked for" exit, and the params went to every sink in the clear with nothing reported. A refused snapshot now fails closed in `handleLog` itself - empty `redactedParams` and a redaction diagnostic under `<redactedKeys>` - and the list is never read again.
- `ArraySink` gained an in-flight format-error guard, matching `FileSink` and `NamedPipeSink`, so an `onFormatError` that writes back into the sink cannot recurse through a throwing `transformer` or an unreadable param and remains guarded until an async handler settles.
- `CookieJar.setCookie()` and `fromJSON()` now enforce the `__Secure-` and `__Host-` name prefixes, which need no request URL: `__Secure-` requires `secure`, `__Host-` requires `secure`, `hostOnly` and `path: '/'`. A persisted jar tampered into a `__Host-` cookie with `hostOnly` cleared used to be restored and sent to every subdomain.
- The HTTP client's fallback signal composition releases its listeners even when attaching one throws: the caller's signal is now composed inside the request's `try`, and each composition records its release before attaching, so a signal whose second `addEventListener` throws does not leave the first listener behind.
- `isErrorValue()` and `toError()` use `Error.isError` where the runtime provides it, consulted before `instanceof`: it reads the internal slot and cannot be claimed with `Symbol.toStringTag` or with `Object.create(Error.prototype)`. A `DOMException` is accepted beside it, since Bun's `Error.isError` refuses one where Node's accepts it and every `AbortError` is one - recognised through its branded `code` accessor rather than `instanceof`, so a borrowed `DOMException.prototype` is refused too. On a runtime without `Error.isError`, `instanceof` and the brand check remain, with the bargain their documentation describes.
- The default redaction mask no longer splits a surrogate pair: it masks by grapheme cluster where the runtime has `Intl.Segmenter` and by code point otherwise, so an emoji-heavy value is masked with no lone surrogate in the output, a family emoji or a flag hides behind one mask character, and the visible prefix and suffix are counted in characters as a reader sees them. Outputs for values without astral characters are unchanged. The masking itself now lives in this library as `lifecycleion/datamask` - `maskString`, `maskDomain`, `maskEmail`, and a `datamask` object with the npm package's `string`/`domain`/`email` shape - with the same arguments and defaults as the `datamask` package it replaces, which is no longer a dependency.
- `describeContainer` refuses an object with more than `MAX_REDACTION_ENTRIES` own keys as unreadable, so a `Proxy` whose `ownKeys` invents millions of keys fails closed at the same bound an over-long array already does rather than being walked and copied past it. `namedArrayKeys` holds an array to the same bound on its named keys, counted as they are found, so a dense array past the cap is not refused for its elements and a claimed `length` hides nothing - refused as a failed read, which every caller already marks and reports - and `snapshotList` refuses a redaction list whose own keys outnumber its cap before scanning them. The key list itself is allocated by the runtime before any of these can look; what is bounded is every step after it.
- `AdapterRequest` carries `initialURL`, the resolved URL of the original request before any redirect, so an adapter can tell a hop to another origin from the request the caller addressed.
