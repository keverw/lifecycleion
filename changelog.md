## 0.0.1 (Feb 23, 2026)

- Initial package publish

## 0.0.2 (Feb 28, 2026)

- LifecycleManager error and warning logs now pass full error objects in `params.error` for consistency with other component-operation log paths

## 0.0.3 (Feb 28, 2026)

- LifecycleManager, added `attachSignalsBeforeStartup` for attaching signal handlers before startup begins while preserving the original `attachSignalsOnStart` behavior
- LifecycleManager now automatically stops components that finish starting after LifecycleManager shutdown has already begun
- LifecycleManager, startup timeouts without `onStartupAborted()` now auto-stop the component if that delayed startup later completes

## 0.0.4 (Mar 2, 2026)

- LifecycleManager, fixed `enableLoggerExitHook()` so `logger.exit()` calls made during an already-running shutdown are deferred and completed after shutdown finishes instead of being left pending

## 0.0.5 (Mar 3, 2026)

- CurlyBrackets now supports array index paths such as `{{users[0].name}}`, `{{matrix[0][2]}}`, and mixed object-array traversal with existing fallback behavior preserved
- Logger redaction now supports the same mixed object-array paths in `redactedKeys`, including paths like `users[0].password`
- CurlyBrackets and logger docs/tests now explicitly cover nested path fallback behavior, primitive intermediate values, falsey terminal values, and `Error` interpolation behavior

## 0.0.6 (Mar 3, 2026)

- CurlyBrackets now supports quoted bracket keys such as `{{user["display-name"]}}` and mixed paths like `{{users[0]["display-name"]}}`
- Logger redaction now supports matching quoted bracket-key paths such as `users[0]["password-hash"]` in `redactedKeys`
- Shared internal path parsing now rejects unsupported syntax cleanly instead of partially tokenizing invalid paths

## 0.0.7 (Mar 4, 2026)

- Logger messages now render from redacted params when `redactedKeys` are configured, so templated sensitive fields are masked in `message` as well as `redactedParams`
- CurlyBrackets and logger redaction now share an internal value-stringification helper so arrays, objects, and `Error` values are normalized consistently before rendering or redaction, non-string values are now always stringified before passing to redaction functions

## 0.0.8 (Mar 18, 2026)

- Added `lifecycleion/dev-mode`, a runtime-settable dev/production mode flag with auto-detection from CLI args (`'dev'`/`'prod'`) or `NODE_ENV`, first-wins semantics for HTML injection compatibility, and `overrideDevMode()` for test/tooling use

## 0.0.9 (Mar 19, 2026)

- LifecycleManager error and warning log messages now include `error.message` inline (e.g., `"Component failed to start: Connection refused"`) so failure reasons are visible in plain log output without a custom structured sink

## 0.0.10 (Apr 7, 2026)

- Added the new adapter-based HTTP client foundation in `lifecycleion/http-client`, including the shared `HTTPAdapter` contract, fluent request builder, retries, redirect handling, cancellation, interceptors, response/error observers, request tracking, and the default `FetchAdapter`
- Added `MockAdapter` plus server-side cookie jar support and shared HTTP client request/response utilities
- Added `lifecycleion/http-client-node` with a Node adapter for server-side HTTP requests, streaming downloads, multipart uploads, Unix sockets, and TLS/mTLS options
- Added `lifecycleion/http-client-xhr` with an XHR adapter for environments that expose `XMLHttpRequest`, including real per-chunk upload/download progress, redirect detection, and Playwright-based browser integration tests
- Added `lifecycleion/domain-utils`, hardened helpers for normalizing and matching domains and origins, including IDNA/TR46 normalization, IPv6 literal support with zone-ID rejection, wildcard CORS matching with PSL/IP-tail guards, credentials-safe origin matching, and re-exports of `tldts` helpers (`getDomain`, `getSubdomain`) so consumers don't need a separate install
- Added `lifecycleion/lru-cache`, a TTL-aware LRU cache with configurable max entries, optional byte-size limit, per-entry TTL overrides, automatic expiration, and pluggable size calculators
- Fixed test-only TypeScript assertion issues reported in some unit test cases. No runtime or API behavior changed for them
- Added `lint` and `type-check` to `prepublishOnly` to strengthen the future release process

## 0.0.11 (Apr 9, 2026)

## 0.0.13 (Apr 19, 2026)

- LifecycleManager now supports an opt-in `repeatedShutdownRequestPolicy` with a required `onForceShutdown()` hook so applications can decide how to escalate repeated shutdown requests received during an already-running shutdown
- Repeated shutdown escalation now tracks request count and timing window across real signals, keyboard-triggered shutdown requests, and programmatic `triggerShutdown()` calls that flow through the same signal callback path
- The default repeated shutdown escalation window is now 2 seconds with a default force threshold of 3 requests
- Repeated shutdown escalation now supports optional `armedAfterFailureMS` overrides so failed or stalled shutdown attempts can stay force-armed longer than the default derived post-failure window
- LifecycleManager shutdown logs now distinguish between the normal first shutdown request, repeated shutdown requests still being tracked, and repeated-request escalation when the force threshold is reached

## 0.0.14 (Apr 28, 2026)

- LifecycleManager now detects when a stalled component's original `stop()` or `onShutdownForce()` promise eventually resolves and automatically transitions it from `stalled` to `stopped`, clearing the stall record and emitting a `component:stalled-resolved` event. A per-component stop generation token prevents a late-resolving promise from affecting a component that has already been restarted since stalling.
- Docs now document the `stop()` promise-deduplication pattern as the recommended approach when `onShutdownForce()` should join an already-running `stop()`, and the `onGracefulStopTimeout()` pattern as an alternative for unblocking `stop()` without a concurrent second close.
- BaseComponent now exposes a protected `reportUnexpectedStop(error?)` method. Call it when the component detects an internal failure (crashed server, lost connection, exited worker) to let the manager mark it stopped, store the error as `lastError`, emit `component:unexpected-stop`, and then emit the canonical `component:stopped` event for the resulting stopped state. A subsequent `stopAllComponents()` call skips the already-stopped component and proceeds normally. The call is a no-op once the manager begins stopping or unregistering the component, and the handler is automatically re-armed after each successful restart.
- If `reportUnexpectedStop()` fires during `startAllComponents()`, required components now fail the bulk startup with `code: 'component_unexpected_stop'` and trigger rollback of later-started components, while optional components are recorded in `failedOptionalComponents`.
- Added `component:unexpected-stop` event (payload: `{ name, error? }`) emitted when a running component calls `reportUnexpectedStop()`, immediately before the follow-up `component:stopped` event.
- BaseComponent now exposes a protected `getSelfStatus()` method that returns the component's own `ComponentStatus` from the manager without requiring the caller to pass the component name.

## 0.0.20 (Aug 21, 2026)

- **Added `crl` to `NodeAdapterConfig`:** certificate revocation lists, so a server certificate whose serial has been revoked is rejected even though its chain and hostname still verify. Revocation failures resolve as status `495` like other TLS certificate errors. The value is read on every request, so refreshing a revocation set does not require rebuilding the adapter, and no connection-pool handling is needed. `crl` is part of Node's pool key, so changing it partitions the pool and a socket established under the old CRL is never reused under the new one.
- **Concatenated CRL bundles are split for you.** Node reads only the **first** CRL of a concatenated PEM string and silently ignores the rest, unlike `ca`, which reads every certificate in a bundle. The bundle is the standard interchange format. Apache documents `SSLCARevocationFile` as "the concatenation of the various PEM-encoded CRL files," nginx and HAProxy agree, and `openssl verify -CRLfile` reads a whole bundle. This is Node diverging from the library it links rather than an OpenSSL limitation. The adapter splits bundles on the RFC 7468 boundary, including strings nested inside an array, so `[bundleOfTwo, oneMore]` contributes three CRLs. This includes **Buffers**: `fs.readFileSync('bundle.pem')` without an encoding returns one and its contents are PEM like any other bundle, so passing Buffers straight through would leave the most ordinary way of loading a file silently truncated. In testing, a bundle whose second CRL revoked the server's certificate accepted the connection as a Buffer and rejected it once split. DER Buffers pass through untouched, since DER encodes exactly one CRL. Note also that OpenSSL uses the **first** CRL it has for a given issuer rather than the newest, so a bundle must not contain two CRLs for the same issuer. Without this the failure is `UNABLE_TO_GET_CRL`, which reads as "no CRL supplied" rather than "your bundle was truncated." A bundle whose first entry happens to cover the root in use appears to work until the roster or export order changes.
- **Revocation failures are now classified as TLS certificate errors**, so they resolve as status `495` rather than a generic transport failure. This covers `CERT_REVOKED` plus every CRL verification code OpenSSL exposes, matched by property rather than by name, since the message-text fallback catches almost none of them (`CRL has expired` and "format error in CRL's lastUpdate field" contain none of the words it looks for).
- **Only PEM blocks and whitespace are accepted in a `crl` string.** A truncated or corrupted CRL, a damaged delimiter, or decoded `openssl ... -text` output is refused with an error rather than silently dropped. Splitting keeps only complete blocks, so a cut-short entry would disappear while the intact ones stayed in force, leaving the caller enforcing a set they never supplied, with no error. Passing the string through unsplit is no better, since Node reads its first CRL and ignores the rest. The rule is exact rather than heuristic because a parser cannot distinguish a half-written CRL from a line of commentary, so admitting the second necessarily admits the first. Strip annotations before passing a bundle.
- **Bun compatibility note:** Bun ignored `crl` entirely through 1.3.14. It accepted a revoked certificate with no error, no warning, and no throw on a malformed CRL, meaning the option was never read. The same was true of `minVersion`, `maxVersion`, and `secureProtocol`. All are fixed in Bun 1.4.0, which matches Node 25.9.0 on every case tested. **Require Bun >= 1.4.0 if you depend on these options for security.** The enforcement tests probe the runtime and skip where `crl` is unsupported rather than passing for the wrong reason. The bundle-splitting tests run everywhere.
- Two caveats worth reading before enabling `crl`, both fail-closed and therefore safe, but both able to refuse healthy connections: every certificate in the chain needs a covering CRL (`X509_V_FLAG_CRL_CHECK_ALL`, so a partial CRL set refuses every root it does not cover, even unrevoked ones), and CRLs expire (`CRL_HAS_EXPIRED` blocks good certificates past `nextUpdate`). See `docs/http-client.md`.
- Adapter contract types (`HTTPAdapter`, `AdapterRequest`, `AdapterResponse`, `AdapterType`, `AdapterProgressEvent`, `HTTPMethod`) are re-exported from the adapter subpaths, so code driving an adapter directly no longer has to import types from `lifecycleion/http-client`. Type-only, so nothing is added to the runtime bundle. The node subpath also re-exports the response-streaming types.
- Pinned `@types/bun` to 1.3.14. `@types/bun` 1.4.0 declares `off`/`removeListener` overloads for its `memoryPressure` event directly on `NodeJS.Process`, which shadows the generic `EventEmitter` overloads that `@types/node` relies on being inherited, breaking `process.off('SIGINT', ...)` and every other signal detach at the type level. Types only, so no runtime or security impact.
- Applied `brace-expansion` and `js-yaml` overrides to clear two high-severity advisories reaching the tree through ESLint's dev-only dependencies.
- Dependency refresh within existing ranges: `find-my-way` 9.8.0, `tldts` 7.4.10, `uuid` 14.0.2, `@playwright/test` 1.62.1, and the `typescript-eslint` packages 8.67.0.

## 0.0.21 (Aug 25, 2026)

- **Fixed callback error reporting on Node.js.** `safeHandleCallback()` and `safeHandleCallbackAndWait()` report failures by dispatching an `ErrorEvent` of type `'reportError'` through `globalThis.dispatchEvent()`. Node 25 added a global `ErrorEvent` constructor but did **not** make `globalThis` an `EventTarget`, so `dispatchEvent`, `addEventListener`, and `removeEventListener` are all `undefined` there. This meant callback errors were caught and then silently dropped on Node. The existing tests missed this because they run under Bun, which provides the browser-style global event methods. The same gap made `logger.registerReportErrorListener()` return `'not_available'` on Node.
- **Added [global-event-target](./docs/global-event-target.md)** (`lifecycleion/global-event-target`), a conservative polyfill that supplies the missing global event methods, backed by a single shared `EventTarget`. It installs only when all three methods are absent, so native and user-installed implementations are never overwritten. It is idempotent, keeping the backing target and install flag in one shared object on `globalThis` (`__lifecycleion_global_event_target__`, the same style as `dev-mode` and `process-signal-manager`) so repeated initialization and multiple copies of the package share it. Installed properties are non-enumerable and bound to the backing target. A partial or foreign surface (some methods present, others missing or present but not callable, such as `globalThis.dispatchEvent = null`) is deliberately left alone rather than mixing methods from unrelated targets or clobbering a value the application put there. A member explicitly assigned `undefined` counts as absent, since that is how a global gets cleared. Reporting is skipped there, and the helpers still return their normal results. Because installation runs during module initialization, it never throws. A non-extensible global object (`Object.freeze(globalThis)`) or a non-configurable property returns `'blocked'`, and every global it reads, including the three methods and the `EventTarget` constructor, goes through one guarded read, since reading a global runs its getter and a getter can throw. A throwing accessor is reported as `'partial'` (or `'unsupported'` for the constructor) rather than crashing the import. The reporting path is likewise throw-proof. It can drop a report, but never raise an error while reporting one rather than breaking the import of `safe-handle-callback` and everything downstream of it. A definition rejected despite that preflight is rolled back so nothing is left half-installed. Importing `lifecycleion/safe-handle-callback` or `lifecycleion/logger` installs it, so for most users this is transparent. Browser and Bun behavior is unchanged, and `ErrorEvent` is never polyfilled. Node 25+ is the supported floor and provides it natively.
- **Added Node-runtime tests.** A Bun-only suite cannot catch this class of bug, since Bun has the globals natively. The new suite bundles fixtures with `Bun.build({ target: 'node' })` and runs them under the real `node` binary, asserting that a plain `globalThis.addEventListener('reportError', ...)` receives both synchronous throws and rejected async callbacks, that the reported `ErrorEvent` carries the wrapped callback name and original error details, that nothing becomes an uncaught exception or unhandled rejection, and that repeat installation and pre-existing global implementations are handled as documented. It also pins down that Node itself has `ErrorEvent` but no global event methods, so the assumption behind the fix fails loudly if it ever changes.
- `sideEffects` is now a list rather than `false`: the installation happens at module initialization, and a blanket `sideEffects: false` would let a bundler drop a bare `import 'lifecycleion/safe-handle-callback'` despite the documented guarantee that importing it installs. Only the `safe-handle-callback` and `logger` entry files are listed, so the rest of the package stays fully tree-shakeable, and the reporting path re-runs the install itself so a swallowed error can never be a packaging artifact.
- Documentation now describes `'reportError'` as Lifecycleion's reporting convention built from web-standard primitives (`ErrorEvent` plus the global `EventTarget` methods), rather than implying the event type itself is a web-standard API.
- **Fixed unsafe retries on `FetchAdapter` when a response body was truncated.** A body that failed after headers arrived (peer reset mid-body, premature close, short read against `Content-Length`) rejected out of `send()` because the body read sat outside the adapter's `try`/`catch`. That landed on `HTTPClient`'s generic network-error path as `status: 0`, which is in `RETRYABLE_STATUS_CODES`, so the request was retried up to the policy limit. Headers arriving means the server received and processed the request, so replaying a non-idempotent write could apply it twice. `NodeAdapter` already resolved these as `isStreamError` and never retried them, so **the same truncation was retried on `fetch` and not on Node**. This was a correctness difference rather than a performance one, and one that would not show up for anyone testing on Node and shipping on Bun or in a browser. Note that the client's retry guard (`!adapterResponse.isStreamError`) was correct throughout and never fired: it only runs on a _resolved_ adapter response, and a throw out of `send()` never becomes one. `FetchAdapter` now resolves with `isStreamError: true`, `streamErrorCode: 'stream_response_error'`, the real HTTP status, and the underlying `errorCause`. A caller's `AbortSignal` still re-throws so cancellations stay classified as cancellations rather than network faults. It now carries the response metadata out with it, since the adapter sees one composite signal and cannot tell a caller cancel from a per-attempt timeout. Without that, a timeout firing mid-body-read lost the real status and left an otherwise terminal post-header failure eligible for retry, the same divergence in a second guise. `NodeAdapter` already tagged its response-stream aborts this way. The client sorts the two apart. (Carrying the metadata out was necessary but not sufficient. See the entry below on which rejections the client would accept it from.)
- **Added `MockResponse.streamError`** so the `isStreamError` branch can be tested without a real socket. Pass `true` for the default `'stream_response_error'`, or name the code explicitly. The mock reports the `status`, headers, and cookies you set, matching a real post-header failure, where the status is known and only the body is lost, while forcing `body` to `null` regardless of what the handler returned.
- **Documented which `isStreamError` guarantees are Node-only.** `NodeAdapter` covers streamed and buffered bodies and distinguishes `stream_write_error` from `stream_response_error`. `FetchAdapter` covers buffered bodies in both server runtimes and browsers. Headers have arrived by then, so the status is readable either way, but it always reports `stream_response_error`, since `fetch` buffers the body and exposes no per-chunk delivery to tell a local write failure from an upstream one. `XHRAdapter` does not report the flag at all, and that one is a spec-level limitation rather than a browser inconsistency: setting `XMLHttpRequest`'s error flag sets the response to a network error, which forces `status` to `0`, leaving no evidence that headers ever arrived. A mid-body truncation is therefore indistinguishable from a connection refused there, stays an ordinary transport failure. For an idempotent method that is still eligible for retry, so a truncated `GET` is silently re-fetched rather than reported with its real status. A non-idempotent write is spared only because `XHRAdapter` never supplies `wasDefinitelyNotSent` and the default rule blocks a replay for want of proof, not because the truncation was recognized, so enabling `retryNonIdempotentMethods` removes that protection. Browser code making replay decisions on non-idempotent writes should prefer `FetchAdapter`.
- **`NodeAdapter` now decides transport-failure replay safety from the error code** rather than from a body-byte count. The old test was `uploadedBodyBytes === 0`, which reports `0` for a request with no body, so an empty-body `POST` whose headers reached the server and then lost the connection was marked safe to replay. The counter also tracks bytes handed to the stream rather than bytes on the wire, so it could be non-zero for a connection that was never established. Only codes proving no connection happened (`ECONNREFUSED`, `ENOTFOUND`, and similar) are now treated as replayable. `ECONNRESET`, `EPIPE`, `ETIMEDOUT`, and anything unrecognized fall on the side of possible delivery. `EHOSTUNREACH` and `ENETUNREACH` are excluded despite reading like connect-time failures, because an ICMP unreachable arriving for an established connection surfaces on that connection with the same code. Seeing one does not rule out a request that was already written and received. That verdict is carried on the new `wasDefinitelyNotSent` rather than on `isRetryable`, which blocks retries for every method and is reserved for the case below. The error code is also the only signal that behaves identically on Node and Bun. `socket.bytesWritten` is not implemented under Bun and `socket.connecting` reports the wrong value there, so either would have silently claimed "nothing sent" for a request the server had already received.
- **`isRetryable: false` is now reserved for failures no method should retry.** It blocks a retry for every method, but `NodeAdapter` was setting it once a request body had started going out, including for a mid-upload socket error and both body-write failure paths. That stopped retrying an idempotent `PUT` or `DELETE` after an ordinary transport blip, the case a retry is most likely to fix, and it overrode `retryNonIdempotentMethods` where the caller had stated a replay is safe. Whether a partly-sent request may be replayed is the method question below, and withholding `wasDefinitelyNotSent` already answers it, so those three vetoes are gone. The remaining use is a rejected TLS certificate, where another attempt genuinely cannot succeed.
- **`FetchAdapter` now classifies TLS certificate failures as `495`**, matching `NodeAdapter`, instead of letting them arrive as `status: 0`, which is in `RETRYABLE_STATUS_CODES`, so a bad certificate was retried to the policy limit, failing identically each time. This is a server-runtime classification: Bun exposes the OpenSSL code on the rejected error and Node hangs it off `cause`, both of which are now recognized, while a browser reports an opaque `TypeError` with neither and such a failure keeps the ordinary transport-error shape. `XHRAdapter` cannot classify these at all.
- **Added `AttemptEndEvent.retrySuppressedReason`** so a suppressed retry explains itself. `willRetry: false` could not distinguish a policy declining from a safety rule stepping in, which made the non-idempotent default below discoverable only by reading this changelog. When the status alone would have allowed a retry, the event now names what stopped it: `adapter_veto` (the adapter reported `isRetryable: false`), `stream_error` (the body failed after headers arrived), or `non_idempotent_method`. Absent when a retry was scheduled, when no policy is configured, when the policy has no attempts left, or when the status was never retryable. In those cases nothing was suppressed.
- **Added `MockResponse.transportError`** so the replay rules are testable without a socket. `MockAdapter` could simulate cookies, redirects, delays, and (as of this release) stream errors, but had no way to produce a failure with no response at all, so none of the rules below could be exercised against it. It delivers nothing from the handler's response (no body, headers, cookies, or terminal progress) and accepts the signals a real adapter would attach: `wasDefinitelyNotSent` for proven non-delivery, `isRetryable: false` for a failure no method should retry, and a diagnostic `status` such as `495`.
- **Retries no longer replay `POST` and `PATCH` by default.** The retry decision never consulted the request method, so with a retry policy active a `POST` was retried on a `500`, even though the handler definitely ran and may have committed, making it a stronger case against replay than the transport failures above. `HTTPClient` now declines to retry the methods RFC 9110 does not define as idempotent: never after a real HTTP response, never after a thrown adapter error or per-attempt timeout, and after a transport failure only when the adapter reports the new `AdapterResponse.wasDefinitelyNotSent: true` (proof that no request bytes reached the server). The transport condition is part of the rule rather than a shortcut: on a real response delivery is already settled the other way. `isRetryable` deliberately does **not** grant this exception. It is a retry hint whose contract only ever defined `false`, so a custom adapter may set it `true` for a failure it considers transient without knowing whether the request was delivered, and reading that as proof would replay a write after an ambiguous failure. `PUT` and `DELETE` are unaffected. Both mutate, but both are idempotent by definition, so replay is safe. Set `retryNonIdempotentMethods: true` on the client config, or `.retryNonIdempotentMethods(true)` per request, to restore the old behavior for writes guarded by an idempotency key. This only ever removes retries. It never adds one, and does nothing unless a retry policy is active.
- **Set-Cookie now survives a post-header stream abort.** Cookies were stored only when an adapter resolved a response. As a result, `Set-Cookie` was dropped when the body was cut short by a timeout, a stream abort, or the caller cancelling mid-read. The identical response arriving intact stored it, as did a buffered stream failure that resolved rather than threw. Headers had arrived in every one of those cases, which is the whole basis for the existing behaviour of applying cookies from error responses to follow-up requests, as browsers and curl do.
- **The response-stream abort marker, not the error's name, is what routes a post-header abort.** The client's branch for a body that failed after headers arrived required both the adapter's marker and an error named `AbortError`. But an adapter tags that throw whenever the attempt signal aborted mid-body, and the rejection it hands back is whatever the runtime produced. Undici surfaces a timeout during the body read as `TypeError: terminated`, not as an `AbortError`. The tag arrived on an error the gate then refused. With the cancel signal untouched, because a per-attempt timeout aborts only the timeout controller, the throw fell past the cancellation check too and landed on the generic network path: the tagged status and headers discarded, `status: 0` reported, and since `0` is retryable, a `503` whose body was cut short replayed against a server that had already answered. An idempotent method is not spared, the method rule below covering only `POST` and `PATCH`. The marker is now the whole gate. This is what makes the previous entry's fix effective rather than merely present.
- **A marker is trusted only when it reads exactly `true`.** Both marker checks tested for the property rather than its value, so an ordinary adapter error carrying one as `false` reached a branch meant for a tag an adapter deliberately set. For the response-stream marker that branch is terminal _and_ writes to the cookie jar, so an error that also carried stale `streamAbortStatus`/`streamAbortHeaders` fields had that response's `Set-Cookie` filed under the current request's URL. For the XHR browser-timeout marker, a deliberate cancel reported `isTimeout`. Every adapter writes the literal `true`, so nothing is lost by asking for it. Both reads are also guarded now: the value is whatever a runtime, a library, or a caller's abort reason produced, and a throwing getter would otherwise escape the classifier that exists to normalize the failure.
- **Fixed a DNS failure reading as a permanent certificate failure.** The TLS classifier falls back to matching certificate wording in the error message, and that message is one the runtime built. For a DNS or connect failure, it has the hostname interpolated into it. `getaddrinfo EAI_AGAIN certificates.internal.corp` matches on the host's name alone, so any deployment calling a `certificates.*` or `certificate-authority.*` host had every DNS blip resolve as `495` with `isRetryable: false`. This veto holds for every method, including an idempotent `GET`, turning the most transient failure there is into a permanent one. Retrying a genuine certificate failure wastes milliseconds. Refusing to retry a DNS blip defeats the point of having retries. A code that names a transport failure now settles the question and the message is not consulted. **This predates the changes above:** `NodeAdapter` has used this classifier all along, so the false positive was live on Node, and `FetchAdapter` adopting it only widened the surface. Note the fix could not simply be "skip the message whenever the error has a code", because OpenSSL exposes far more verification failures than the classifier names, and `CERT_UNTRUSTED`, `CERT_REJECTED`, `HOSTNAME_MISMATCH`, `UNABLE_TO_GET_ISSUER_CERT` and `INVALID_CA` match no code rule at all, so the message is the only thing that catches them. Nothing covered those nine, which is how a change breaking every one of them could leave the suite green. They are covered now.
- `CRL` is matched as an underscore-delimited token rather than as a substring. This keeps the argument for asking by property rather than by list. Future OpenSSL CRL codes still match, including the plural `NO_CRLS_INCLUDED`, while excluding `CRLF`, the one word that shares the prefix by accident and the one a header- or framing-error code would plausibly be named for. Such a failure is a connection problem, the opposite of a permanent certificate verdict.
- Clarified in the `isStreamError` doc comment and in [http-client](./docs/http-client.md) that for replay decisions a stream error groups with a **real response**, not with a transport failure. Both leave you without a usable body, but a `status: 0` transport failure may never have reached the server, while a stream error means it arrived and may have committed, just as a 500 tells you. The resemblance is superficial and inverts the decision.
- **A truncated `3xx` keeps its redirect target.** `FetchAdapter`'s post-header failure path reported the real status but not `wasRedirectDetected` or `detectedRedirectURL`, which the intact path resolves for every response. So with `followRedirects: false`, a `302` carrying a `Location` header whose body was then cut short arrived with nothing to say where it pointed, while the identical intact response reported the resolved absolute URL. The headers arrived before the body failed, so the target is known just as well either way.
- **A truncated `3xx` is no longer followed.** `HTTPClient` checked the redirect status before the failure state, so with `followRedirects: true` a `302` whose body failed after headers arrived was followed like any other. The `Location` header had survived, which is exactly what made this quiet: the hop continued, a healthy destination answered `200`, and the attempt that failed was no longer the one being reported. This left a documented terminal failure resolving as a success. A per-attempt timeout striking mid-body is the sharpest form of it, since `wasTimeout` rides on the attempt result and the next hop overwrites it with its own. Redirect following is now gated on `!isStreamError`, so the response reports the real `3xx` status with `isStreamError`, the timeout if there was one, and still `wasRedirectDetected` / `detectedRedirectURL`, so the caller loses none of what the previous entry restored. The `followRedirects: false` branch is deliberately not gated: it follows nothing, and reporting a truncated `3xx` exactly as it reports an intact one is what that branch is for.
- **A truncated `3xx` reported by a _thrown_ abort keeps its redirect target too.** Both adapters resolve `wasRedirectDetected` / `detectedRedirectURL` on a post-header failure they hand back as a response, but when the body fails via a tagged throw the client rebuilds the response itself from `streamAbortStatus` / `streamAbortHeaders`, and those two fields were simply never set on it. That was invisible while such a hop was still followed. Making a stream error terminal for a `3xx` is what exposed it, since nothing downstream resolves the target any more. A per-attempt timeout striking mid-body, the sharpest case for the entry above, therefore reported `wasRedirectDetected: false` on a `302` whose `Location` header had arrived intact, and with `followRedirects: false` the same response came out the other way round: that branch hardcodes the flag, so it claimed a redirect and had no destination to name. The client now resolves both from the tagged headers, exactly as `FetchAdapter` does on the path where it resolves rather than throws.
- **A rejected install no longer destroys the shared state it replaced.** Rollback exists so a failed install leaves the environment exactly as found. That held for the three methods, where deleting them is the undo, but not for the shared-state key: once an unusable state object could be _replaced_ rather than reused, rolling back deleted it outright, so a failed install destroyed another copy's object as a side effect. The original descriptor is now put back in place and never deleted first, since whatever rejected the definition may have sealed the global object and re-adding a key to a non-extensible object throws. Reaching this at all takes the one piece of caller-controlled code that runs between the preflight and the first definition, the `EventTarget` constructor itself. A fixture uses exactly that to seal the global mid-install, and asserts the original object comes back by identity.
- **A backing target whose `bind` returns a non-function no longer installs.** `bind` is an ordinary property on a method, so a target reachable through the shared global can replace it with something that returns a non-function without ever throwing, while every cheaper check passes, since the three members still read as functions. Guarding only a throwing `bind` put that value straight onto `globalThis` and reported `'installed'`: `addEventListener` became a number, `isGlobalEventTargetPolyfilled()` claimed the polyfill was in place, and every `reportError` dispatch threw `TypeError`. That is strictly worse than not installing, because these methods start out absent. What `bind` returns is now checked, and a target that fails it is passed over for a fresh one. A related gap in the result codes is closed at the same time: an `EventTarget` constructor that is callable but cannot produce a usable instance. It may throw on construction or return something that cannot service the three methods. The constructor now reports `'unsupported'` because nothing was ever offered to the global object, so `'blocked'` would have been the wrong story, and nothing is left behind.
- **The backing event target is re-validated at the moment the globals are bound to it.** `installGlobalEventTarget` validated the shared state's `target` when it read the state, then bound `globalThis.addEventListener` and friends to a second, unguarded read of the same field, the one read in the module that actually matters. The field belongs to an object anything on the global object can reach, so a getter returning a real `EventTarget` when probed and something else afterwards would have bound the three methods to a value that never passed a check, and a getter throwing on that second read turned a perfectly viable install into `'blocked'` with all three methods rolled back, leaving Node with no event methods at all. The bind now takes the target and the three methods off it in one validated pass. Binding a method read later would have been the same gap moved one level in, since a method on somebody else's object is no more ours to trust than the field holding it. A target that no longer vouches for itself is treated as absent: installation proceeds with a fresh one, which orphans nothing, since a target that cannot service the three methods never had listeners registered through this module.
- Corrected the `retrySuppressedReason` documentation for `adapter_veto`, which said no built-in adapter produces it. `NodeAdapter` and `FetchAdapter` do not, for the reason given, but `MockAdapter` does. `transportError: { isRetryable: false }` leaves the default retryable `status: 0` in place, so the veto is what stops the retry. That is the point of the example the same page already gives.

## 0.0.22 (Unreleased)

- **BREAKING: errors are now reported on the standard global `'error'` event instead of a custom `'reportError'` event type.** Everything Lifecycleion catches on your behalf — `safe-handle-callback`, `EventEmitter` handlers, `LRUCache`'s `onChange`, `SingleEventObserver` subscribers, `LifecycleManager` event handlers, `PromiseProtectedResolver`'s `beforeResolveOrReject`, `ProcessSignalManager` — dispatched an `ErrorEvent` whose **type** was the string `'reportError'`. That looked like the web platform's `reportError`, but it was Lifecycleion's own convention and nothing in the platform emits or listens for it, so reports were invisible to an ordinary `addEventListener('error', ...)` and a consumer had to know the private string. The type is now the standard `'error'`. **Any code doing `globalThis.addEventListener('reportError', ...)` must change to `'error'`.** `logger.registerReportErrorListener()` has been switched over and keeps its name; it no longer listens for the old type, so there is no deprecation window.
- **Reporting now falls back in three rungs, dispatch first.** Rung 1 dispatches `new ErrorEvent('error', { error, message, cancelable: true })` when the global object has `dispatchEvent` and `ErrorEvent`; a listener calling `preventDefault()` claims the report and nothing further is written. Rung 2 calls `globalThis.reportError(error)` when dispatch is unavailable. Rung 3 writes to `console.error`, which is also where an uncancelled dispatch lands, so an application with no listener registered never loses an error silently. The order is deliberately the reverse of what the WHATWG "report an exception" algorithm suggests: on Bun 1.3.14 `globalThis.reportError()` exists but notifies no `addEventListener('error', ...)` listener at all (measured: zero listener calls) and sets the process exit code to `1` as a side effect, so a `reportError()`-first order would make every report invisible to listeners on Bun and let a failed callback turn a clean run into a failing one. It also never falls from a dispatch on to `reportError()`: in browsers that call dispatches a second `'error'` event to the listeners that already saw the first, reporting one failure twice. `cancelable: true` is load-bearing rather than decorative — `EventInit.cancelable` defaults to `false`, and `preventDefault()` on an uncancelable event is a silent no-op that leaves `dispatchEvent()` returning `true` no matter what a listener does, which would make the console fall-through unsuppressable. A `dispatchEvent()` that throws is treated as an uncancelled dispatch rather than as an unavailable one, since the event was still handed over and listeners may have run; only a failure to construct the event means nothing was dispatched. A throwing listener does not reach that path — per spec a listener's exception does not propagate back into `dispatchEvent`, and browsers, Bun and Node all honour it — but an exotic or hostile `dispatchEvent` that rejects the event outright does. Note that "does not propagate" is not "is harmless": a browser reports the exception and carries on, but outside one the runtime treats it as uncaught, and on Bun 1.3.14 and Node 25.9.0 a listener that throws exits the process with code `1` while `dispatchEvent()` still returns normally to the caller. Anything registered on this channel should therefore catch its own failures, including whatever formatting it does with the error; the logger's listener now does. The pattern is written up in [safe-handle-callback](./docs/safe-handle-callback.md#the-reporting-pattern) for use in your own code that catches errors it must not rethrow.
- **`logger.registerReportErrorListener()` takes an options object and cancels the event by default.** The signature is now `registerReportErrorListener(prefix?, options?)`, where `options.preventDefault` defaults to `true`. The listener already logs the error through `errorObject()` to every sink, so cancelling stops `safe-handle-callback` from also writing it to the console and suppresses the browser's own console line, rather than recording one failure twice. Pass `{ preventDefault: false }` to log to the sinks and leave the error for the console as well. Note the widened scope that comes with the standard channel: in browsers this listener now also receives genuine uncaught script errors, which can arrive with no `error` object — the event's `message` is logged instead of `undefined` — and which the default `preventDefault: true` therefore also silences in the console. Resource-load failures are not included by default, since those `error` events fire on the element and do not bubble to a listener registered without capture; pass `captureResourceErrors: true` to register with capture and take them too. Those arrive as a plain `Event` with no `error` and usually no `message`, so they are described from the failing element instead — `Failed to load IMG: /logo.png` — and tagged `'resource'` so a custom sink can route or drop them, since every broken asset on the page becomes a log entry. Verified in real headless Chromium rather than asserted: a Playwright suite covers the default ignoring a failed image, the flag logging and tagging it, an ordinary callback report staying untagged, and `unregisterReportErrorListener()` actually detaching a capturing listener (`removeEventListener` only detaches one registered with the same capture flag). `close()` now unregisters the listener: a closed logger's `handleLog` is a no-op, so one left registered would cancel reports it could not record, leaving them to reach neither a sink nor the console. Registering _after_ `close()` returns the new `'closed'` result and attaches nothing, since `_closed` is never cleared — such a listener could never log or claim anything and would simply sit on `globalThis` holding the logger and its sinks alive.
- **A logger event handler that fails no longer feeds itself.** Logging emits a `'logger'` event, `EventEmitter` reported a failing handler on the same channel `registerReportErrorListener()` listens to, and that report was logged — which emits again. A handler that throws synchronously recursed until the stack gave out: one `logger.info()` call produced 101 handler invocations and 51 log entries before a test guard stopped it. A handler that fails _asynchronously_ was worse in a quieter way: each rejection is reported in a later microtask, so it is not re-entrancy at all but a steady-state cycle that never terminates and never blows the stack. `Logger` now reports failures of its own `'logger'` handlers to the new `onEventHandlerError` option — or to `console.error` when none is given, and also when that callback itself throws — instead of to the global `'error'` channel, which removes the edge that closes the loop for both. Both cases now settle at a single handler call. Failures from handlers on _other_ Lifecycleion emitters are unchanged and still reach the logger's sinks. It gets its own option rather than reusing `onSinkError`, which is handed the sink that failed: no sink is involved here, so there would be nothing honest to pass. **This predates the channel change above** and reproduces identically on 0.0.21 with the old `'reportError'` event type; it needed both a registered listener and a reliably failing `'logger'` handler, so it was never on the default path.
- **`EventEmitterProtected.emit` reports handler failures through a new overridable `handleEventHandlerFailure(event, error)`.** The default is exactly the previous behaviour — report on the standard `'error'` channel, as `safeHandleCallback` does — so nothing changes for existing emitters. It exists because that channel is not safe for an emitter whose own events are logged, which is the loop above; `Logger` overrides it. `safe-handle-callback` now exports `reportCallbackError(callbackName, error)` so an override can report the same way the default does, or deliberately not.
- **A callback that throws a non-`Error` value no longer crashes the call that invoked it.** `throw` and promise rejection both accept any value, and the failure paths cast rather than checked: `Logger`'s handler-failure reporting and `handleSinkError` each read `.message` straight off the caught value, so a `'logger'` handler or a sink `write()` doing `throw null` raised a `TypeError` that escaped through `emit()` and out of `logger.info()` itself — the log call failed, not just its error report. Both now normalize first, and `handleEventHandlerFailure`, `reportCallbackError`, and `handleSinkError` take `unknown` instead of `Error` so the casts that hid this are gone. Normalizing also makes `onSinkError`'s declared `Error` parameter honest: a sink that throws a non-`Error` now yields a real `Error` reading `Non-error value thrown: null`, with the value thrown kept as its `cause`, where before the raw value was passed through against the type. The normalizer guards `instanceof` as well as `String()`, since both run code the library does not own — a revoked `Proxy` throws on the prototype-chain walk alone. `EventEmitterProtected`'s own default was never affected; it routes through `errorToString`, which already accepted `unknown`.

- **The reporting path can no longer throw a second error out of the first.** Rendering a thrown value runs code the library does not own: `errorToString` reads `message` and `stack` off it and walks `additionalInfo`. A revoked `Proxy`, a throwing `stack` accessor, or a cyclic `additionalInfo` each made that render throw, and the render sat outside the guard — so `safeHandleCallback` threw, `safeHandleCallbackAndWait` rejected instead of returning its structured failure, and `EventEmitterProtected.emit` threw into whatever was emitting (a `LRUCache.set`, a `LifecycleManager` transition). A value that cannot be described is now reported without its description. The logger's global listener is hardened the same way: it reads the event's `error`, `message`, and `target` through guards, guards the `instanceof` on the payload, and wraps its own logging so a failing sink or an unrenderable error falls to the console instead of escaping. That last part matters more than it sounds — a listener that throws does not propagate back into `dispatchEvent`, but outside a browser the runtime treats it as uncaught, and on Bun 1.3.14 and Node 25.9.0 it exits the process with code `1`.
- **`safeHandleCallbackAndWait` returns a real `Error` for a non-`Error` throw.** `CallbackResult.error` is declared `Error` but was a cast, so a callback doing `throw null` handed back `null` typed as one and `result.error.message` threw. It is now normalized like every other failure path, with the value thrown kept as `cause`. The normalizer moved to its own module (`to-error`) so the logger and `safe-handle-callback` share one copy, and ships as `lifecycleion/to-error` like every other helper, so a consumer inspecting `result.error.cause` can reproduce the same normalization.
- **`to-error` adds `describeError(value)`, and reading an error's `message` is now guarded everywhere.** `toError` guarantees an `Error` _object_, not a readable one: it returns an `Error` instance unchanged — deliberately, so identity, `stack`, and `cause` survive for a caller that needs them — while `message` stays an ordinary property that a subclass or a `Proxy` can turn into an accessor that throws. Four sites in the logger normalized with `toError` and then read `.message` unguarded, so a sink or `'logger'` handler throwing such an error made the exception escape `handleLog` and land in the caller's own `logger.info()` — and in the global `'error'` listener it escaped the listener entirely, skipping `preventDefault()` and losing the original report. All four now use `describeError`, which normalizes and reads in one guarded step and never throws. Exported as part of `lifecycleion/to-error` because the same trap faces any consumer writing an `onSinkError` or `onEventHandlerError`, both of which the docs require not to throw.
- **`errorToString` never throws.** It is called on reporting paths to render whatever a callback threw, but read its subject's `message`, `stack`, `code`, and `additionalInfo` directly, so a throwing accessor raised a second failure on top of the first and a cyclic `additionalInfo` exhausted the stack. Every property read is now guarded and an unreadable member treated as absent, values that resist rendering become `<unrenderable>`, the recursive walk refuses to revisit an object it has already seen and emits `<circular>`, and the whole render is wrapped so that even a stack exhausted by a deeply nested payload returns `<error could not be rendered>`. Rendering of ordinary errors is byte-for-byte unchanged — the existing snapshots cover it. `reportCallbackError`'s own try/catch around it is kept as a local backstop rather than resting on another module's guarantee.
- **The error-normalization idiom is replaced by `toError` across `lifecycle-manager`.** All 21 sites hand-rolled `error instanceof Error ? error : new Error(String(error))` on values thrown by component callbacks. Both halves of that can throw — `instanceof` walks a prototype chain a revoked `Proxy` refuses, and `String()` on an `Object.create(null)` throw value raises a `TypeError` with no `Proxy` involved — and several of these sit inside `setTimeout` callbacks (`onStartupAborted`, `onGracefulStopTimeout`, `onShutdownForceAborted`) where there is no caller left to catch anything and the runtime treats the throw as uncaught. In the graceful-stop case the `reject()` that follows never ran either, leaving `shutdownComponentGraceful`'s `Promise.race` unsettled and the stop hung. Non-`Error` throws now also keep the original on `cause`, where the old idiom discarded it.
- **`handleComponentUnexpectedStop` normalizes at the boundary.** `reportUnexpectedStop(error?: Error)` is declared `Error` but is unvalidated component input, and the value was stored raw and dereferenced in several places later. The `.message` read sat _after_ the state mutations and _before_ the event emissions, so an unreadable error left the manager recording the component as stopped while `component:unexpected-stop` and `component:stopped` were never emitted. Normalized once on entry, which covers the later reads in `startAllComponents`'s failure summary too.
- **The fire-and-forget shutdown-warning chain has a terminal `catch`.** With `timeoutMS === 0` the chain is deliberately not retained, so a throw from its reporting handler became an unhandled rejection mid-shutdown — fatal under Node's default `--unhandled-rejections=throw`. The timed branch was already contained by `Promise.allSettled`.
- **`NamedPipeSink` no longer lets a throwing `onError` kill the process.** The callback was invoked unguarded, unlike `FileSink`'s, and `handleError` is reached both from a Node stream `'error'` handler — where a throw is an uncaught exception — and from `initializePipe`, whose promise the constructor starts without a `.catch`, where it became an unhandled rejection from a constructor. It is now wrapped and falls through to the console, and the value it receives is normalized rather than cast.
- **A frozen error from a `streamResponse` factory no longer loses its retry classification.** `markStreamFactoryError` in the Node adapter assigned marker flags directly onto the caller's error; a frozen or sealed one made that assignment throw in strict mode, and the rejection then carried neither flag, so the client took its generic retry arm instead of terminating as a non-retryable `stream_setup_error` and invoked the factory again. Tagging is now attempted in place — preserving the original identity and stack in the normal case — and falls back to a fresh carrier holding the same marks with the original on `cause`, as the fetch adapter's `markResponseStreamAbort` already did.
- **`http-client`'s four private `normalizeError` copies keep the thrown value on `cause`.** A rejection with `{ code: 'E42' }` reached the caller as `Error("[object Object]")` with the payload unrecoverable.
- **Template rendering no longer throws on an unreadable value.** `CurlyBrackets` walked the placeholder path with a bare `in` test and property read, then `String()`, all of which run code it does not own. `{{error.message}}` against an error with a throwing `message` accessor therefore threw out of `handleLog` and into whatever called `logger.warn()` — which, for the abort callbacks above, is a bare timer. An unresolvable path already renders the configured fallback; an unreadable one now does the same.
- **Redaction fails closed.** `applyRedaction` calls the user's `redactFunction` and stringifies caller-supplied values, and neither was guarded, so a redactor that throws — or a value whose `toString` does — threw out of `handleLog` and into whatever called `logger.info()`. Worse than the throw was the alternative: `handleLog` renders the message from `redactedParams ?? params`, so any handling that let redaction fall through would have printed the very values redaction was asked to hide, to every sink. Each key is now redacted inside its own guard and a failure substitutes `***REDACTION FAILED***` rather than leaving the original in place, with a backstop in `handleLog` for a wholesale failure. The marker is deliberately distinct from an ordinary `***` mask, so a broken `redactFunction` cannot hide itself behind output that looks successful. `entry.params` is unchanged and still carries the raw values for sinks that opt into them, as before.
- **`errorToString` marks only genuine cycles as `<circular>`.** The recursive walk of `additionalInfo` marked every object it had ever seen, so a payload that simply referenced one object twice side by side rendered the second as `<circular>` - a claim that was not true, and read as a bug in the caller's data. It now tracks the objects on the current path and releases each one as that branch finishes, so only an object contained within itself is cut.
- **`REDACTION_FAILED_MARKER` is exported from `lifecycleion/logger`,** so a sink can recognise a value whose redaction failed without hard-coding the literal.
- **`sensitiveFieldNames` now uses the same path syntax as the logger's `redactedKeys`.** It matched bare names against the top-level keys of `additionalInfo` only, so `additionalInfo: { user: { password: 'hunter2' } }` with `sensitiveFieldNames: ['password']` rendered the password in the clear - the recursive walk never consulted the list. Rather than make bare names match at any depth, which would have left the library with two opposite redaction models, entries are now parsed with the same `getPathParts` the logger uses: a bare name addresses a top-level key, and `user.password`, `items[0].token`, and quoted bracket keys address one exact location. A path written in `sensitiveFieldNames` previously matched nothing at all. Masking also fails closed - a list that is present but unusable, including a malformed path, drops `additionalInfo` wholesale rather than rendering it.
- **The HTTP client's error normalization now matches `toError` word for word.** Its four private `normalizeError` copies produced a bare `String(value)` and an `Unknown error` fallback, so the same thrown value described itself one way when the HTTP client caught it and another when anything else did. All four now produce `Non-error value thrown: <description>`, with `unknown value` as the description when the value resists `String()`. `Unknown error` said less than it appeared to: nothing about the failure was unknown except how to render the value. The copies stay local by design, so the HTTP client keeps its own guarded normalization rather than importing across module boundaries.
- **`sensitiveFieldNames` masking fails closed.** A value that is present but not a usable array of strings - a comma-joined string, a `Set`, or an accessor that throws and reads back as `undefined` - previously disabled masking silently and rendered `additionalInfo` in the clear. The caller asked for masking without saying which names, so `additionalInfo` is now dropped wholesale and replaced with `*** (sensitiveFieldNames unreadable)`. This matches the fail-closed rule the logger's redaction adopted in the same release.
- **One unreadable value no longer collapses the whole `errorToString` render.** `Array.isArray` throws on a revoked `Proxy` and ran outside the per-value guards, so a single bad leaf in `additionalInfo` escaped to the top-level backstop and threw away the error's message, name, and stack. It is guarded like every neighbouring read, and that leaf alone degrades to `<unrenderable>`.
- **Normalizing what `reportUnexpectedStop()` stores no longer changes which failure wins.** `LifecycleManager` decides an overlapping startup failure by asking whether the component self-reported _with its own error_, and that test was `instanceof Error` on the stored value. Storing a normalized error made every off-type value pass it, so a bare string signal outranked a real thrown startup error and replaced the useful diagnostic. Whether a real `Error` was supplied is now recorded when the report arrives, so the rule is unchanged while the stored value stays safe to read.
- **A dotted `redactedKeys` entry now covers both readings.** `'user.password'` was resolved only as a path, so a params object carrying one literal key of that name - `{ 'user.password': 'secret' }` - redacted nothing and logged the value in the clear, since the walk looked for `params.user.password`. The entry is ambiguous, and leaving either reading unredacted is what redaction exists to prevent, so both are redacted when both exist. Note the guarantee is about redaction _failing_, not about finding every secret: an entry that resolves to nothing still redacts nothing, so a typo protects nothing.
- **An unreadable `sensitiveFieldNames` no longer fails open.** A throwing accessor was read through an ordinary guarded read, so it came back `undefined` and was indistinguishable from the member being absent - which means "mask nothing", and the values it named rendered in the clear. The read now tells the two apart, and an unreadable list fails closed like any other unusable one.
- **A bare `sensitiveFieldNames` entry is taken literally.** Routing every entry through the path grammar meant an ordinary name that is not a valid path segment, such as `password-hash`, failed to parse and dropped the whole of `additionalInfo` along with every unrelated diagnostic field, while the logger's `redactedKeys` masked the same name without complaint. A bare name is now matched literally in both. A dotted or bracketed entry covers the nested reading and the literal-key reading, also matching the logger.
- **The redaction failure marker reaches a literal dotted key.** `applyRedaction`'s catch wrote through `setNestedValue`, which re-parses the key as a path - so for a key spelled `'user.password'` it found no path, wrote nothing, and the clone's original value survived in the clear. Reachable with no user code at all: a value whose `toString` throws fails on the success path and lands in that catch.
- **An unquoted path segment is no longer restricted to `\w+`.** It is now a run of name characters - letters, digits, combining marks, `_`, `$`, `@` and `-` - so ordinary key names resolve without quoting: `user.password-hash`, `users[0].api-key`, `user.@id`. Previously those failed to parse, and an unparseable path silently resolves to nothing in every consumer of this grammar - it rendered the literal placeholder in `CurlyBrackets`, and redacted nothing in the logger's `redactedKeys` and in `errorToString`'s `sensitiveFieldNames`, with no warning either way. The failure mode was silence and the consequence was an unmasked secret, while the same name worked fine as a bare top-level key, so the restriction was sharpest exactly where it mattered least to have it. Genuinely unsupported syntax is still rejected, which is what the grammar was tightened for in 0.0.6: wildcard selectors such as `users[*].password`, a trailing dot, and an unterminated bracket all still fail to parse, and a key that really contains a delimiter still needs the quoted bracket form, since only quoting can disambiguate it. Everything else is excluded for that same reason and one more, which is why the segment is an allowlist rather than "anything that is not a delimiter": a placeholder is written by hand into prose, and `CurlyBrackets` leaves one it cannot parse exactly as written but renders the configured fallback for one that parses and resolves to nothing. Admitting whitespace or prose punctuation would make almost any brace-wrapped phrase parse as a key name, so `Note: {{Hello world}} done` and `Note: {{Hello,world}} done` would silently become `Note: (null) done`. A key that genuinely contains a space, a comma, or any other punctuation takes the quoted form, `u['my key']`. `{{user.display-name}}` now resolves rather than rendering as itself.
- **`errorToString` accepts a `redactFunction`, and shares the logger's default masking.** `errorToString(error, maxRowLength, { redactFunction })` controls how a value named by `sensitiveFieldNames` is rendered, taking the same `(key, value)` shape as the logger's option so one function serves both - the same key as written in `sensitiveFieldNames`, and the value already stringified, which also keeps a mutating function from reaching into the caller's error object. The default is now the same masking the logger applies rather than a full `***`, so a value renders identically whether it went through a log line or a rendered error. That default is partial - the first and last characters survive, so a secret can be correlated across log lines without being readable - which means rendered errors now reveal those characters where they previously showed nothing. The shared implementation lives in one place so the two cannot drift. A `redactFunction` that throws, or a value whose accessor throws, still falls back to `***` rather than to the original.
- **A `redactFunction` can return `null` to defer to the default,** in the logger and in `errorToString` alike. Special-casing a few keys previously meant reproducing the default masking for every other key, since any return value was taken literally. Returning `null` now falls back to the default for that value; to render a literal null, return the string. Only `null` defers - returning nothing keeps being used literally, which drops the value, since treating a missing return as a deferral would turn a field an existing caller was dropping into a partial mask.
- **The default masking no longer returns a value it failed to mask.** `datamask` hides a proportion of a string, so a one-character secret came back verbatim and a two-character one lost a single character. A mask that did not mask is not a mask, so anything too short for proportional masking now falls back to `***REDACTED***`. Note what the default does keep visible on longer values: roughly the middle 60% is masked, so a long secret leaves a proportionally long prefix and suffix readable. Pass a `redactFunction` returning a constant where that is not acceptable.
- **Naming a container redacts its contents instead of stringifying it.** `redactedKeys: ['creds']` over `{ creds: { pw: 'secret' } }` produced `"[ob*********ct]"` - a mask applied to the text `[object Object]`, which was never the secret, with the structure thrown away so a structured sink received a string where an object had been. An array fared worse: `['topsecret', 'other']` was joined to `topsecret,other` and masked as one string, so the edges of both elements survived into a single value. A plain object or array is now walked, each leaf masked, and the container rebuilt. An `Error` or a `Date` is deliberately not treated as a container - its string form says more than its enumerable properties would, so it is still masked as a single value. A container that contains itself terminates rather than recursing. Note the rendered message interpolates a redacted container exactly as it does an unredacted one, so a shape that survives for a structured sink still reads as `[object Object]` in the message text.
- **The default masking has a length floor.** `datamask` masks a proportion of a string, so a short value kept most of itself: a four-digit PIN rendered `1**4` and a two-character value rendered `*b`. Anything shorter than 8 characters is now replaced with `***REDACTED***` outright, since a proportional mask of something that short hides almost nothing. Longer values are unchanged.
- **A value's _derived_ string form is never partially masked.** Naming something sensitive that is not a plain object or array - a `URL`, a `Map`, a class instance, a function, a symbol - stringified it and masked a proportion of the result. The default masking preserves a value's first and last characters, and for a `URL` that is exactly where the query string sits, so an API key passed as `?api_key=...` survived almost intact: 13 of 18 characters in the clear, in `redactedParams` and in the rendered message. A function or symbol carrying a secret in its `toString` or description leaked the same way. Any value whose string form is produced rather than being the value itself is now replaced outright with `***REDACTED***`. Partial masking applies only to a genuine string. A plain object or array is still walked leaf by leaf.
- **The failure marker is one shared constant.** `errorToString` reported a failed mask as `***` while the logger reported `***REDACTION FAILED***`, so the same condition read differently depending on which feature hit it. Both now use `REDACTION_FAILED_MARKER`, which moved to the shared module and is still exported from `lifecycleion/logger`. A throwing value accessor in `errorToString` reports it too, rather than yielding `undefined` and masking the word to `un*****ed`.
- **A `__proto__` key inside a redacted container is rebuilt as an own property.** Plain assignment silently dropped it for a string value and reparented the rebuilt object for an object value.
- **A `redactFunction` can ask for the library's masking instead of producing it.** Special-casing one key previously meant reimplementing the default for it. The return value now decides: a string is used literally, `null` defers to the default, a **number** defers at that percent, and an **object** is a masking request - `strategy` (`'string' | 'email' | 'domain'`), `percent`, `maskChar`, plus `userPercent`/`domainPercent` for email. `'email'` keeps the `@` and the dots so an address stays recognizable, and `'domain'` does the same for a hostname; the default `'string'` strategy mangles both, since it masks a proportion of the whole value. `redactedKeys` still decides _what_ is redacted, and this decides _how_ for the keys you single out. A returned object counts as a masking request only when its own enumerable keys are all masking settings; any other object - `{ note: 'withheld' }`, or one mixing settings with unknown keys - is an ordinary literal replacement, matching how an array return has always been treated. `{}` is a request, not a literal: every setting is optional, so an empty object asks for the defaults and lands where `null` does - which is what a config assembled conditionally should do when it ends up empty. It lands there in full, non-string handling included: only a request that actually names a setting is the deliberate opt-in that masks a produced string in part, so an empty one cannot quietly hand a `URL` back with its query intact. Recognizing by shape rather than by "is a plain object" matters in one direction in particular: reading a caller's structured stand-in as an empty masking request would discard their value _and_ emit a proportional mask of the original in its place, partially disclosing the value they asked to replace outright. A request that would hide nothing - a percent of `0`, a value too short, an address that will not parse - falls through to `***REDACTED***` rather than returning the original.
- **A `redactFunction` is typed for what it actually receives and may return.** `value` was declared `unknown` on all four aliases and is always a `string` - the leaf is rendered before the function is called, which is also what keeps a mutating function from reaching into the caller's payload. It now says `string`, which is not a breaking change for an implementor: a function written `(key, value: unknown)` still satisfies it. The return is a named `RedactFunctionResult` - `string | number | RedactMaskConfig | null | undefined` - rather than `unknown`, so the four control signals are visible in the type instead of buried in prose. Returning anything else is now a type error, though the runtime still handles it for JavaScript callers.
- **An object returned from a `redactFunction` is always a masking request, never a replacement value.** Returning one used to put it in the output, where it rendered as `{"note":"x"}` in the log line a masked value belonged in - and deciding _which_ objects were configs was the guess that leaked: an unrecognized shape read as one discarded the caller's value and emitted a proportional mask of the original in its place. There are now two outcomes for an object and neither emits it: every own key names a setting and there is at least one, so it is masked with exactly those; or it is not usable as a request, and the default masking applies. The second covers `{}`, an unrecognized key, a mixture such as `{ percent: 10, note: 'x' }`, an array, a class instance, and a `Proxy` too hostile to read. All land exactly where `null` does, in full - the non-string rule included, so an unusable request cannot hand a `URL` back with its query intact or a card number with its BIN prefix and last four. Keys are read with `Reflect.ownKeys`, so a symbol or non-enumerable key counts as a key rather than making an object look empty. To substitute a value of your own, return a string; that is what the function is for.

- **A masking request must name a setting with a value, not merely carry the key.** `{ percent: undefined }` was classified as a request and masked through `maskWithConfig`, skipping the rule that refuses to partially mask a _derived_ string - so a `URL` came back with its query intact and a card number with its BIN prefix and last four. `{}` was already routed to the default masking for exactly that reason, and this is the same object one line of conditional assembly later: `{ percent: cond ? 10 : undefined }` is what a config built that way actually looks like, so the shape the rule exists for was the shape missing it. Values are now read, not just keys; a config where every setting is `undefined` lands where `{}` and `null` land.
- **A non-finite `number` return defers instead of being emitted.** `Number.isFinite` gated the percent branch and the value then fell through to the literal rule, so `redactFunction: () => Number(process.env.MASK_PERCENT)` on an unset variable put a bare `NaN` in the output, serializing to `null`. `{ percent: NaN }` already fell back to the default masking, so the two spellings of the same mistake disagreed. Both now defer.
- **`logger.errorObject()` renders through the logger's own redaction settings.** `prepareErrorObjectLog` called `errorToString` with no options, so an error's `sensitiveFieldNames` were masked with the library defaults rather than the logger's `redactFunction` - the same value masking one way as a param and another inside an error - and a redaction failure there went to `console.error` even when `onRedactionError` was supplied, in addition to the params report, twice for one call with one of them uninterceptable. Both options are now threaded through. The once-only bound is documented as per redaction _pass_ rather than per log call, which is what it always was: `errorObject()` redacts twice, and those are two different failures in two different values.

- **Added `onRedactionError`, so a failed redaction leaves a diagnosis and not only a marker.** Redaction fails closed and substitutes `***REDACTION FAILED***`, deliberately distinct from an ordinary mask so a broken `redactFunction` cannot hide behind output that looks fine - but the thrown error was discarded outright, so the marker said _that_ redaction failed and nothing about why. A redactor throwing for one key out of forty left one marker and no way to trace it. The new callback is on `LoggerOptions`, `StringifyValueOptions`, and `ErrorToStringOptions`, and receives the failure normalized to an `Error` plus the entry as the caller wrote it (`user.password`, not the leaf). It also fires for the branches that discard data wholesale and could not be diagnosed from the output at all: a `redactedKeys` that is not an array, and a `sensitiveFieldNames` that is not a usable list. It **defaults to `console.error`**, so a broken redactor is loud. Deliberately not the global `'error'` channel every other failure here uses: reporting a redaction failure there loops, since a listening logger logs it, logging renders, rendering redacts, and redaction throws again - each pass a fresh turn, which no re-entrancy guard closes. `onEventHandlerError` exists for the same reason and takes the same shape. It fires at most once per call, because a failure is raised per leaf and an unconditional throw would otherwise report once for every value inside a named container; the markers in the output still show the full extent. The output is byte-for-byte unchanged either way - this is purely additive.

- **Masking a named container degrades one leaf at a time.** Naming a plain object or array in `redactedKeys` or `sensitiveFieldNames` masks every leaf inside it and keeps the shape, but the walk that does so had no per-entry guard - so one unreadable element, or a `redactFunction` that threw on a single leaf, collapsed the _whole_ container to `***REDACTION FAILED***` and took the shape with it. Each leaf is now read and masked inside its own guard, so the failure is marked where it happened and every sibling still masks and still renders. This brings the masking walk in line with the redaction walk and the renderer, which both already degraded per element; a value treated one way by one walk and another way by another is the bug class these three share an implementation to avoid. The array length and the object key set are read through guards for the same reason, and a cycle now yields the shared `***REDACTED***` constant rather than a hardcoded copy of it.
- **The default now masks 90% of a value, up from 60%.** At 60% a long secret left a proportionally long prefix and suffix readable: an API key showed roughly ten of twenty-two characters. Enough still survives at each end to correlate the same value across log lines.
- **Numbers are no longer partially masked.** A number reaches the masker as a produced string, and proportional masking keeps its ends - so a card number kept its BIN prefix and last four, `4111111111111111` rendering as `411*********1111`. Partial masking now applies only to values that were genuinely strings; everything else is replaced with `***REDACTED***`. A masking request opts a specific value back in, so partial masking of a number is a deliberate choice rather than the default.
- **A plain object or array in a template renders as JSON.** `{{meta}}` produced `[object Object]` and `{{list}}` produced a bare comma join, which cannot be told apart from one element containing a comma. Both now render as JSON, so the values are actually readable - and a redacted container interpolated whole shows its masked leaves rather than hiding them behind `[object Object]`. Anything with a string form of its own is unchanged: an `Error` still renders `Error: boom`, a `Date` its timestamp, a `URL` its href.
- **A class instance says what it is.** An instance that does not define `toString` inherits `Object.prototype`'s, which renders `[object Object]` and names nothing. It now renders as `[FooBar]` - enough to identify what was passed without dumping fields the caller never asked to print. An instance that does define `toString` keeps it.
- **Added [stringify-value](./docs/stringify-value.md)** (`lifecycleion/stringify-value`), exporting `stringifyValue` and `redactValue` - the rendering and masking every module already used, exported so an application can produce the same text - and masking-aware, so one call renders a value with parts of it redacted. `stringifyValue(value, { redactedKeys, redactFunction })` takes the same path syntax and the same `redactFunction` contract as the logger, so a function written for one works with the other. It consolidates what had been three separate concerns - rendering a value, matching redaction paths, and applying a mask - behind one entry point, built from the same shared internals the logger and `errorToString` use rather than a fourth copy.
- **`redactValue` returns the masked structure rather than text.** `stringifyValue` renders to a string, which left no way to get the redacted value back short of parsing that string. `redactValue(value, options)` takes the same options and returns the value with every named path masked and its shape intact, so an object comes back an object. The two compose - `stringifyValue(redactValue(v, o))` produces the same text as `stringifyValue(v, o)` - and rendering an already-masked structure is just `stringifyValue` with no options. Both share one implementation with the logger's `redactedKeys`, so a `redactFunction` behaves identically in all three.
- **Redaction changes only what it masks.** The walk descended into anything object-shaped, so masking one field rebuilt an `Error` or a class instance as a plain object - and the renderer, which prints those through their own string form, then printed their _fields_ instead. Asking to hide `password` on a `Session` printed the `internalToken` beside it, and redacting a field on an `Error` printed the `databaseURL` hanging off it, neither of which any unredacted log line had ever shown. Redaction disclosed. It now walks exactly what the renderer walks - a plain object or an array - so everything else is one value in both, and naming anything inside one masks the whole of it: one string replaced by another, leaving the printed shape as it was. Nothing is rebuilt for such a value; only plain objects and arrays are ever copied. An array is rebuilt as a plain `[]` filled by index rather than through `map`, because `map` on a subclass runs `ArraySpeciesCreate` and a subclass constructor that validates its arguments threw from inside the walk, turning an entire payload into the failure marker over one value the renderer handled without trouble. The exceptions to "only what was masked changes" are stated rather than silent: a container whose keys cannot be read, and a container holding itself once a mask has landed elsewhere, both become the failure marker, since redaction can copy around neither and handing back the original risks returning it unmasked. A cycle in a payload where nothing matched at all is left exactly as it came in - which needs the two conditions kept apart, because they are not the same evidence. A back-edge points at an ancestor already on the stack, so "nothing matched" is a fact about a place the walk has seen; a read that threw hides whatever was behind it, so the same conclusion would hand back an original with a redacted key still in the clear. Masking also covers exactly what rendering prints - own enumerable string-keyed properties - so a non-enumerable property, a symbol key, or one a `Proxy` hides from `ownKeys` is neither masked nor printed: nothing reaches a log line, but `redactValue`'s result is safe to render rather than a sanitizer for an arbitrary consumer. That also retires a run of special cases this release went through trying to patch the old shape, since a value the renderer prints whole can no longer be entered at all: there is nothing left for a symbol key, a private `#field`, a `Map` subclass's `toString`, or a lying `Proxy` `has` trap to slip through, and no predicate has to guess which of those carry state. The rule the old shape kept breaking is now the stated one: redacted output differs from unredacted output only where a value was masked.
- **A value now renders the same way at every depth.** Nested values went through `JSON.stringify`, which applies its own rules rather than this library's, and the two disagreed in ways that lost information or leaked it - invisibly, since the same value printed differently depending only on whether it sat inside an object. An `Error` and a `Map` both rendered `{}`; a function and an `undefined` vanished without trace; a single `BigInt` anywhere threw and collapsed the whole render to `[object]`, losing every other field over one value; and a class instance had its fields dumped, though naming it rather than dumping it is a deliberate rule one level up - so a secret that `stringifyValue(session)` correctly hid as `[Session]` was printed in full by `stringifyValue({ session })`, where no redaction path could reach it either, because nothing had been named. Containers are now rendered by a small serializer of our own that sends every leaf back through the same top-level rules, so `{"v":"Error: boom"}`, `{"v":"[Map]"}`, `{"v":"[Session]"}`. Only plain objects and arrays are walked, which is the same structure-versus-value rule redaction uses - a `Map` or `Set` is a leaf at any depth, so nesting one inside another is a single `[Map]` and a self-referencing one cannot loop. **A `toJSON` method is no longer called.** `JSON.stringify` honoured it and the first cut of this renderer did too, which turned out to be both arbitrary and expensive: it was honoured for a plain object and silently ignored for a class instance, and it is caller code on the logging path - free to throw, to be slow, or to return a different answer each call. It also fought redaction, since masking a rebuilt copy cannot reach through a method: a `toJSON` closing over its own state returned the pre-mask values, so `redactedParams` looked correctly masked while the rendered message leaked, and a field appearing only in the method's result was not a property at all and could never be reached. Resolving the method before masking closed that, at the cost of keeping caller code on the path for a case that splits arbitrarily by prototype. Not calling it closes the same hole with no special case anywhere: an object defining `toJSON` is walked like any other, so `['cfg.apiKey']` masks that one field, and the method itself prints as `[Function: toJSON]`. Use `redactedKeys` to keep a field out of a log line. A function now renders as `[Function: name]` rather than its entire source, which is unbounded and carries whatever the author wrote inside it into the log line. A cycle is cut where it closes (`{"a":1,"self":"[circular]"}`) rather than collapsing the object around it, and one unreadable element or entry degrades to `[unrenderable]` on its own rather than taking its container with it - the array branch previously had no guard at all, so a single throwing element lost the whole payload. The walk stops at a depth of 100 and says so with `[max depth exceeded]`, rather than recursing until the stack gives out: with the per-entry guards in place that `RangeError` was caught and swallowed, so a pathological payload rendered tens of kilobytes that simply stopped, with nothing marking the truncation. **`Date` now renders as ISO everywhere**, including at top level where it previously used the locale form: `2020-01-01T00:00:00.000Z` rather than `Wed Jan 01 2020 00:00:00 GMT+0000 (...)`, which is sortable, parseable, and timezone-independent. This affects `stringifyValue`, and template rendering through it, so a `{{when}}` placeholder changes shape.
- **The "plain object or array" test is shared rather than copied.** `maskValueDeep` and `stringifyTemplateValue` each carried a byte-identical private copy, and it is the single rule both redaction and rendering turn on - what counts as structure to walk, versus a value to mask or render whole. Two copies of that could only drift apart into a value masked one way and rendered another.
- **Redaction no longer flattens the values it was not asked to touch.** The shared path walk rebuilt every object it descended through, and it rebuilt them from `Object.entries` - which is empty for a `Date`, a `Map`, a `Set`, and a `RegExp`, and skips the non-enumerable `message` and `stack` of an `Error`. Naming a single key therefore replaced every unrelated value beside it with `{}`: `logger.info('{{when}} / {{error.message}}', { params, redactedKeys: ['password'] })` rendered `{} / ` where the same call without `redactedKeys` rendered the date and the message, and a structured sink reading `entry.redactedParams` got empty objects in place of the originals. The walk now copies only the branches that lead to a mask and passes everything else through by reference, so anything not named comes back as the value that went in, identity included - the exceptions being a cycle and a value whose keys cannot be read, which still fail closed to the marker. A container that _was_ masked inside is still rebuilt as a plain object, since the caller's own value must not be mutated and a class instance cannot be reconstructed from outside - losing the type there is the price of masking within it, and it applies only where redaction actually landed. This affected `redactValue` and `stringifyValue` as well as the logger; `errorToString` renders rather than rebuilds and was never affected. Which locations an entry addresses is unchanged, in all three.
- **Redaction no longer hands back the original when it cannot read a value's keys.** The walk that looks for redaction paths reads the keys of each object it descends into. If that read threw - a sibling property with a throwing getter - it returned the value it had been given, which is every sibling in the clear, including the ones named for redaction that the walk never reached. It returns the failure marker instead. A cycle is cut the same way rather than placing the unmasked original inside the copy. `applyRedaction` was already safe here by accident, since its `deepClone` probe throws first; `redactValue` and `stringifyValue` were not.
- **A stream write failure no longer leaves a listener on the caller's writable.** A failed write destroys the stream and emits its `error` after the request has settled and its listeners are gone, so the adapter attaches a one-shot absorber to keep that from being an uncaught exception that ends the process. `once` only detaches on delivery, though, and a hand-written `WritableLike` that throws from `write` or `end` is not obliged to emit anything afterwards - so a writable reused across requests accumulated one absorber per failure until Node warned about a leak. The absorber is now keyed on the writable rather than on the request - `streamResponse` may hand the same sink to several concurrent requests, and a per-request absorber let a dozen simultaneous failures attach a dozen listeners inside one turn, before any removal ran. One per writable is also all that is needed, since it is attached with `on` rather than `once` and so keeps absorbing instead of standing down after the first error and leaving a sibling's unhandled. Its lifetime is bounded by a `setImmediate` that removes it unconditionally. The timing is measured rather than guessed: on Node 25 and Bun 1.4 a failed write emits after `process.nextTick` and before the next `setImmediate`, so a real stream has always delivered by then and the removal is a no-op. The removal is `unref`'d so it cannot hold the process open, and a runtime that cannot schedule it keeps the listener, which is the safe direction of the two. An absorber is not attached at all to a writable that declares no listener-removal method, since it could never be taken back - the scheduled cleanup would drop its bookkeeping while the listener stayed and the next failure attached another, which is the growth being prevented. Nothing is lost by skipping it: the request's own `'error'` listener could not have been detached from such a writable either, so it is still attached and absorbs the late error itself. If the removal itself refuses - it is caller code and can throw - the listener is still attached, so the record saying so is kept rather than dropped, which is what stops the next failure adding a second listener on top of one that never came off. `removeListener` is now honoured alongside `off` when one is present, since both are `EventEmitter`'s, and both are declared on `WritableLike` as optional members worth defining. Neither affects a Node stream, which has both and reports its write failures on time; [docs/http-client.md](./docs/http-client.md#writing-your-own-writablelike) now spells out both expectations for anyone hand-rolling a sink. That timing is now written down as part of the `WritableLike` contract: an implementation that emits its `'error'` later than the next `setImmediate` turn must not leave it unhandled, since the alternative is holding a listener on the caller's sink forever.
- **A params bag with a non-plain prototype still comes back a record.** The shared walk treats anything whose prototype is not `Object.prototype` as a single _value_ and masks it whole, which is right for a `URL` or a class instance nested inside a payload - that is how it renders - but wrong for the bag being walked. A class instance passed as `params` matched "a path points inside this" at the root and came back as the bare string `'***REDACTED***'`, against `applyRedaction`'s declared record type: every template placeholder then rendered as the fallback, and a structured sink reading `entry.redactedParams` got a string where it expected its params. The bag is now normalized to a plain object first, by spreading its own enumerable properties - which are exactly what the renderer prints and what the walk would have read anyway - so only the prototype changes.
- **Masking an array no longer runs the caller's constructor.** The leaf walk used `Array.prototype.map`, which goes through `ArraySpeciesCreate` and calls the value's own subclass constructor with a length argument. A tuple subclass that rejects that threw from inside the walk, where there is no `catch`, so a named container came back as `***REDACTION FAILED***` instead of the masked array shape. It now fills a plain array by index, the same way the path walk already did for the same reason.
- **`applyRedaction`'s fail-closed path no longer throws.** `redactedKeys` is typed `string[]`, but a JavaScript caller can pass anything, and the marker-everything fallback called `.map` on it - so a non-array threw a `TypeError` out of the one branch that exists because the input could not be trusted. A non-array is now rejected before anything reads it, and the fallback is guarded.
- **A failed write to a `streamResponse` writable no longer resolves as a success.** Every byte could fail to reach the caller's sink and the request still returned `isFailed: false`, `isStreamError: false`, `status: 200` - a broken download reported as complete. Two causes. `WritableLike.end` was typed `end(cb?: () => void)`, so the callback's error argument was neither modelled nor read, and a write that fails destroys the stream, which makes `end` report through that argument rather than succeed. And the writable's own `error` event arrives a tick later, usually after the request has settled and its listener has been removed - an `error` event with no listener is an uncaught exception. The signature now carries the error, the callback honours it, `writable.errored` is consulted as a second signal, and a one-shot absorber is attached on the write-failure path so the late event cannot go unhandled. `errored` is read through a guard, like every other member of a caller-supplied writable: the read happens inside `end`'s callback, which a real stream invokes on a later tick with no `try` above it, so an accessor that throws there would be an uncaught exception rather than a failed download. **`WritableLike` changed:** `end`'s callback now receives `err?: Error | null`, and an optional `errored` property was added. Both are backwards compatible for an implementor - an existing `end(cb)` still satisfies it.
- **`TmpDir.cleanup()` works again for a directory that is empty.** It called `fs.rm(path, { recursive: false })`, and `fs.rm` refuses a directory outright without `recursive`, reporting `ERR_FS_EISDIR` whether or not it is empty - so a safe cleanup could never succeed, including in the ordinary case it exists to handle. It worked before only because older Bun reported a different code for the non-empty case. It uses `rmdir` now, which means what this wants: remove it if empty, report `ENOTEMPTY` if not. The recognized not-empty codes keep the older ones and add `ERR_FS_EISDIR`.
- **`captureResourceErrors` classifies far more narrowly.** A capturing listener sees _every_ `'error'` event dispatched anywhere in the document, and anything with a `tagName` was being described as `Failed to load X`, tagged `'resource'`, and cancelled. A component dispatching its own `new CustomEvent('error', { cancelable: true })` and branching on the result therefore had its answer changed by a logger. An event now only counts as a resource failure when it is **trusted**, is a plain `Event` — not an `ErrorEvent` or `CustomEvent` — and has a target element naming a resource in `src`, `href`, or `currentSrc`. The trust check is what covers a plain `new Event('error')` the page dispatches itself: only the user agent can produce a trusted event, since `dispatchEvent()` sets `isTrusted` to `false` unconditionally, so a wrapper element re-announcing a failure with `this.dispatchEvent(new Event('error'))` stays the application's own signal rather than being logged as a load that never happened. This is unrelated to CORS — a cross-origin resource's load failure is still dispatched by the user agent and stays trusted. All three exclusions are covered in the Playwright suite. Note a platform limit this option cannot lift: resource `error` events are dispatched with `composed: false`, so failed loads inside a shadow root never reach `globalThis` and are invisible to any global listener, capture or not.
- **A non-`Error` payload on an `'error'` event is no longer discarded.** A browser `throw { code: 'E42' }` arrives with that object on the event and `Uncaught [object Object]` as the message; the object was dropped and only the message logged. It is now kept as the synthesized error's `cause`, defined non-enumerable so an arbitrary payload does not start appearing in JSON-serialized log entries.
- `safe-handle-callback` exports `runCallbackSafely(callbackName, callback, args, onError)`, the single invocation helper behind both `safeHandleCallback` and `EventEmitterProtected.emit`. `emit` previously carried its own copy of that body, which had drifted: its message for a non-callable handler read `Callback provided for event X is not a function` rather than the `Callback provided for event handler for X is not a function` every prior release produced. The original wording is restored.
- The logger's error listener also ignores reports that arrive while it is already logging. That guard only ever covered the synchronous case and is no longer what fixes it, but it is kept as a cheap backstop for any other path that dispatches synchronously from inside a sink write. The flag is cleared in a `finally`, so a sink or handler throwing its way out cannot leave the listener permanently deaf.
- `global-event-target` is unchanged in behaviour and still installs the `EventTarget` methods on Node.js, where `globalThis` is not an `EventTarget` as of Node 25. Only the event type dispatched through it has changed.
