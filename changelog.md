## 0.0.1 (Feb 23, 2026)

- Initial package publish

## 0.0.2 (Feb 28, 2026)

- LifecycleManager error and warning logs now pass full error objects in `params.error` for consistency with other component-operation log paths

## 0.0.3 (Feb 28, 2026)

- LifecycleManager, added `attachSignalsBeforeStartup` for attaching signal handlers before startup begins while preserving the original `attachSignalsOnStart` behavior
- LifecycleManager now automatically stops components that finish starting after LifecycleManager shutdown has already begun
- LifecycleManager, startup timeouts without `onStartupAborted()` now auto-stop the component if that delayed startup later completes

## 0.0.4 (Mar 2, 2026)

- LifecycleManager, fixed `enableLoggerExitHook()` so `logger.exit()` calls made during an already-running shutdown are deferred and completed after shutdown finishes instead of being left pending

## 0.0.5 (Mar 3, 2026)

- CurlyBrackets now supports array index paths such as `{{users[0].name}}`, `{{matrix[0][2]}}`, and mixed object-array traversal with existing fallback behavior preserved
- Logger redaction now supports the same mixed object-array paths in `redactedKeys`, including paths like `users[0].password`
- CurlyBrackets and logger docs/tests now explicitly cover nested path fallback behavior, primitive intermediate values, falsey terminal values, and `Error` interpolation behavior

## 0.0.6 (Mar 3, 2026)

- CurlyBrackets now supports quoted bracket keys such as `{{user["display-name"]}}` and mixed paths like `{{users[0]["display-name"]}}`
- Logger redaction now supports matching quoted bracket-key paths such as `users[0]["password-hash"]` in `redactedKeys`
- Shared internal path parsing now rejects unsupported syntax cleanly instead of partially tokenizing invalid paths

## 0.0.7 (Mar 4, 2026)

- Logger messages now render from redacted params when `redactedKeys` are configured, so templated sensitive fields are masked in `message` as well as `redactedParams`
- CurlyBrackets and logger redaction now share an internal value-stringification helper so arrays, objects, and `Error` values are normalized consistently before rendering or redaction, non-string values are now always stringified before passing to redaction functions

## 0.0.8 (Mar 18, 2026)

- Added `lifecycleion/dev-mode`, a runtime-settable dev/production mode flag with auto-detection from CLI args (`'dev'`/`'prod'`) or `NODE_ENV`, first-wins semantics for HTML injection compatibility, and `overrideDevMode()` for test/tooling use

## 0.0.9 (Mar 19, 2026)

- LifecycleManager error and warning log messages now include `error.message` inline (e.g., `"Component failed to start: Connection refused"`) so failure reasons are visible in plain log output without a custom structured sink

## 0.0.10 (Apr 7, 2026)

- Added the new adapter-based HTTP client foundation in `lifecycleion/http-client`, including the shared `HTTPAdapter` contract, fluent request builder, retries, redirect handling, cancellation, interceptors, response/error observers, request tracking, and the default `FetchAdapter`
- Added `MockAdapter` plus server-side cookie jar support and shared HTTP client request/response utilities
- Added `lifecycleion/http-client-node` with a Node adapter for server-side HTTP requests, streaming downloads, multipart uploads, Unix sockets, and TLS/mTLS options
- Added `lifecycleion/http-client-xhr` with an XHR adapter for environments that expose `XMLHttpRequest`, including real per-chunk upload/download progress, redirect detection, and Playwright-based browser integration tests
- Added `lifecycleion/domain-utils`, hardened helpers for normalizing and matching domains and origins, including IDNA/TR46 normalization, IPv6 literal support with zone-ID rejection, wildcard CORS matching with PSL/IP-tail guards, credentials-safe origin matching, and re-exports of `tldts` helpers (`getDomain`, `getSubdomain`) so consumers don't need a separate install
- Added `lifecycleion/lru-cache`, a TTL-aware LRU cache with configurable max entries, optional byte-size limit, per-entry TTL overrides, automatic expiration, and pluggable size calculators
- Fixed test-only TypeScript assertion issues reported in some unit test cases. No runtime or API behavior changed for them
- Added `lint` and `type-check` to `prepublishOnly` to strengthen the future release process

## 0.0.13 (Apr 19, 2026)

- LifecycleManager now supports an opt-in `repeatedShutdownRequestPolicy` with a required `onForceShutdown()` hook so applications can decide how to escalate repeated shutdown requests received during an already-running shutdown
- Repeated shutdown escalation now tracks request count and timing window across real signals, keyboard-triggered shutdown requests, and programmatic `triggerShutdown()` calls that flow through the same signal callback path
- The default repeated shutdown escalation window is now 2 seconds with a default force threshold of 3 requests
- Repeated shutdown escalation now supports optional `armedAfterFailureMS` overrides so failed or stalled shutdown attempts can stay force-armed longer than the default derived post-failure window
- LifecycleManager shutdown logs now distinguish between the normal first shutdown request, repeated shutdown requests still being tracked, and repeated-request escalation when the force threshold is reached

## 0.0.14 (Apr 28, 2026)

- LifecycleManager now detects when a stalled component's original `stop()` or `onShutdownForce()` promise eventually resolves and automatically transitions it from `stalled` to `stopped`, clearing the stall record and emitting a `component:stalled-resolved` event. A per-component stop generation token prevents a late-resolving promise from affecting a component that has already been restarted since stalling.
- Docs now document the `stop()` promise-deduplication pattern as the recommended approach when `onShutdownForce()` should join an already-running `stop()`, and the `onGracefulStopTimeout()` pattern as an alternative for unblocking `stop()` without a concurrent second close.
- BaseComponent now exposes a protected `reportUnexpectedStop(error?)` method. Call it when the component detects an internal failure (crashed server, lost connection, exited worker) to let the manager mark it stopped, store the error as `lastError`, emit `component:unexpected-stop`, and then emit the canonical `component:stopped` event for the resulting stopped state. A subsequent `stopAllComponents()` call skips the already-stopped component and proceeds normally. The call is a no-op once the manager begins stopping or unregistering the component, and the handler is automatically re-armed after each successful restart.
- If `reportUnexpectedStop()` fires during `startAllComponents()`, required components now fail the bulk startup with `code: 'component_unexpected_stop'` and trigger rollback of later-started components, while optional components are recorded in `failedOptionalComponents`.
- Added `component:unexpected-stop` event (payload: `{ name, error? }`) emitted when a running component calls `reportUnexpectedStop()`, immediately before the follow-up `component:stopped` event.
- BaseComponent now exposes a protected `getSelfStatus()` method that returns the component's own `ComponentStatus` from the manager without requiring the caller to pass the component name.

## 0.0.20 (Aug 21, 2026)

- **Added `crl` to `NodeAdapterConfig`:** certificate revocation lists, so a server certificate whose serial has been revoked is rejected even though its chain and hostname still verify. Revocation failures resolve as status `495` like other TLS certificate errors. The value is read on every request, so refreshing a revocation set does not require rebuilding the adapter, and no connection-pool handling is needed. `crl` is part of Node's pool key, so changing it partitions the pool and a socket established under the old CRL is never reused under the new one.
- **Concatenated CRL bundles are split for you.** Node reads only the **first** CRL of a concatenated PEM string and silently ignores the rest, unlike `ca`, which reads every certificate in a bundle. The bundle is the standard interchange format. Apache documents `SSLCARevocationFile` as "the concatenation of the various PEM-encoded CRL files," nginx and HAProxy agree, and `openssl verify -CRLfile` reads a whole bundle. This is Node diverging from the library it links rather than an OpenSSL limitation. The adapter splits bundles on the RFC 7468 boundary, including strings nested inside an array, so `[bundleOfTwo, oneMore]` contributes three CRLs. This includes **Buffers**: `fs.readFileSync('bundle.pem')` without an encoding returns one and its contents are PEM like any other bundle, so passing Buffers straight through would leave the most ordinary way of loading a file silently truncated. In testing, a bundle whose second CRL revoked the server's certificate accepted the connection as a Buffer and rejected it once split. DER Buffers pass through untouched, since DER encodes exactly one CRL. Note also that OpenSSL uses the **first** CRL it has for a given issuer rather than the newest, so a bundle must not contain two CRLs for the same issuer. Without this the failure is `UNABLE_TO_GET_CRL`, which reads as "no CRL supplied" rather than "your bundle was truncated." A bundle whose first entry happens to cover the root in use appears to work until the roster or export order changes.
- **Revocation failures are now classified as TLS certificate errors**, so they resolve as status `495` rather than a generic transport failure. This covers `CERT_REVOKED` plus every CRL verification code OpenSSL exposes, matched by property rather than by name, since the message-text fallback catches almost none of them (`CRL has expired` and "format error in CRL's lastUpdate field" contain none of the words it looks for).
- **Only PEM blocks and whitespace are accepted in a `crl` string.** A truncated or corrupted CRL, a damaged delimiter, or decoded `openssl ... -text` output is refused with an error rather than silently dropped. Splitting keeps only complete blocks, so a cut-short entry would disappear while the intact ones stayed in force, leaving the caller enforcing a set they never supplied, with no error. Passing the string through unsplit is no better, since Node reads its first CRL and ignores the rest. The rule is exact rather than heuristic because a parser cannot distinguish a half-written CRL from a line of commentary, so admitting the second necessarily admits the first. Strip annotations before passing a bundle.
- **Bun compatibility note:** Bun ignored `crl` entirely through 1.3.14. It accepted a revoked certificate with no error, no warning, and no throw on a malformed CRL, meaning the option was never read. The same was true of `minVersion`, `maxVersion`, and `secureProtocol`. All are fixed in Bun 1.4.0, which matches Node 25.9.0 on every case tested. **Require Bun >= 1.4.0 if you depend on these options for security.** The enforcement tests probe the runtime and skip where `crl` is unsupported rather than passing for the wrong reason. The bundle-splitting tests run everywhere.
- Two caveats worth reading before enabling `crl`, both fail-closed and therefore safe, but both able to refuse healthy connections: every certificate in the chain needs a covering CRL (`X509_V_FLAG_CRL_CHECK_ALL`, so a partial CRL set refuses every root it does not cover, even unrevoked ones), and CRLs expire (`CRL_HAS_EXPIRED` blocks good certificates past `nextUpdate`). See `docs/http-client.md`.
- Adapter contract types (`HTTPAdapter`, `AdapterRequest`, `AdapterResponse`, `AdapterType`, `AdapterProgressEvent`, `HTTPMethod`) are re-exported from the adapter subpaths, so code driving an adapter directly no longer has to import types from `lifecycleion/http-client`. Type-only, so nothing is added to the runtime bundle. The node subpath also re-exports the response-streaming types.
- Pinned `@types/bun` to 1.3.14. `@types/bun` 1.4.0 declares `off`/`removeListener` overloads for its `memoryPressure` event directly on `NodeJS.Process`, which shadows the generic `EventEmitter` overloads that `@types/node` relies on being inherited, breaking `process.off('SIGINT', ...)` and every other signal detach at the type level. Types only, so no runtime or security impact.
- Applied `brace-expansion` and `js-yaml` overrides to clear two high-severity advisories reaching the tree through ESLint's dev-only dependencies.
- Dependency refresh within existing ranges: `find-my-way` 9.8.0, `tldts` 7.4.10, `uuid` 14.0.2, `@playwright/test` 1.62.1, and the `typescript-eslint` packages 8.67.0.

## 0.0.21 (Aug 25, 2026)

- **Fixed callback error reporting on Node.js.** `safeHandleCallback()` and `safeHandleCallbackAndWait()` report failures by dispatching an `ErrorEvent` of type `'reportError'` through `globalThis.dispatchEvent()`. Node 25 added a global `ErrorEvent` constructor but did **not** make `globalThis` an `EventTarget`, so `dispatchEvent`, `addEventListener`, and `removeEventListener` are all `undefined` there. This meant callback errors were caught and then silently dropped on Node. The existing tests missed this because they run under Bun, which provides the browser-style global event methods. The same gap made `logger.registerReportErrorListener()` return `'not_available'` on Node.
- **Added [global-event-target](./docs/global-event-target.md)** (`lifecycleion/global-event-target`), a conservative polyfill that supplies the missing global event methods, backed by a single shared `EventTarget`. It installs only when all three methods are absent, so native and user-installed implementations are never overwritten. It is idempotent, keeping the backing target and install flag in one shared object on `globalThis` (`__lifecycleion_global_event_target__`, the same style as `dev-mode` and `process-signal-manager`) so repeated initialization and multiple copies of the package share it. Installed properties are non-enumerable and bound to the backing target. A partial or foreign surface (some methods present, others missing or present but not callable, such as `globalThis.dispatchEvent = null`) is deliberately left alone rather than mixing methods from unrelated targets or clobbering a value the application put there. A member explicitly assigned `undefined` counts as absent, since that is how a global gets cleared. Reporting is skipped there, and the helpers still return their normal results. Because installation runs during module initialization, it never throws. A non-extensible global object (`Object.freeze(globalThis)`) or a non-configurable property returns `'blocked'`, and every global it reads, including the three methods and the `EventTarget` constructor, goes through one guarded read, since reading a global runs its getter and a getter can throw. A throwing accessor is reported as `'partial'` (or `'unsupported'` for the constructor) rather than crashing the import. The reporting path is likewise throw-proof. It can drop a report, but never raise an error while reporting one rather than breaking the import of `safe-handle-callback` and everything downstream of it. A definition rejected despite that preflight is rolled back so nothing is left half-installed. Importing `lifecycleion/safe-handle-callback` or `lifecycleion/logger` installs it, so for most users this is transparent. Browser and Bun behavior is unchanged, and `ErrorEvent` is never polyfilled. Node 25+ is the supported floor and provides it natively.
- **Added Node-runtime tests.** A Bun-only suite cannot catch this class of bug, since Bun has the globals natively. The new suite bundles fixtures with `Bun.build({ target: 'node' })` and runs them under the real `node` binary, asserting that a plain `globalThis.addEventListener('reportError', ...)` receives both synchronous throws and rejected async callbacks, that the reported `ErrorEvent` carries the wrapped callback name and original error details, that nothing becomes an uncaught exception or unhandled rejection, and that repeat installation and pre-existing global implementations are handled as documented. It also pins down that Node itself has `ErrorEvent` but no global event methods, so the assumption behind the fix fails loudly if it ever changes.
- `sideEffects` is now a list rather than `false`: the installation happens at module initialization, and a blanket `sideEffects: false` would let a bundler drop a bare `import 'lifecycleion/safe-handle-callback'` despite the documented guarantee that importing it installs. Only the `safe-handle-callback` and `logger` entry files are listed, so the rest of the package stays fully tree-shakeable, and the reporting path re-runs the install itself so a swallowed error can never be a packaging artifact.
- Documentation now describes `'reportError'` as Lifecycleion's reporting convention built from web-standard primitives (`ErrorEvent` plus the global `EventTarget` methods), rather than implying the event type itself is a web-standard API.
- **Fixed unsafe retries on `FetchAdapter` when a response body was truncated.** A body that failed after headers arrived (peer reset mid-body, premature close, short read against `Content-Length`) rejected out of `send()` because the body read sat outside the adapter's `try`/`catch`. That landed on `HTTPClient`'s generic network-error path as `status: 0`, which is in `RETRYABLE_STATUS_CODES`, so the request was retried up to the policy limit. Headers arriving means the server received and processed the request, so replaying a non-idempotent write could apply it twice. `NodeAdapter` already resolved these as `isStreamError` and never retried them, so **the same truncation was retried on `fetch` and not on Node**. This was a correctness difference rather than a performance one, and one that would not show up for anyone testing on Node and shipping on Bun or in a browser. Note that the client's retry guard (`!adapterResponse.isStreamError`) was correct throughout and never fired: it only runs on a _resolved_ adapter response, and a throw out of `send()` never becomes one. `FetchAdapter` now resolves with `isStreamError: true`, `streamErrorCode: 'stream_response_error'`, the real HTTP status, and the underlying `errorCause`. A caller's `AbortSignal` still re-throws so cancellations stay classified as cancellations rather than network faults. It now carries the response metadata out with it, since the adapter sees one composite signal and cannot tell a caller cancel from a per-attempt timeout. Without that, a timeout firing mid-body-read lost the real status and left an otherwise terminal post-header failure eligible for retry, the same divergence in a second guise. `NodeAdapter` already tagged its response-stream aborts this way. The client sorts the two apart. (Carrying the metadata out was necessary but not sufficient. See the entry below on which rejections the client would accept it from.)
- **Added `MockResponse.streamError`** so the `isStreamError` branch can be tested without a real socket. Pass `true` for the default `'stream_response_error'`, or name the code explicitly. The mock reports the `status`, headers, and cookies you set, matching a real post-header failure, where the status is known and only the body is lost, while forcing `body` to `null` regardless of what the handler returned.
- **Documented which `isStreamError` guarantees are Node-only.** `NodeAdapter` covers streamed and buffered bodies and distinguishes `stream_write_error` from `stream_response_error`. `FetchAdapter` covers buffered bodies in both server runtimes and browsers. Headers have arrived by then, so the status is readable either way, but it always reports `stream_response_error`, since `fetch` buffers the body and exposes no per-chunk delivery to tell a local write failure from an upstream one. `XHRAdapter` does not report the flag at all, and that one is a spec-level limitation rather than a browser inconsistency: setting `XMLHttpRequest`'s error flag sets the response to a network error, which forces `status` to `0`, leaving no evidence that headers ever arrived. A mid-body truncation is therefore indistinguishable from a connection refused there, stays an ordinary transport failure. For an idempotent method that is still eligible for retry, so a truncated `GET` is silently re-fetched rather than reported with its real status. A non-idempotent write is spared only because `XHRAdapter` never supplies `wasDefinitelyNotSent` and the default rule blocks a replay for want of proof, not because the truncation was recognized, so enabling `retryNonIdempotentMethods` removes that protection. Browser code making replay decisions on non-idempotent writes should prefer `FetchAdapter`.
- **`NodeAdapter` now decides transport-failure replay safety from the error code** rather than from a body-byte count. The old test was `uploadedBodyBytes === 0`, which reports `0` for a request with no body, so an empty-body `POST` whose headers reached the server and then lost the connection was marked safe to replay. The counter also tracks bytes handed to the stream rather than bytes on the wire, so it could be non-zero for a connection that was never established. Only codes proving no connection happened (`ECONNREFUSED`, `ENOTFOUND`, and similar) are now treated as replayable. `ECONNRESET`, `EPIPE`, `ETIMEDOUT`, and anything unrecognized fall on the side of possible delivery. `EHOSTUNREACH` and `ENETUNREACH` are excluded despite reading like connect-time failures, because an ICMP unreachable arriving for an established connection surfaces on that connection with the same code. Seeing one does not rule out a request that was already written and received. That verdict is carried on the new `wasDefinitelyNotSent` rather than on `isRetryable`, which blocks retries for every method and is reserved for the case below. The error code is also the only signal that behaves identically on Node and Bun. `socket.bytesWritten` is not implemented under Bun and `socket.connecting` reports the wrong value there, so either would have silently claimed "nothing sent" for a request the server had already received.
- **`isRetryable: false` is now reserved for failures no method should retry.** It blocks a retry for every method, but `NodeAdapter` was setting it once a request body had started going out, including for a mid-upload socket error and both body-write failure paths. That stopped retrying an idempotent `PUT` or `DELETE` after an ordinary transport blip, the case a retry is most likely to fix, and it overrode `retryNonIdempotentMethods` where the caller had stated a replay is safe. Whether a partly-sent request may be replayed is the method question below, and withholding `wasDefinitelyNotSent` already answers it, so those three vetoes are gone. The remaining use is a rejected TLS certificate, where another attempt genuinely cannot succeed.
- **`FetchAdapter` now classifies TLS certificate failures as `495`**, matching `NodeAdapter`, instead of letting them arrive as `status: 0`, which is in `RETRYABLE_STATUS_CODES`, so a bad certificate was retried to the policy limit, failing identically each time. This is a server-runtime classification: Bun exposes the OpenSSL code on the rejected error and Node hangs it off `cause`, both of which are now recognized, while a browser reports an opaque `TypeError` with neither and such a failure keeps the ordinary transport-error shape. `XHRAdapter` cannot classify these at all.
- **Added `AttemptEndEvent.retrySuppressedReason`** so a suppressed retry explains itself. `willRetry: false` could not distinguish a policy declining from a safety rule stepping in, which made the non-idempotent default below discoverable only by reading this changelog. When the status alone would have allowed a retry, the event now names what stopped it: `adapter_veto` (the adapter reported `isRetryable: false`), `stream_error` (the body failed after headers arrived), or `non_idempotent_method`. Absent when a retry was scheduled, when no policy is configured, when the policy has no attempts left, or when the status was never retryable. In those cases nothing was suppressed.
- **Added `MockResponse.transportError`** so the replay rules are testable without a socket. `MockAdapter` could simulate cookies, redirects, delays, and (as of this release) stream errors, but had no way to produce a failure with no response at all, so none of the rules below could be exercised against it. It delivers nothing from the handler's response (no body, headers, cookies, or terminal progress) and accepts the signals a real adapter would attach: `wasDefinitelyNotSent` for proven non-delivery, `isRetryable: false` for a failure no method should retry, and a diagnostic `status` such as `495`.
- **Retries no longer replay `POST` and `PATCH` by default.** The retry decision never consulted the request method, so with a retry policy active a `POST` was retried on a `500`, even though the handler definitely ran and may have committed, making it a stronger case against replay than the transport failures above. `HTTPClient` now declines to retry the methods RFC 9110 does not define as idempotent: never after a real HTTP response, never after a thrown adapter error or per-attempt timeout, and after a transport failure only when the adapter reports the new `AdapterResponse.wasDefinitelyNotSent: true` (proof that no request bytes reached the server). The transport condition is part of the rule rather than a shortcut: on a real response delivery is already settled the other way. `isRetryable` deliberately does **not** grant this exception. It is a retry hint whose contract only ever defined `false`, so a custom adapter may set it `true` for a failure it considers transient without knowing whether the request was delivered, and reading that as proof would replay a write after an ambiguous failure. `PUT` and `DELETE` are unaffected. Both mutate, but both are idempotent by definition, so replay is safe. Set `retryNonIdempotentMethods: true` on the client config, or `.retryNonIdempotentMethods(true)` per request, to restore the old behavior for writes guarded by an idempotency key. This only ever removes retries. It never adds one, and does nothing unless a retry policy is active.
- **Set-Cookie now survives a post-header stream abort.** Cookies were stored only when an adapter resolved a response. As a result, `Set-Cookie` was dropped when the body was cut short by a timeout, a stream abort, or the caller cancelling mid-read. The identical response arriving intact stored it, as did a buffered stream failure that resolved rather than threw. Headers had arrived in every one of those cases, which is the whole basis for the existing behaviour of applying cookies from error responses to follow-up requests, as browsers and curl do.
- **The response-stream abort marker, not the error's name, is what routes a post-header abort.** The client's branch for a body that failed after headers arrived required both the adapter's marker and an error named `AbortError`. But an adapter tags that throw whenever the attempt signal aborted mid-body, and the rejection it hands back is whatever the runtime produced. Undici surfaces a timeout during the body read as `TypeError: terminated`, not as an `AbortError`. The tag arrived on an error the gate then refused. With the cancel signal untouched, because a per-attempt timeout aborts only the timeout controller, the throw fell past the cancellation check too and landed on the generic network path: the tagged status and headers discarded, `status: 0` reported, and since `0` is retryable, a `503` whose body was cut short replayed against a server that had already answered. An idempotent method is not spared, the method rule below covering only `POST` and `PATCH`. The marker is now the whole gate. This is what makes the previous entry's fix effective rather than merely present.
- **A marker is trusted only when it reads exactly `true`.** Both marker checks tested for the property rather than its value, so an ordinary adapter error carrying one as `false` reached a branch meant for a tag an adapter deliberately set. For the response-stream marker that branch is terminal _and_ writes to the cookie jar, so an error that also carried stale `streamAbortStatus`/`streamAbortHeaders` fields had that response's `Set-Cookie` filed under the current request's URL. For the XHR browser-timeout marker, a deliberate cancel reported `isTimeout`. Every adapter writes the literal `true`, so nothing is lost by asking for it. Both reads are also guarded now: the value is whatever a runtime, a library, or a caller's abort reason produced, and a throwing getter would otherwise escape the classifier that exists to normalize the failure.
- **Fixed a DNS failure reading as a permanent certificate failure.** The TLS classifier falls back to matching certificate wording in the error message, and that message is one the runtime built. For a DNS or connect failure, it has the hostname interpolated into it. `getaddrinfo EAI_AGAIN certificates.internal.corp` matches on the host's name alone, so any deployment calling a `certificates.*` or `certificate-authority.*` host had every DNS blip resolve as `495` with `isRetryable: false`. This veto holds for every method, including an idempotent `GET`, turning the most transient failure there is into a permanent one. Retrying a genuine certificate failure wastes milliseconds. Refusing to retry a DNS blip defeats the point of having retries. A code that names a transport failure now settles the question and the message is not consulted. **This predates the changes above:** `NodeAdapter` has used this classifier all along, so the false positive was live on Node, and `FetchAdapter` adopting it only widened the surface. Note the fix could not simply be "skip the message whenever the error has a code", because OpenSSL exposes far more verification failures than the classifier names, and `CERT_UNTRUSTED`, `CERT_REJECTED`, `HOSTNAME_MISMATCH`, `UNABLE_TO_GET_ISSUER_CERT` and `INVALID_CA` match no code rule at all, so the message is the only thing that catches them. Nothing covered those nine, which is how a change breaking every one of them could leave the suite green. They are covered now.
- `CRL` is matched as an underscore-delimited token rather than as a substring. This keeps the argument for asking by property rather than by list. Future OpenSSL CRL codes still match, including the plural `NO_CRLS_INCLUDED`, while excluding `CRLF`, the one word that shares the prefix by accident and the one a header- or framing-error code would plausibly be named for. Such a failure is a connection problem, the opposite of a permanent certificate verdict.
- Clarified in the `isStreamError` doc comment and in [http-client](./docs/http-client.md) that for replay decisions a stream error groups with a **real response**, not with a transport failure. Both leave you without a usable body, but a `status: 0` transport failure may never have reached the server, while a stream error means it arrived and may have committed, just as a 500 tells you. The resemblance is superficial and inverts the decision.
- **A truncated `3xx` keeps its redirect target.** `FetchAdapter`'s post-header failure path reported the real status but not `wasRedirectDetected` or `detectedRedirectURL`, which the intact path resolves for every response. So with `followRedirects: false`, a `302` carrying a `Location` header whose body was then cut short arrived with nothing to say where it pointed, while the identical intact response reported the resolved absolute URL. The headers arrived before the body failed, so the target is known just as well either way.
- **A truncated `3xx` is no longer followed.** `HTTPClient` checked the redirect status before the failure state, so with `followRedirects: true` a `302` whose body failed after headers arrived was followed like any other. The `Location` header had survived, which is exactly what made this quiet: the hop continued, a healthy destination answered `200`, and the attempt that failed was no longer the one being reported. This left a documented terminal failure resolving as a success. A per-attempt timeout striking mid-body is the sharpest form of it, since `wasTimeout` rides on the attempt result and the next hop overwrites it with its own. Redirect following is now gated on `!isStreamError`, so the response reports the real `3xx` status with `isStreamError`, the timeout if there was one, and still `wasRedirectDetected` / `detectedRedirectURL`, so the caller loses none of what the previous entry restored. The `followRedirects: false` branch is deliberately not gated: it follows nothing, and reporting a truncated `3xx` exactly as it reports an intact one is what that branch is for.
- **A truncated `3xx` reported by a _thrown_ abort keeps its redirect target too.** Both adapters resolve `wasRedirectDetected` / `detectedRedirectURL` on a post-header failure they hand back as a response, but when the body fails via a tagged throw the client rebuilds the response itself from `streamAbortStatus` / `streamAbortHeaders`, and those two fields were simply never set on it. That was invisible while such a hop was still followed. Making a stream error terminal for a `3xx` is what exposed it, since nothing downstream resolves the target any more. A per-attempt timeout striking mid-body, the sharpest case for the entry above, therefore reported `wasRedirectDetected: false` on a `302` whose `Location` header had arrived intact, and with `followRedirects: false` the same response came out the other way round: that branch hardcodes the flag, so it claimed a redirect and had no destination to name. The client now resolves both from the tagged headers, exactly as `FetchAdapter` does on the path where it resolves rather than throws.
- **A rejected install no longer destroys the shared state it replaced.** Rollback exists so a failed install leaves the environment exactly as found. That held for the three methods, where deleting them is the undo, but not for the shared-state key: once an unusable state object could be _replaced_ rather than reused, rolling back deleted it outright, so a failed install destroyed another copy's object as a side effect. The original descriptor is now put back in place and never deleted first, since whatever rejected the definition may have sealed the global object and re-adding a key to a non-extensible object throws. Reaching this at all takes the one piece of caller-controlled code that runs between the preflight and the first definition, the `EventTarget` constructor itself. A fixture uses exactly that to seal the global mid-install, and asserts the original object comes back by identity.
- **A backing target whose `bind` returns a non-function no longer installs.** `bind` is an ordinary property on a method, so a target reachable through the shared global can replace it with something that returns a non-function without ever throwing, while every cheaper check passes, since the three members still read as functions. Guarding only a throwing `bind` put that value straight onto `globalThis` and reported `'installed'`: `addEventListener` became a number, `isGlobalEventTargetPolyfilled()` claimed the polyfill was in place, and every `reportError` dispatch threw `TypeError`. That is strictly worse than not installing, because these methods start out absent. What `bind` returns is now checked, and a target that fails it is passed over for a fresh one. A related gap in the result codes is closed at the same time: an `EventTarget` constructor that is callable but cannot produce a usable instance. It may throw on construction or return something that cannot service the three methods. The constructor now reports `'unsupported'` because nothing was ever offered to the global object, so `'blocked'` would have been the wrong story, and nothing is left behind.
- **The backing event target is re-validated at the moment the globals are bound to it.** `installGlobalEventTarget` validated the shared state's `target` when it read the state, then bound `globalThis.addEventListener` and friends to a second, unguarded read of the same field, the one read in the module that actually matters. The field belongs to an object anything on the global object can reach, so a getter returning a real `EventTarget` when probed and something else afterwards would have bound the three methods to a value that never passed a check, and a getter throwing on that second read turned a perfectly viable install into `'blocked'` with all three methods rolled back, leaving Node with no event methods at all. The bind now takes the target and the three methods off it in one validated pass. Binding a method read later would have been the same gap moved one level in, since a method on somebody else's object is no more ours to trust than the field holding it. A target that no longer vouches for itself is treated as absent: installation proceeds with a fresh one, which orphans nothing, since a target that cannot service the three methods never had listeners registered through this module.
- Corrected the `retrySuppressedReason` documentation for `adapter_veto`, which said no built-in adapter produces it. `NodeAdapter` and `FetchAdapter` do not, for the reason given, but `MockAdapter` does. `transportError: { isRetryable: false }` leaves the default retryable `status: 0` in place, so the veto is what stops the retry. That is the point of the example the same page already gives.

## Unreleased

- **`LifecycleManager`'s async methods no longer reject.** Every one answers with a result object, including when something unplanned goes wrong - a bug in the manager, or a component getter such as `getDependencies()` that throws. The promise resolves with `code: 'unknown_error'` (`'error'` for messaging, health, and `trigger*()` results; an empty array for `broadcastMessage()`), and the original is reported on the global `'error'` channel. `ShutdownResult` gains an optional `error`, and `UnregisterFailureCode` gains `'unknown_error'`. Because nothing rejects, an operation can be started without awaiting it and its result read later from the same promise - `const pending = manager.stopAllComponents(); pending.then(...)` - or dropped with `void`. See [running operations in the background](./docs/lifecycle-manager.md#running-operations-in-the-background).
- A shutdown pass that throws outright now resolves `stopAllComponents()` with that failure instead of rejecting it, and emits the same result on `lifecycle-manager:shutdown-completed`, which now always pairs with `lifecycle-manager:shutdown-initiated`. The result lists the components that had already stopped, scopes `stalledComponents` to the ones that pass had in view, and updates `getLastShutdownResult()`. The escalation window is armed exactly as it is for a stalled or timed-out pass, so `onForceShutdown` stays reachable. `restartAllComponents()` resolves with the crashed result as its `shutdownResult` and skips its startup phase.
- An automatic process-signal attach that throws now fails the start with the new code `'signal_attach_failed'` (on both `StartupResult` and `ComponentOperationResult`) instead of rejecting with manager state still held. With `attachSignalsBeforeStartup`, a throw during `startAllComponents()` used to leave the manager in startup forever - every later start got `already_in_progress` and every `stopComponent()` got `startup_in_progress` - and during `startComponent()` it left the component stuck in `starting`; the start is now refused and that state released. With `attachSignalsOnStart`, which attaches once a component has started, the throw came after the component was marked running; that component is now stopped again and its start fails, so a process configured to handle signals never stays up without them. In `startAllComponents()` this fails the whole startup with `'signal_attach_failed'` and rolls it back, optional component or not. An explicit `attachSignals()` call still throws.
- A process-signal detach that throws once the last component stops (with `detachSignalsOnStop`) no longer sends a clean graceful stop on to the force phase, or makes `unregisterComponent()` reject after it had already removed the component. The detach failure is logged and reported, and the stop or unregister completes. An explicit `detachSignals()` call still throws.
- `triggerReload()`, `triggerInfo()`, and `triggerDebug()` no longer reject when a configured `onReloadRequested` / `onInfoRequested` / `onDebugRequested` callback throws or rejects. They resolve with `code: 'error'` and report the failure.
- A registration that failed after the component was already committed to the registry now reports `registered: true` and emits `component:registered`, matching the registry, rather than claiming it was rejected.
- A per-component stop or start that crashes after claiming the component - a component getter such as `shutdownGracefulTimeoutMS` that throws, say - no longer leaves it in `stopping`, `force-stopping`, or `starting` for good, where every later start or stop was refused and it could never be unregistered. A crashed stop now marks the component `stalled` (so it can be retried or unregistered) and emits `component:stalled`; a crashed start puts it back to the state it had before the attempt. Both resolve with `'unknown_error'`.
- `restartAllComponents()` is no longer treated as an operator's retry when it runs while escalation is armed after a failed shutdown. With `countManualRetriesTowardEscalation` enabled it used to advance the count - reaching `forceAfterCount` ran `onForceShutdown` instead of restarting - and with it disabled it cleared the count outright. Only shutdown requests - signals and `stopAllComponents()` - count. The restart's stop phase is still a shutdown pass, so its outcome settles escalation the way any pass does: a clean stop clears it, and a failed one re-arms it with the count carried over.
- A `signals-attached` listener that re-enters the manager during an automatic attach can no longer start the same work twice: a nested `startAllComponents()` gets `already_in_progress`, a nested `startComponent()` of the same component gets `component_already_starting`, and a shutdown started from there refuses the start with `shutdown_in_progress` rather than having its state reset underneath it.
- Component-scoped messaging (`ComponentLifecycle.sendMessageToComponent()` / `broadcastMessage()`) resolves the same way the manager's own methods do, instead of rejecting on an unexpected failure.
- `SignalBroadcastResult` and `HealthReport` gain an optional `error`, set when the call failed as a whole - a custom `on*Requested` callback that threw, or an unexpected failure.
- A start that crashes after the component was already marked running now stops it again, so its failed result is true and a bulk startup's rollback is not left with a component running outside it. When stopping it again after a failed `attachSignalsOnStart` attach does not take, bulk startup's rollback now covers that component too.
- A per-component stop that crashes into a stall now releases any pending force-stop waiter. Like every other stall, it leaves process signals attached, so the operator's next Ctrl+C still reaches escalation.
- A component that fails a `broadcastMessage()` now fails only its own entry (`code: 'error'`) instead of discarding the answers already collected from the others.
- A shutdown signal that arrives while a pass is running is now always answered by the in-progress path. Against an escalation window that had already lapsed, it used to fall through, emitting `signal:shutdown` a second time and reseeding escalation under the running pass.
- Documented that `lifecycle-manager:shutdown-completed` and `shutdown-escalation-armed` listeners run while the pass still holds its shutdown latch: `getSystemState()` reports `shutting-down` there, and an operation started from one - a retrying `stopAllComponents()`, say - is refused with `already_in_progress`. Defer it out of the listener (`setImmediate`, `queueMicrotask`), or `await` the promise `stopAllComponents()` returned.
- A `restartAllComponents()` stop phase no longer seeds a `repeatedShutdownRequestPolicy` cycle: nobody has asked the process to go down yet. The first shutdown signal during it is treated as the operator's initial request - it cancels the restart and starts the cycle with that signal as `firstMethod`, without being counted. It used to count as the first press, so force fired one press early and `ForceShutdownContext.firstMethod` reported `'manual'`; and a restart whose stop phase failed with no signal at all armed escalation on its own behalf, so the next Ctrl+C forced at once. `getShutdownEscalationStatus()` shows no cycle during a restart until a signal arrives. A restart that inherits a live cycle keeps it, and signals count against it as before.
- `LifecycleManager` now reads each component's name once, at registration, and uses that everywhere afterwards. A component whose `getName()` throws after registration can no longer crash broadcasts, health checks, shutdown ordering, or any other operation that looked it up. A `getName()` that returns something other than a string is refused at registration with `'unknown_error'`.
- `getValue()` - and the component-scoped `ComponentLifecycle.getValue()` - no longer throws on an unexpected failure. It returns `code: 'error'` with the new optional `ValueResult.error`, and reports the failure on the global `'error'` channel.
- `unregisterComponent()` now clears the manager's own state before calling the component's internal unregister hooks, so a hook that throws no longer leaves a component removed from the registry but still present in the state maps.
- A crashed per-component start or stop now only acts on a run it owns: a start that crashes before refusing an already-running component leaves it running, and a stop that crashes before refusing an in-progress stop no longer stalls it. The broadcast function handed to `on*Requested` callbacks resolves rather than rejects.
- Registration is all-or-nothing: the registry entry and the manager's state for it are committed together, and a component registration hook that throws rolls the whole registration back - on the component too, so it can be registered again. Registration also reads a component's name exactly once, so a `getName()` that answers differently - or throws - on a second read no longer skews `startupOrder` or fails the registration.
- `startAllComponents()` reads its options before taking the startup latch, and a component's `startupTimeoutMS` is read before the component is claimed as `starting`, so a throwing getter in either can no longer leave startup or the component stuck, or signals attached behind a start that never began.
- `unregisterComponent()` checks again for a bulk startup or shutdown after stopping the component, and refuses with `bulk_operation_in_progress` - the component stays registered, stopped - rather than removing it from under one that began meanwhile.
- A stalled component's force-phase retry during `stopAllComponents()` now goes through the same safety net as any other stop, so a force-phase failure outside the component's own hooks marks it stalled instead of ending the whole shutdown pass before the components after it were stopped.
- `triggerReload()` / `triggerInfo()` / `triggerDebug()` read each component's handler - and, when it has one, its `signalTimeoutMS` - per component, so one that throws becomes that component's entry instead of ending the broadcast for everyone after it. That entry is new in shape: `called: false` with `code: 'error'`, and it counts toward the broadcast's `error` / `partial_error` code like a handler that threw.
- An escalation window that expires now resets its state before emitting `lifecycle-manager:shutdown-escalation-expired`, so a shutdown started from that listener seeds its own cycle rather than having it wiped - which left `firstMethod` null and `onForceShutdown` unreachable for that pass.
- A failure while stopping a component that finished starting after its startup timeout is now logged as a warning and reported on the global `'error'` channel, instead of only at debug level.
- A startup refused because a `signals-attached` listener started a shutdown no longer detaches process signals from under that shutdown.
- A startup aborted by a shutdown now reports the optional failures and dependency skips it had already collected.
- A `stopAllComponents()` or `restartAllComponents()` that does not come through an armed escalation window now starts a fresh `repeatedShutdownRequestPolicy` cycle. It used to inherit whatever state an earlier failed cycle had left - one with arming disabled, or one whose force had already fired - so presses against it were counted against the old cycle, and with force already marked as fired, `onForceShutdown` could never run again. A shutdown request made from inside `onForceShutdown` still continues the cycle that fired it.
- The first shutdown signal during a restart's stop phase starts the escalation cycle even when a `stopAllComponents()` or `logger.exit()` reached that stop phase first.
- `unregisterComponent()` checks, after stopping the component, that the same instance is still registered. If a `component:stopped` listener unregistered it - and perhaps registered a replacement under the same name - it now answers `component_not_found` instead of removing the replacement.
- A startup-crash rollback that leaves an optional component stalled no longer relabels it `failed`.
- The start and stop safety nets now act on a component only through a claim they own. A start or stop that crashed before claiming the component - while another one claimed it across an `await` - no longer resets, stops, or stalls that other one's work.
- A `lifecycle-manager:shutdown-escalation-expired` listener that starts a shutdown is no longer undone by the request that expired the window: a manual stop no longer wipes the cycle that shutdown just seeded, and a signal is answered as one landing on a running shutdown.
- A component's `onStartupAborted` is read before its start, so a getter that throws fails the start instead of escaping the startup timer as an uncaught exception.
- `broadcastMessage()` reads its options before emitting `component:broadcast-started`, so a throwing option no longer leaves a started event with no completed event after it.
- The manager's guarded logger guards frozen log methods, and fully frozen service objects, like any other: its proxy targets a fresh object inheriting from your service rather than the service itself, so the engine's proxy invariants never pin a read to an unguarded value. Its cache of `entity()` children is a plain recency-ordered `Map` (still capped at 256), rather than the `LRUCache` that sized each child with `JSON.stringify` - running the child's getters outside every guard. A native promise returned from `entity()` with its own throwing `then` is contained too.
- A startup that crashes during a rollback no longer rolls the same components back twice.
- A shutdown pass now fails when a component's stop failed without stalling it - a stop that crashed before claiming the component, leaving it running - instead of reporting success with that component still up. `restartAllComponents()` reports the failed shutdown phase accordingly.
- A component's `onGracefulStopTimeout` and `onShutdownForceAborted` hooks are read before their timers start, like `onStartupAborted`, so a getter that throws fails the stop up front instead of escaping the timer as an uncaught exception and leaving the stop waiting forever.
- A `signal:shutdown` listener that calls `stopAllComponents()` no longer resets the escalation cycle that signal just started.
- A startup rollback that throws partway now still rolls back the components it had not reached, without stopping any twice.
- Signal-driven reload, info and debug broadcasts go through the same safety net as `triggerReload()` and friends.
- A failed `unregisterComponent()` reports `wasStopped: true` when the component was stopped before the failure.
- A `broadcastMessage()` that fails partway keeps the per-component answers already collected and still emits `component:broadcast-completed`.
- A shutdown pass that ends cleanly now detaches process signals (`detachSignalsOnStop`) when nothing is left running, covering a startup refused or aborted by that shutdown, which skipped its own detach while the pass ran and left the handlers - and raw-mode stdin - attached.
- A shutdown pass halted by `haltOnStall` no longer reports success while components it never reached are still running.
- A component's stop timeouts (`shutdownGracefulTimeoutMS`, `shutdownForceTimeoutMS`, and a per-call `timeout`) are read before the stop claims it, so a throwing getter fails the stop with the component still running instead of marking it stalled although `stop()` never ran.
- `broadcastMessage()` reads its options once - `componentNames` included - and sends every target the same values. `sendMessageToComponent()` and `getValue()` read theirs before emitting `component:message-sent` / `component:value-requested`, so a throwing getter no longer leaves either event without its pair.
- A startup that fails with `signal_attach_failed` reports in `startedComponents` any component its rollback could not stop.
- During a shutdown pass, stopping the last running component no longer detaches process signals (`detachSignalsOnStop`) while stalled components remain; the pass detaches only once it ends cleanly - or, for a clean pass that ran during a bulk startup, the startup detaches as it finishes - so a failed pass keeps Ctrl+C reaching escalation.
- Automatic signal detach (`detachSignalsOnStop`) now waits while any component is stalled, wherever the last stop comes from. A startup cleanup stop that ran after a failed shutdown pass - a bulk startup whose late-finishing component it stopped, say - used to detach the handlers even though that pass had stalled a component and armed escalation, leaving the next Ctrl+C with nothing to reach.
- A shutdown pass settles each component against the registry once when it finishes - stopped, stalled, still stopping elsewhere, or still running - and fails only for the last three. A component that had already gone down some other way (a late-startup cleanup, say) no longer fails the pass as "not running".
- A `getValue()` whose handler throws now returns that error on `ValueResult.error`, as health checks and messages do.
- A `startAllComponents()` that crashes partway through - a component getter that throws, say - now rolls back the components it had started, as any other failed startup does, and resolves with `'unknown_error'`.
- **A `Logger` that throws or rejects can no longer fail or derail a `LifecycleManager` operation.** `LifecycleManager` logs from roughly 140 places - OS signal handlers, timer callbacks, floating promise chains, the middle of a startup or shutdown pass - and a log method that threw propagated into whichever operation happened to be logging: a throw in the shutdown stop loop left the remaining components running. The manager now wraps its own service logger once, at construction, so every log call, `entity(name)` chains included, is routed through `runCallbackSafely`: a synchronous throw, a returned rejecting promise, and a log method behind a throwing getter are all contained and reported on the global `'error'` channel, never back through the logger. An `entity()` that throws, or returns `undefined` or a promise, is reported and the line falls back to the service scope. Reports are labelled by logger method - `lifecycle-manager logger.warn` in place of per-line labels such as `shutdown notification after SIGTERM` - with the original on `cause`; adjust any listener matching on those strings. Your logger object is never wrapped or modified: `enableLoggerExitHook()`, `logger.exit()`, and each component's scoped logger still use the exact instance you passed in. This contains failures rather than repairing them - a logger that throws still loses those lines.
- A shutdown request that arrives while `restartAllComponents()` is running its shutdown phase now wins: the restart skips its startup phase instead of starting them all again after an operator or caller asked the process to stop. A `SIGINT`/`SIGTERM`, a direct `stopAllComponents()` call, and a `logger.exit()` under `enableLoggerExitHook()` all count. `RestartResult` gains `startupSkippedByShutdownRequest`, present and `true` only in this case, and `StartupResult` gains the code `'shutdown_requested_during_restart'`. The request itself is still answered with `already_in_progress` - the restart's shutdown phase is the shutdown the caller gets. The skip is decided before the shutdown phase's own outcome, so a stalled or failed phase paired with a request still reports the request. Only the restart whose shutdown phase is actually running can be cancelled: a restart started while a shutdown is already running has its own shutdown phase refused and never reports a skip. A request during the restart's startup phase instead aborts that startup through the existing `shutdownToken` check (`'shutdown_in_progress'`). This also covers an `onForceShutdown` that calls `restartAllComponents()`: the request that fired it is recorded on the restart's pass rather than dropped. The skip only means nothing is started again: whether every component stopped is still `shutdownResult`'s to say, and a shutdown phase that stalled or timed out can leave some running.
- A shutdown request now consumes the post-failure escalation window before running escalation callbacks rather than after, so a shutdown request made from inside `onForceShutdown` or a `lifecycle-manager:shutdown-escalation-forced` listener continues the request that fired it instead of counting as a second press. With `countManualRetriesTowardEscalation` enabled, `getShutdownEscalationStatus().requestCount` no longer counts that one request twice. `stopAllComponents()` calls made while a shutdown is running never count toward escalation, whatever that flag says.
- A refused `stopAllComponents()` now reports `reason: 'Shutdown in progress'` in place of `'Shutdown already in progress'`. The `code` is still `'already_in_progress'` and is what callers should branch on.
- Auto-detach (`detachSignalsOnStop`) has one idle check: nothing running or stalled, and nothing transient in flight - no startup or shutdown latch, no component starting or stopping, no late-startup cleanup. A detach due while something transient is in flight is deferred and runs when it ends, rather than being dropped or run under it: stopping the last running component while another was still starting used to detach the handlers the new one would need. A clean shutdown pass now detaches before emitting `lifecycle-manager:shutdown-completed`, as the last component's stop did before this release, so a listener there finds stdin restored and can attach again without being undone.
- `attachSignalsOnStart` attaches whenever a component starts and handlers are not attached, not only for the first running component. A start that finished while another start was being rolled back for a failed attach came up without handlers. It only attaches if the component is still running after its `component:started` listeners, so one that stopped from there does not leave handlers on an idle manager.
- A stall cleared by a late stop that a newer attempt had already superseded - a failed `forceStalled` start, say - now runs the detach check, so the handlers come off once nothing is left.
- A shutdown pass skips a component some other path already took down, in whatever state that left it, instead of treating it as a failed stop and halting (`haltOnStall`) before the components after it.
- A pass that falls short names every reason: `Stalled: api; Failed to stop: db` rather than only the components a `haltOnStall` break never reached.
- A signal raised from inside escalation handling - `onForceShutdown`, or a `shutdown-escalation-forced` / `signal:shutdown` listener - continues the cycle that fired it instead of reseeding it, which let the next press force a second time.
- `logger.exit()` called synchronously from `onForceShutdown` (with `enableLoggerExitHook`) proceeds at once. It used to wait out the running pass - its whole timeout, for the stall that prompted the force - or, from the post-failure armed window, start and wait out a new one. An exit from anywhere else during escalation - a `signal:shutdown` listener, say - still waits for the shutdown, as it did before this release.
- `unregisterComponent()` is refused while a start or stop is in flight for the component, with the new `UnregisterFailureCode`s `'component_starting'` and `'component_stopping'` - checked again after its own stop, since a `component:stopped` listener can start the component again in between. Removing it mid-start left whatever `start()` brought up running with nothing to stop it; mid-force-retry, the retry later marked a replacement stalled or stopped; and a graceful stop in flight was stopped a second time and reported as `stop_failed`. A start superseded while `start()` ran - the component reported an unexpected stop and a listener started it again - no longer marks it running over the newer attempt, and, if `start()` then throws, no longer resets the newer attempt's state, clears its unexpected-stop handler, or emits `component:start-failed`.
- A stop released by its own timeout hook (`onGracefulStopTimeout` resolving what `stop()` awaits, say) clears the stall that follows, as a late stop does; it used to be dropped and the stall kept for good.
- A stalled component whose force retry is still running is not retried again by the next shutdown pass, which ran `onShutdownForce()` twice at once.
- A force attempt that resumes after a late graceful stop and a restart - a `component:stopped` listener starting the component again - no longer marks the running component stopped or emits a second `component:stopped`.
- `restartAllComponents()` skips its startup phase when the stop phase timed out, instead of reporting a startup that never ran as successful; and after a crashed stop phase its `startupResult` carries the `error`.
- A `stopAllComponents()` started from a `component:starting` listener is noticed by that start, which sends the component through the stop pipeline once it is up. A shutdown started from a listener on the last component's `start-failed-optional` or `start-skipped` event fails the bulk startup with `shutdown_in_progress` instead of reporting success.
- `registerComponent(c, { autoStart: true })` during a bulk startup, once its first component is running, starts the component instead of being refused with `startup_in_progress`.
- An unregister whose `_markUnregistered()` throws still clears the component's registration, so it can be registered again.
- A component without `onShutdownForce` no longer has its force-timeout getters read, so a throwing one cannot replace the real graceful error or suppress `component:shutdown-force`.
- `runCallbackSafely()` and `safeHandleCallbackAndWait()` report a revoked proxy as not a function instead of throwing.
- `startAllComponents({ ignoreStalledComponents })` now requires exactly `true`; a truthy non-boolean no longer counts.
- A component whose `onShutdownWarning` or `getDependencies()` getter throws during a shutdown pass is skipped for that read and reported, instead of ending the whole pass as `'unknown_error'` with every component still running.
- A stop deferred out of `lifecycle-manager:shutdown-completed` with `queueMicrotask`, as the docs suggest, now cancels a restart the same way a request during its stop phase does (`startupSkippedByShutdownRequest`). It used to be reported as a startup refused with `shutdown_in_progress`. Another restart started in that gap does not count.
- An `onShutdownForce()` that rejects with the manager's own timeout text is no longer taken for a force timeout.
- A stop whose `stop()` or `onShutdownForce()` settles right as its timeout fires - released by its own timeout hook, say - now succeeds instead of stalling, halting a shutdown pass, or waiting out a force phase it no longer needs, and a force retry released that way no longer stays stalled.
- `onShutdownForce` is read once per force phase and that value is called, so a getter or swap that answered `undefined` the second time can no longer mark a component stopped with no force handler run. A `forceImmediate` stop reads the component's force getters before it clears the unexpected-stop handler, so a throwing one leaves that handler in place.
- A start in flight when a shutdown pass begins, which lands during the pass and is still stopping or stalls stopping when it ends, fails the pass rather than letting it report success. A component another stop owned is settled once that stop is done, whatever state it left behind.
- `startAllComponents()` refuses with `partial_state` while any component is still stopping, instead of counting it as running - which reported a restart's startup as successful though `start()` never ran.
- A stalled component's force retry is not run over a `forceStalled` start in flight; the start path stops it once it is up. The shutdown loop reads stalls when it reaches each component, not from a snapshot, so a stall that cleared mid-pass no longer halts it.
- `unregisterComponent()` refuses with `component_running` when a `component:stopped` listener started the component again and it is already up.
- A component auto-started (`autoStart: true`) from inside a bulk startup joins that startup, so a later failure rolls it back with the rest. One whose `start()` is still running when that startup rolls back stops itself once it is up, and its auto-start fails with the new code `'startup_rolled_back'`. It is held to that startup's deadline, so one still starting when the startup times out is cleaned up when it finishes, as the startup's own late starts are.
- A startup that rolls back reports in `startedComponents` any component its rollback could not stop, as the other failure paths already did.
- A crashed `unregisterComponent()` reports `wasRegistered` as of the call, without calling the public `hasComponent()` - an override that threw made it reject.
- A component whose `getDependencies()` throws is reported on the global `'error'` channel - once per registration - when it fails registration, and no longer blocks stopping, restarting, or unregistering other components.
- A throwing `getValue` getter is answered with `code: 'error'`, reported, and paired with `component:value-returned`.
- A throwing `_clearUnexpectedStopHandler()` override no longer turns a start timeout into `unknown_error`.
- A promise that carries its own `then` or `catch` can no longer swallow its rejection in `runCallbackSafely()` or the guarded logger.
- Every promise a component hands back - from `start()`, `stop()`, `onShutdownForce()`, `healthCheck()`, `onMessage()`, `onShutdownWarning()` and the `on*` signal handlers - is adopted through the built-in `Promise.prototype.then` before the manager races or watches it. A native promise carrying its own no-op `then` used to hold the call for its whole timeout, and its real rejection went unhandled.
- A stop timeout is counted one macrotask after its timeout hook runs, so a hook that releases what `stop()` or `onShutdownForce()` awaits lets the stop finish as a success. This replaces the earlier bookkeeping for stops that settled as they timed out; a start's timeout still counts at once, since its abort hook exists to abort it.
- A `getValue` handler that returns a promise answers `code: 'error'` - `getValue()` is synchronous - and its rejection is handled instead of going unhandled.
- `stopAllComponents()` records a request to stay down on a running pass before reading its options, so a throwing options getter can no longer let a restart start everything again.
- `onMessage` is read once, guarded, and that value is called.
- `validateDependencies()` reads each component once, guarded, so one whose `getDependencies()` throws is reported and checked as declaring none, and one whose `isOptional()` throws is reported and checked as required, instead of making the call throw.
- An `autoStart` registration made from a `signals-attached` listener, before a bulk startup's loop begins, is left to that loop instead of being started twice - which failed the whole startup as `required_component_failed`. Its registration result says so with the new `autoStartDeferred: true`, since whether it starts is then that startup's to decide.
- `healthCheck` is read once, guarded, and that value is called.
- When `runCallbackSafely()`'s `onError` itself throws, both errors reach the console rendered through `errorToString`, so fields an error marks sensitive stay masked.
- Another component's `getDependencies()` - read to find dependents, validate, protect dependencies during shutdown, or check a registration during startup - is read through one guard: a throw, or a result that is not an array, is reported and read as declaring none, and a list with non-string entries is reported and read as its string entries. The result is copied inside the guard, so an array subclass or proxy cannot run code past it.
- A `healthCheck` getter that throws is logged and emits `component:health-check-started` followed by `component:health-check-failed`. An `onMessage` getter that throws is logged and emits `component:message-failed` alone - nothing was sent, as its `sent: false` result says.
- `validateDependencies()` lists components whose `getDependencies()` throws, does not return an array, or returns a non-string entry in a new `unreadableDependencies` field (counted in `summary.totalUnreadableDependencies`), and reports `valid: false` for them, since the component's own start fails on the same list. A throwing `isOptional()` is not listed: validation reads it as required, as startup does.
- An auto-start is not started when the bulk startup it would join is already rolling back (`startup_rolled_back`). One that outlives the startup it joined keeps that startup's deadline but no longer reports a timeout on its behalf.
- Registering a component another one depends on, before a bulk startup's loop begins, is accepted rather than refused with `startup_in_progress`; the loop orders and starts it.
- A stalled component's force retry decides from the same `onShutdownForce` read it calls whether to open a new stop attempt, so a floating `stop()` is not orphaned when no force handler runs.
- `component:registered` carries `autoStartDeferred` too, and `registerComponent()` includes that key only when it is `true`, as `insertComponentAt()` does.
- A dependency list reporting an implausible `length` - a proxy claiming `Infinity`, say - is treated as unreadable instead of being iterated, which would have blocked the event loop.
- A bulk startup that ends before its loop runs - refused because a shutdown started, or unable to compute its order - warns about auto-starts that were left to it (`autoStartDeferred`) and so never attempted.
- `safeHandleCallbackAndWait()` invokes its callback through `Reflect.apply`, and reads a promise the callback returns the same hardened way `runCallbackSafely()` does.
- Every dependency read is bounded and guarded, so a list reporting `length: Infinity` can no longer block the event loop. Startup ordering and the shutdown pass read other components' lists tolerantly - a broken entry is reported and skipped - so one component cannot break the order for the whole registry. A registration candidate whose `getDependencies()` throws or reports an implausible length is refused, and a component whose list is broken fails its own start with `missing_dependency`, naming it. `validateDependencies()` flags the same lists, and both require the declared array (a `Set` is refused).
- A throwing `_clearUnexpectedStopHandler()` override is contained on every path - stop, force stop, start and unregister - instead of failing a stop before it had claimed the component.
- `unreadableDependencies` lists each component once, and a broken `getDependencies()` is reported once per registration of a component instead of on every read.
- An auto-start joining a bulk startup that is already past its deadline starts on its own timeout instead of being refused.
- Signal handlers (`onReload`, `onInfo`, `onDebug`) are called with their component through `Reflect.apply`, not through the handler's own `bind`.
- `isOptional()` is read the same way everywhere: only an answer of exactly `true` makes a component optional, and one that throws is reported once and treated as required, instead of crashing a bulk startup. A bulk startup reads a dependency's `isOptional()` only when that dependency was skipped or failed, and a single start only for a dependency that is not running.
- A component that is already running, starting, or stopping answers as such before its dependency list is checked, so one whose list broke after it started no longer fails a bulk startup. A broken own list - `getDependencies()` throwing, not returning an array, or holding a non-string entry - fails the start as `missing_dependency`, reported once per registration.
- A promise returned by a component hook or a callback is followed as `await` would follow it, except that a `then` attached to the promise itself, as an own property, is never trusted: a native promise with its own `then` is read through the built-in `Promise.prototype.then`, so one carrying a no-op `then` can no longer hang an operation or leave its rejection unhandled. A `then` a `Promise` subclass defines on its prototype - a lazy promise that starts its work there - and a proxy around a promise are followed as `await` follows them (a proxy works when its `then` does). Something inheriting from `Promise.prototype` with an own `then` that the built-in refuses is rejected: a native promise whose `constructor` misbehaves (a getter that throws, a value that is not a constructor, a species that throws) fails the operation with that error instead of hanging, and so does an `Object.create(Promise.prototype)` fake. Such a broken promise cannot be read without modifying it, which the library never does, so its own rejection is left unhandled.
- A native promise returned by a callback or hook is recognized as one without reading its `then`, so one whose own `then` is not a function, or is a getter that throws, is still adopted - and its rejection handled - instead of being passed through as a plain value or leaving its rejection unhandled. This covers `runCallbackSafely()`, `safeHandleCallbackAndWait()`, the guarded logger's `entity()`, and `getValue` handlers.
- The logger reads a promise returned by a sink's `write()` or `writeDiagnostic()`, and the failure reporters read one returned by `onFormatError` and sink failure handlers (`ArraySink` included), the same way: a rejected native promise whose own `then` is not a function, or does nothing, is followed and reported instead of leaving its rejection unhandled.
- `HTTPClient` reads an adapter's `send()` result and `requestBodySettled`, and a request interceptor's result, `MockAdapter` a route handler's result, and `RetryRunner` an operation's returned promise the same way, so a rejected native promise with a non-function or no-op own `then` - or its own `constructor` - is followed rather than left unhandled, and can no longer hang a request or an attempt.
- A start reads everything of the component's own code it needs - its dependency list, its dependencies' `isOptional()`, its timeout and abort handler - before deciding, then checks the component and its dependencies without running any more of it and claims the component. Those reads can start, stop, unregister or replace components re-entrantly: one that started the same component got `start()` run twice, and one that stopped a dependency let the start go ahead on it. A dependency's `isOptional()` answer applies only to the instance that gave it, not to one registered under its name since. Each start option is read once.
- A registration refused as a dependency cycle, or rolled back by a failed hook, no longer spends the component's one report of a broken dependency list, so the registration that follows still reports it.
- `startComponent()` with `allowNonRunningDependencies` no longer reads a non-running dependency's `isOptional()`, whose answer it ignores.
- A bulk startup reads each component's dependency list once, and uses that one read for the startup order, its skip checks and the component's own start. Read again for each, a list that answered differently could put a component ahead of a dependency it then failed on, rolling the whole startup back.
- A component registered by one of a bulk startup's dependency-list reads is ordered and started with the rest: its auto-start waits for the startup's loop instead of starting at once, ahead of dependencies the loop had not started, and one registered without `autoStart` is no longer left unstarted while the startup reports success.
- A message handler that times out emits `component:message-failed` with `timedOut: true` and `code: 'timeout'`, as one that threw or rejected does, and as the event's documentation says. The event's `error` describes the timeout; the result still answers `error: null` with `timedOut: true`.
- A registration that fails after it has committed - the component is registered - reports what it had done: the startup order it computed, whether its target was found, where it is (`actualPosition`, described from the registry as it stands, and `manualPositionRespected`), and an auto-start it attempted or left to a bulk startup (`autoStartAttempted`, `autoStartDeferred`, `autoStartSucceeded`, `startResult`), on the result and on `component:registered`. A caller told `autoStartAttempted: false` for an auto-start that ran could start the component again.
- A successful registration reports the component's index and `actualPosition` as they are once its auto-start has finished, rather than as they were before it: a `start()` that registers other components moves it.
- A dependency that is stopping no longer counts as running when a component starts on it: its stop had already checked for running dependents, so the dependent ended up running on a stopped dependency. The start now fails as `dependency_not_running`.
- Registration commits a new registry array instead of splicing the live one, as unregister already did, so a loop over the registry - the startup order, finding dependents - that a registration lands in from a `getDependencies()` read keeps walking the array it started on, instead of shifting names out of step (a false dependency cycle) or listing a dependent twice.
- Registration reads everything of the caller's code it needs first - once the checks that need none of it have passed, so one refused for an invalid position or a shutdown reads nothing - whether the instance says it is registered, its own dependency list, and every registered component's list, including components those reads register - repeating until those reads stop changing anything, then makes every check and commits without running any more of it. A read that begins a shutdown stops the remaining reads, and the registration is refused as `shutdown_in_progress`; a bulk startup's reads stop the same way. That code could register, unregister, start a bulk startup or begin a shutdown in the meantime: two components could end up registered under one name, inserted at a stale index or next to a target that was gone, or checked for cycles against an out-of-date registry. Lazy wiring that registers a helper from `getDependencies()` still registers normally; a registry that every read keeps growing is refused with `unknown_error` and reported. `validateDependencies()` reads the same way, so it checks the registry as it stands, not as it was when it began.
- `runCallbackSafely()` no longer lets a throwing `onError` escape. A synchronous throw previously surfaced at an unrelated call site, and one from the promise rung became an unhandled rejection - fatal under Node's default `--unhandled-rejections=throw`, which is the outcome the helper exists to prevent. Both are now caught and sent to the guarded console rung.
- `runCallbackSafely()` accepts an optional `thisArg`. The callback is invoked with the receiver you supply, so an extracted method such as `logger.info` can keep using `args` instead of a wrapping closure. Passing one without a receiver still loses `this`, which arrives as an ordinary callback failure rather than a `TypeError` at the call site; the docstrings for `safeHandleCallback()`, `safeHandleCallbackAndWait()` and `runCallbackSafely()` now say so.
- `reportToHost()` is public through `lifecycleion/safe-handle-callback`. Use it when you already hold a well-formed `Error` and want listeners to see exactly that. `reportCallbackError()` remains the normalizer for a raw thrown value, which it wraps in an `Error` naming the callback.
- `CallbackResult<T>` is exported and is now a discriminated union, so `if (result.success)` narrows without a non-null assertion on `value` or `error`. Each branch still declares the other's field as optional `undefined`, so reading either without narrowing keeps compiling. `T` defaults to `unknown`, since it can never be inferred from a `callback` typed `unknown`. Code that builds one by hand - a mock of `safeHandleCallbackAndWait()` returning `{ success: true }` with no `value`, say - needs the branch's own fields to type-check.
